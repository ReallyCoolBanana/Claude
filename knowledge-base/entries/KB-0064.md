## Critical Corrections to KB-0059

### 1. Hub Brain: Switch from Phi-4 Mini to Qwen3-4B

KB-0059 recommended Phi-4 Mini 3.8B. Research (KB-0061) revealed significant issues:
- **Hallucinated function names** — invents tools not in the tool list
- **IFEval weakness** — struggles with strict output formatting (critical for an orchestrator)
- **Ollama default template broken** for function calling — requires custom Modelfile
- **vLLM function calling parser doesn't work** (open bug #14682)

**Qwen3-4B is the better choice:**
- Native MCP support
- Dual thinking/non-thinking modes (fast routing vs complex decomposition)
- More robust parallel tool calling
- Stronger instruction following
- ~2.7 GB at Q4_K_M (comparable VRAM to Phi-4 Mini)
- [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507) reaches Qwen3-8B performance level
- Apache 2.0 license

**GGUF download:**
```bash
huggingface-cli download bartowski/Qwen3-4B-GGUF \
  --include "Qwen3-4B-Q4_K_M.gguf" --local-dir ~/models/
```

### 2. FAISS Installation: pip install faiss-gpu Is Dead

KB-0059 showed `faiss-gpu` in pip install. This package is **abandoned**.

**Correct installation:**
```bash
pip install 'faiss-gpu-cu12[fix-cuda]'
# OR via conda (official Meta channel):
conda install -c pytorch faiss-gpu
```

The `[fix-cuda]` extra pins CUDA 12.1 to avoid conflicts with PyTorch's bundled CUDA. The pip package is maintained by [Di-Is](https://github.com/Di-Is/faiss-gpu-wheels), not by Meta — it's unofficial but actively maintained and supports RTX 4070 Super (Compute Capability 8.9).

### 3. FAISS StandardGpuResources Steals 1.5 GB

KB-0059's code doesn't set temp memory. Default `StandardGpuResources()` allocates **1.5 GB scratch space**.

**Always do this:**
```python
res = faiss.StandardGpuResources()
res.setTempMemory(256 * 1024 * 1024)  # 256 MB instead of 1.5 GB
```

At 50K-80K nodes with a flat index, you need <250 MB for the index. The extra 1.25 GB of default scratch is pure waste.

### 4. MCP Package: Use fastmcp, Not mcp

KB-0059 shows `pip install mcp`. The correct package:
```bash
pip install fastmcp  # v3.1.0 by PrefectHQ, Python >= 3.10
```

Import as `from fastmcp import FastMCP`, NOT `from mcp.server.fastmcp import FastMCP`.

**Critical pitfall:** Never use `print()` in stdio MCP servers — it corrupts the JSON-RPC stream and silently breaks the connection. Use `print(..., file=sys.stderr)` or `ctx.info()`.

### 5. Sentence-Transformers VRAM Leak

KB-0059 loads the embedding model in the FastAPI process. sentence-transformers has a [known VRAM leak](https://github.com/UKPLab/sentence-transformers/issues/487) on repeated encode calls.

**Mitigation:**
```python
import torch

vectors = model.encode(texts, normalize_embeddings=True)
vectors_cpu = vectors.copy()  # move to CPU immediately
del vectors
torch.cuda.empty_cache()
```

### 6. Matryoshka: 384-dim Is Viable

nomic-embed-text-v1.5 supports Matryoshka dimensionality. 384-dim loses only ~0.8 MTEB points vs 768-dim but halves memory:

| Dim | MTEB Score | Index Size (50K) | VRAM |
|-----|-----------|------------------|------|
| 768 | 62.28 | 146 MB | 150 MB |
| 384 | ~61.5 | 73 MB | 75 MB |

**Must re-normalize after truncation:**
```python
from torch.nn.functional import layer_norm, normalize

vectors = model.encode(texts, normalize_embeddings=False)  # don't normalize yet
vectors = vectors[:, :384]  # truncate to 384-dim
vectors = layer_norm(torch.tensor(vectors), [384]).numpy()
vectors = vectors / np.linalg.norm(vectors, axis=1, keepdims=True)  # L2 normalize
```

## Corrected Serialization: msgspec, Not msgpack

Research (filesystem migration agent) showed msgspec is **10-80x faster** than plain msgpack and uses 6-9x less memory than orjson.

```bash
pip install msgspec  # not msgpack
```

```python
import msgspec

# Define typed structures for maximum speed
class AdjEntry(msgspec.Struct):
    targets: list[str]
    weights: list[int]
    types: list[str]

encoder = msgspec.msgpack.Encoder()
decoder = msgspec.msgpack.Decoder(dict[str, AdjEntry])

# Encode
data = {"KB-0001": AdjEntry(targets=["KB-0002"], weights=[8], types=["shared_tags"])}
binary = encoder.encode(data)

# Decode
loaded = decoder.decode(binary)
```

## Storage Hybrid: Filesystem + SQLite WAL

Research found SQLite is **35% faster than the filesystem** for blobs under 100KB (all your node files qualify). Recommended hybrid:

| Data | Storage | Why |
|------|---------|-----|
| Node content | Filesystem (JSON per node) | Human-readable, git-diffable, editable |
| Edge indexes | SQLite WAL (`edges.db`) | Fast lookups, atomic multi-edge updates |
| Adjacency cache | msgspec binary | Fastest possible read for hot path |
| Bulk edge logs | JSONL append-only | Easy append, compressible |
| Change tracking | SQLite WAL (same `edges.db`) | Better than inotify, queryable |

## Atomic File Writes

Every file write should use the write-fsync-replace pattern to prevent corruption:

```python
import os, tempfile

def atomic_write(path: str, data: bytes):
    dir_path = os.path.dirname(path)
    fd, tmp = tempfile.mkstemp(dir=dir_path, suffix='.tmp')
    try:
        with os.fdopen(fd, 'wb') as f:
            f.write(data)
            f.flush()
            os.fsync(f.fileno())
        os.replace(tmp, path)  # atomic on POSIX
        dir_fd = os.open(dir_path, os.O_RDONLY)
        try:
            os.fsync(dir_fd)
        finally:
            os.close(dir_fd)
    except:
        try: os.unlink(tmp)
        except OSError: pass
        raise
```

## PyKEEN: RotatE for Link Prediction

For the pointer network's mixed relation types:
- **RotatE** handles symmetry, antisymmetry, inversion, and composition
- At 50K nodes: ~20-50 min training on RTX 4070 Super
- Under 80K nodes: just retrain from scratch (no incremental support)
- Use `predict_target()` with `k` parameter — never `predict_all()` without it

Full pipeline: see KB-0063.
