# 8 Architecture Proposals: Hub Brain + Sub-AI Core Structures for 1M+ Edge Knowledge Graph

## Context
Comparative analysis of 8 different ways to structure a local AI hub controller (Qwen3-4B hub brain + sub-AI worker cores) managing a 1M+ edge multi-domain knowledge graph on RTX 4070 Super (12GB VRAM). The graph contains Wikipedia, KB entries, scripts, SOPs, market research, academic papers, source code, team logs, personal notes, bookmarks, PDFs, and more.

Each structure was independently designed by a separate research agent and evaluated on: routing logic, VRAM fit, cross-boundary handling, scaling from 100K→10M edges, and failure modes.

---

## Structure 1: Domain-Specialist Cores

**Concept:** Partition by knowledge domain — one core owns "finance," another "tech/code," another "science," etc.

**Core roster:** 6 domain cores (Finance, Tech/Code, Science, Ops/Procedure, Personal, Meta/KB) + 1 utility core (embeddings + classification). Each runs Qwen3-1.7B Q4 (~1.1GB VRAM).

**Hub brain role:** Routes queries by domain classification, arbitrates cross-domain conflicts, synthesizes merged results. Maintains a Bridge Table of all cross-domain edges.

**Cross-domain handling:** Edges spanning two domains stored in 3 places: both cores' local indices + a central Hub Bridge Table. Traversal across boundaries requires hub to activate both cores sequentially. A node summary cache (512-token per node) avoids activating a second core for shallow lookups.

**VRAM budget:** Hub 2.5GB + 2 active cores 2.2GB + KV caches 2.3GB + embedding 0.3GB + overhead 0.5GB = ~7.8GB. Leaves 4.2GB headroom.

**Scaling:** At 10M edges, domains split into sub-domains (Science → Science-Bio, Science-Phys). Hub taxonomy config updated; routing adds a second level.

**Best for:** Queries that naturally fall within one domain (most common case).
**Worst for:** Cross-domain queries pay a steep coordination tax (5-20 second latency for 4-domain queries).

## Structure 2: Graph-Partition Cores (METIS/Leiden)

**Concept:** Let the graph's own topology dictate ownership. Leiden community detection finds natural clusters; METIS rebalances oversized communities. No human-defined categories.

**Partition count:** 8 partitions of ~125K nodes each.

**Hub brain role:** Query planner + router + result synthesizer. Maintains a RoutingTable with entity→partition index and partition centroid embeddings for semantic routing fallback. Uses Reciprocal Rank Fusion for multi-partition result merging.

**Border nodes:** 8-15% of nodes have cross-partition edges. A Border Node Registry (BNR) in RAM (~9.6MB at 150K border nodes). Ultra-high-degree nodes (>500 cross-partition edges) get ghost copies in ALL partitions.

**Ghost copies:** Read-only replicas of cross-partition neighbors containing embedding + metadata snapshot. ~36MB ghost embedding cache per partition. Eventually consistent — invalidation broadcast on home-partition update.

**VRAM budget:** Hub 2.4GB + shared embedding 0.13GB + 8 hot-node caches 1.2GB + ghost caches 0.29GB + KV cache 1.5GB + overhead 0.5GB = ~6.0GB. 6GB headroom.

**Re-partitioning triggers:** Edge-cut ratio >15%, partition size imbalance >2x, query spillover >25%, bulk ingest >50K nodes. Hot-swap takes 30-120 seconds.

**Best for:** Load-balanced, topology-aware organization. Minimizes cross-partition traffic by construction.
**Worst for:** Re-partitioning is disruptive (30-120s). Partition semantics are opaque ("Partition 4" vs "Finance domain").

## Structure 3: Hierarchical Tree of Cores

**Concept:** Multi-level org chart. Hub brain at root, 5 mid-level "regional" AIs manage clusters, 20-30 leaf AIs own small subgraphs.

**Tree shape:** 3 levels, fan-out 4-6. Root: Qwen3-4B (3.0GB). Regional: Qwen3-1.7B (1.5GB, loaded one at a time). Leaf: Qwen3-0.6B (0.7GB, spun up transiently).

**Regions:** R1 Encyclopedia (Wikipedia, papers), R2 Operational (SOPs, scripts, code), R3 Knowledge (KB entries, notes), R4 Market (financial data), R5 Discovery (bookmarks, APIs).

**Routing patterns:** Top-down (70%), lateral within-region (15%), bottom-up escalation (10%), root bypass (5%).

**Rollup modes:** (A) Factual lookup — leaf returns structured record, passes upward. (B) Analytical — hard token caps at each level (leaf 512, regional 1024, root 2048). (C) Traversal — lateral dispatch within region, escalate to root for cross-domain.

**VRAM budget:** Hub 3.0GB + embedding 0.3GB + 1 active regional 1.5GB + 1 active leaf 0.7GB + KV caches 1.4GB + overhead 0.5GB = ~7.4GB. 4.6GB headroom.

**Scaling:** Heterogeneous depth — large domains grow to 4-level subtrees while small ones stay at 3. At 10M edges, only 1-2 domains need the 4th level.

**Best for:** Query-heavy, update-light graphs where query locality holds (most questions in one domain).
**Worst for:** Cross-domain queries traverse 3+ model loads = 600ms+ minimum latency. Deep BFS traversals are pathological.

## Structure 4: Task-Specialized Cores (Functional Division)

**Concept:** Sub-AIs divided by FUNCTION, not data. One does semantic search, one does link prediction, one does summarization. All cores access all data through a shared data layer.

**Core roster:** 7 functional cores — SemanticCore (bi-encoder, 0.35GB), TraversalCore (GNN/CPU, 0.5GB), CommunityCore (CPU-only), SummarizationCore (Qwen2.5-3B, 2.0GB), IngestCore (embedding, 0.35GB), ReasoningCore (Qwen2.5-7B, 4.5GB), TaxonomyCore (classifier, 0.5GB).

**Shared data layer:** SQLite WAL for graph store (concurrent readers, one writer), Hnswlib for vector index (concurrent-read-safe), flat filesystem for content blobs, coordination SQLite for task queue.

**Hub brain role:** Decomposes queries into pipeline DAGs. Example: "find communities in finance, summarize, predict links" → SemanticCore → CommunityCore → [SummarizationCore || TraversalCore] → Hub synthesis.

**Concurrency:** Hub 2.5GB always resident. SemanticCore + SummarizationCore + TraversalCore = 5.35GB concurrent — fits. ReasoningCore + SummarizationCore = 9GB — tight but fits.

**Best for:** Complex analytical pipelines chaining multiple operations. Independent model upgrades per function.
**Worst for:** No caching locality (each core re-fetches data from SQLite). Write contention on shared store. Pipeline step boundaries add I/O latency.

## Structure 5: Temporal-Layer Cores

**Concept:** Partition by TIME. Hot layer (7 days) in VRAM, warm layer (90 days) in RAM, cold archive on NVMe. A "trend" core monitors temporal patterns.

**Four layers:** L0 Ephemeral (0-4h, 512MB VRAM), L1 Hot (4h-7d, 2GB VRAM), L2 Warm (7-90d, 2-4GB RAM), L3 Cold (90d+, NVMe SSD).

**Promotion:** Access-triggered with hysteresis. Cold→Warm requires 2 accesses within 24h. Warm→Hot requires 3 distinct queries in 7 days or a write/modification. Single access puts node in quarantine buffer, not promoted directly.

**Trend core:** Monitors access velocity, promotion/demotion flux, subgraph activation patterns, seasonal cycles. Produces predictive promotion lists ("pre-warm these nodes based on seasonal patterns"). Runs on CPU with lightweight time-series model.

**Hub brain role:** Extracts temporal scope from queries. "What's new in finance?" → hot layer only, sub-10ms. "Historical overview of X" → all layers, 1-3s. Temporal reranking: hot nodes get 1.5x score boost by default.

**VRAM budget:** Hub 4.5GB + L0 0.5GB + L1 hot FAISS 2.0GB + adjacency cache 0.5GB + trend summaries 0.25GB + overhead 0.5GB = ~9.75GB. 2.25GB headroom.

**Best for:** Personal knowledge graphs with strong temporal access patterns. "What have I been working on?" queries are instant.
**Worst for:** Temporal locality ≠ semantic locality. Two related nodes in different time layers require expensive cross-layer joins. "Important but old" foundational docs fall to cold.

## Structure 6: Embedding-Space Cores (Semantic Clustering)

**Concept:** Cluster nodes by embedding vectors (nomic-embed-text-v1.5). Each sub-AI owns a region of embedding space. Semantically similar content groups naturally regardless of source type.

**Clustering:** FAISS IVF with 256 Voronoi cells. HDBSCAN for initial exploration, then IVF-PQ for production. Hierarchical splitting for cells >20K nodes; merging for cells <500 nodes. Result: ~180 active cores after rebalancing.

**New node assignment:** Embed → nearest centroid (single matrix multiply, microseconds) → assign. Boundary nodes (close to 2+ centroids) registered with both clusters.

**Hub brain role:** Embeds the query → cosine similarity against 256 centroids → dispatch to k nearest clusters (k=2 for narrow queries, k=10-15 for broad). Centroids always in VRAM (786KB). All NL generation done by hub; cores are retrieval pipelines.

**Drift management:** Online centroid updates as nodes arrive. Local re-clustering when a single cluster drifts >5% of mean inter-centroid distance. Global re-indexing monthly if 20%+ clusters flagged.

**VRAM budget:** Hub Qwen3-4B 8.0GB (4-bit) + centroids 0.75MB + embedding model 0.27GB + IVF buffers 0.5GB + query buffer 0.2GB = ~9.2GB. 2.8GB for active core operations.

**Best for:** Heterogeneous content that defies taxonomy. Schema-free ingestion. Cross-domain discovery ("decision making under uncertainty" pulls from psychology, finance, game theory, military strategy simultaneously).
**Worst for:** Cold start requires bulk embedding of all 1M nodes (~20-30 min). Embedding model lock-in — changing models requires full re-index. Clusters are opaque until auto-labeled.

## Structure 7: Agent-Swarm (Ant Colony)

**Concept:** No permanent data assignment. Pool of identical generalist workers. Hub assigns tasks dynamically. Workers "claim" subgraphs temporarily, process, release. Like ants — no ant owns territory.

**Worker pool:** 5-6 active workers running Qwen3-1.7B Q4 with shared mmap'd weights (1.2GB loaded once). Per-worker cost is KV cache only (~350MB at 4K context).

**Task flow:** Hub decomposes query into work units (DAG). Each WU specifies seed nodes + depth limit + operation type. Workers claim WUs via SQLite coordination table. Hub tracks dependencies, dispatches ready WUs to idle workers.

**Work stealing:** Idle workers grab queued-but-unclaimed WUs from other workers' backlogs. Optimistic locking via SQLite compare-and-swap. Random jitter (0-50ms) prevents racing.

**Caching:** Tier-1 disk cache (subgraph results keyed by seed+depth+graph_version, 10GB budget, 40-70% hit rate). Tier-2 soft affinity — hub prefers dispatching similar subgraph tasks to the same worker.

**VRAM budget:** Hub 3.5GB + shared worker weights 1.2GB + 5 KV caches 1.75GB + traversal buffers 0.5GB + overhead 0.8GB + hub synthesis cache 2.0GB + reserve 2.25GB = 12.0GB. Tight but workable.

**Best for:** Heterogeneous, unpredictable, cross-domain queries. Maximum parallelism for decomposable queries. No hot-spot workers. Elastic — 2 WUs use 2 workers, 8 WUs use 8.
**Worst for:** Context-switching overhead (20-200ms per task load). No deep specialization. Redundant computation from overlapping claims.

## Structure 8: Hybrid Adaptive

**Concept:** Start with domain cores, but the system restructures itself based on usage metrics. The hub brain is a meta-architect that observes query patterns and splits/merges/adds cores over time.

**Day-1 config:** 4 domain cores (Encyclopedic, Procedural, Research, Personal) + 1 functional core (Synthesis). Total ~9.3GB.

**Core types coexist:** Data cores (own a partition), functional cores (stateless workers), hybrid cores (temporary during migration).

**Self-restructuring triggers:** Load imbalance (>45% queries to one core for 30min), latency degradation (p95 >3x baseline for 10min), cross-core join frequency (>30% queries joining same two cores), dead core (<2% queries for 7 days), VRAM pressure (<1.5GB headroom for 5min), semantic drift (new content >0.4 cosine from core centroid).

**Evolution path:**
- 100K edges: 5 cores, observation mode (3 months baseline)
- 500K edges: First splits (Encyclopedic → Wikipedia + KB-Structured). New functional cores appear (Temporal Reasoner).
- 1M edges: 9-10 active cores, tiered embedding strategy, LRU graph locality caching
- 10M edges: Hibernation model — only 4-5 cores active in VRAM, others on NVMe. Hub does speculative loading.

**Migration protocol:** Dual-write with read-fallback. Shadow cores built in RAM, dual-write phase (10-30min), shadow promotion, drain old core. Zero downtime.

**State tracking:** Configuration manifest in SQLite with versioned routing rules, restructuring log, metrics ledger. Rollback to last 3 versions supported.

**Best for:** Long-lived systems where optimal structure is unknowable in advance. Graceful scaling across 100x growth. Observable decision audit trail.
**Worst for:** Most complex to implement. Restructuring causes 20-40% performance degradation for 15-45min. Hub brain is single point of failure for both routing AND restructuring decisions.

## Recommendation for This Use Case

For a personal 1M+ edge multi-domain knowledge graph on RTX 4070 Super:

1. **Best starting point:** Structure 8 (Hybrid Adaptive) with Structure 1 (Domain-Specialist) as day-1 configuration
2. **If implementation simplicity matters most:** Structure 4 (Task-Specialized) — no data partitioning, clean functional separation
3. **If query speed matters most:** Structure 5 (Temporal-Layer) for recency queries + Structure 6 (Embedding-Space) for discovery queries
4. **If the graph grows beyond 10M edges:** Structure 2 (Graph-Partition) provides the most mathematically principled scaling

The practical recommendation: **start with Structure 4 (Task-Specialized)** for its simplicity, then layer on Structure 5's temporal tiering for the hot/cold optimization, evolving toward Structure 8's self-restructuring as usage patterns become clear.
