# Coordination Improvement Patterns: Implementation-Ready Research

## Context
Detailed implementation research for the 6 highest-impact coordination improvements identified in KB-0031 and KB-0032. Each pattern includes production references, code patterns, and direct mapping to our system.

## Method
Analysis of production implementations (Palantir sqlite3worker, Peewee SqliteQueueDatabase, Tokio runtime, NGINX, HAProxy), academic papers (JIQ by Microsoft Research, Mitzenmacher power-of-two thesis, UC Berkeley adaptive batching), and framework documentation.

## Result

### 1. Write Coalescing Thread

**Production references**: Palantir's sqlite3worker, Peewee's SqliteQueueDatabase

**Pattern**: Single daemon thread owns the only SQLite write connection. All callers put `(token, query, values)` tuples onto a `queue.Queue`. Thread drains queue and commits in batches.

**Batch commit strategy**: Commit when queue drains empty OR max count reached.

**Result notification**: Peewee uses `threading.Event` per query — caller blocks on `event.wait(timeout)`, writer calls `event.set()` after execution. Zero polling.

**Impact on our system**: Replaces per-call `BEGIN IMMEDIATE` + `_retry_on_busy` in `coordinator_hub.py` and `work_stealing.py`. Eliminates SQLITE_BUSY entirely.

### 2. Join-the-Idle-Queue (JIQ)

**Source**: Microsoft Research (Lu et al.)

**Data structure**: Each dispatcher maintains an I-queue (idle queue) of agent identifiers.

**Flow**:
1. Agent finishes work → registers with ONE random dispatcher's I-queue
2. New task arrives → pop from I-queue for instant assignment
3. If I-queue empty → fallback to random or power-of-two selection
4. Agent assigned via fallback sends "delete request" to its registered dispatcher

**JIQ-Powd hybrid**: When I-queue empty, probe d agents and assign to least loaded.

**Impact on our system**: Replaces DB polling in `help_protocol.py`. Idle teams register proactively, new work dispatched instantly.

### 3. Power-of-Two-Choices for Work Stealing

**Source**: Mitzenmacher thesis, NGINX, HAProxy (17 lines of code)

**Pattern**: Sample 2 random peers, steal from the fuller one.
- Random victim: max queue O(log n)
- Two-choice: max queue O(log log n) — exponential improvement

**Impact on our system**: `WorkStealing.steal_work()` currently grabs globally. Two-choice would be victim selection in multi-queue-per-agent design.

### 4. Event-Driven State Changes

**Three approaches**:
- **File system events (watchdog/inotify)**: Near-instant notification when JSONL file appended to. Zero polling on Linux.
- **threading.Condition**: In-process push with `notify_all()` on publish, `wait(timeout)` on consume.
- **Per-consumer queues**: Most robust — publisher pushes to each subscriber's `queue.Queue` directly.

**Impact on our system**: `bus_cli.py` writes JSONL with atomic append, consumers poll. Watchdog/inotify gives push semantics with no code change to producers.

### 5. Adaptive Batch Sizing

**Formula**: `batch_size = max(1, steal_latency_ms / avg_task_duration_ms * 2)`

**MAPE loop**: Monitor (track latencies) → Analyze (compute ratio) → Plan (new batch size) → Execute (apply next steal).

**Window**: Rolling window of last 20 observations for both steal latency and task duration.

**Bounds**: `min_batch=1, max_batch=32` prevents pathological sizes.

**Impact on our system**: Replaces fixed single-item steal with auto-tuned batch size. If stealing takes 10ms and tasks take 1ms, batch of 20 amortizes overhead.

### 6. LIFO Slot (Tokio Pattern)

**Pattern**: Each worker has single-slot in-process variable holding most recently produced task. Bypasses queue/DB entirely for producer-consumer locality.

**Key design points**:
- LIFO slot invisible to stealers — no synchronization needed
- Cache locality: recently produced task shares hot cache lines
- **Starvation prevention**: Disable after 3 consecutive LIFO pops to let queued tasks run
- Configurable: can be disabled for strict FIFO workloads

**Impact on our system**: `PipelineManager` stage transitions — when team completes a stage and produces next-stage work, same team picks it up instantly without DB round-trip.

## Current System Mapping

| Pattern | Current Approach | Replacement | Est. Impact |
|---------|-----------------|-------------|-------------|
| Write coalescing | Per-call `BEGIN IMMEDIATE` + retry | Single writer thread + batch commit | Eliminates SQLITE_BUSY |
| JIQ | DB polling in `help_protocol.py` | Idle registry, instant dispatch | Zero-latency assignment |
| Power-of-two | Global queue steal | Sample 2, steal from fuller | O(log log n) vs O(log n) |
| Event-driven | JSONL poll | watchdog inotify or in-process queues | Push semantics |
| Adaptive batch | Fixed single-item | Auto-tuned based on latency ratio | Amortizes steal overhead |
| LIFO slot | All through DB | In-process fast path | Bypasses DB for locality |

## Lessons Learned

1. **Write coalescing is the #1 priority** — production systems (Palantir, Peewee) validate this pattern extensively
2. **JIQ is simpler than auction-based allocation** and achieves near-optimal results
3. **Power-of-two needs only 17 lines** (HAProxy example) for exponential improvement
4. **inotify/watchdog integration** gives push semantics with no change to JSONL producers
5. **LIFO starvation is real** — Tokio's 3-consecutive-use limit is essential (GitHub issue #4323)
6. **Adaptive batching needs bounds** — unbounded batch size causes latency spikes

## Recommendations (Implementation Order)

1. **Write coalescing thread** — add to `coordinator_hub.py`, wraps SQLite connection
2. **LIFO slot** — add to `work_stealing.py` `TeamLeadDistributor`
3. **Adaptive batch sizing** — enhance `steal_batch(n)` with auto-tuning
4. **JIQ pattern** — add idle registry to `help_protocol.py`
5. **Event-driven bus** — add watchdog to `bus_cli.py` consumers
6. **Power-of-two victim selection** — add to multi-queue stealing scenarios
