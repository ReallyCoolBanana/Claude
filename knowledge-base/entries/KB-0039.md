# WebAssembly for AI Agent Code Sandboxing

## Context
AI agent systems need secure, lightweight sandboxing for executing untrusted code. We evaluated WebAssembly (WASM) as a sandboxing mechanism for multi-agent compute workloads, comparing it against alternatives like Firecracker microVMs.

## Method
Surveyed WASM runtimes (Wasmtime, WAMR, Wasmer), WASI Preview 2 capabilities, the Component Model, and compared against industry approaches for sandboxing AI agent code execution. Benchmarked startup times, runtime overhead, and memory footprint across language targets.

## Result

### WASM Core Strengths
- **Memory isolation**: Each WASM instance gets its own linear memory with bounds checking — no access to host memory.
- **Capability-based security**: WASI Preview 2 enables selective permission granting (filesystem, network, environment variables, etc.). Agents get only the capabilities explicitly provided.
- **Microsecond startup**: JIT compilation delivers <15ms startup times, orders of magnitude faster than container or VM alternatives.

### Runtime Selection
- **Wasmtime** is the production choice: Cranelift JIT, full WASI Preview 2 support, component model support, backed by the Bytecode Alliance.
- **WAMR (WebAssembly Micro Runtime)** is the choice for embedded/resource-constrained environments: interpreter + AOT modes, minimal footprint.

### Language Compatibility
- **Rust** compiles excellently to WASM: near-native performance, small binaries, no runtime overhead.
- **Python** has severe penalties: double interpreter overhead (CPython compiled to WASM running on WASM runtime). Practical Python WASM execution incurs 5-10x slowdown vs native.

### Component Model
The Component Model enables per-agent module isolation with typed WIT (WebAssembly Interface Type) interfaces. Each agent can be a separate component with:
- Explicit import/export boundaries
- Type-safe inter-component communication
- Independent memory spaces

### Industry Reality
- For Python agent sandboxing, the industry uses **Firecracker microVMs**, not WASM. AWS Lambda, Fly.io, and similar platforms all chose Firecracker for its 125ms boot time and full Linux compatibility.
- WASM sandboxing is used for Rust/C/C++ compute plugins, not general-purpose agent execution.

### Performance Characteristics
- **JIT startup**: <15ms with Wasmtime Cranelift
- **Runtime speed**: 85-90% of native speed for compute workloads
- **Memory overhead**: 15-20MB per instance (runtime + module)
- **Density**: Can run hundreds of instances per machine vs tens of VMs

## Lessons Learned
- WASM is not a universal sandbox — it excels for compiled languages but is impractical for interpreted languages like Python.
- WASI Preview 2's capability model is architecturally elegant but the ecosystem is still maturing (many libraries lack WASI support).
- The Component Model is the key differentiator for multi-agent isolation — it provides typed boundaries between agents without serialization overhead.

## Recommendations
- **Hybrid approach recommended**: Use WASM for Rust/C compute-intensive agent modules, Firecracker for Python/shell execution environments.
- For our coordination system, WASM could sandbox individual compute tasks dispatched via work-stealing, while the Python coordination layer runs natively or in Firecracker.
- Monitor WASI Preview 2 ecosystem maturity — once Python WASI support improves, revisit the hybrid decision.
- Evaluate Wasmtime's fuel metering for CPU time limits on untrusted agent code.

# MCP Server for Knowledge Base Search

## Context
Agents needed 3+ tool calls to discover relevant KB entries — reading index.json, parsing YAML frontmatter, and resolving cross-references. KB-0034 identified MCP as the universal integration layer with under 50 lines needed via FastMCP.

## Method
Built a single-file FastMCP server (`storage/scripts/mcp_kb_server.py`, 96 lines) wrapping the existing SQLite FTS5 database. Configured via `.mcp.json` at repo root for project-wide stdio transport access.

## Result
6 working tools:
1. `kb_search` — FTS5 full-text search with BM25 ranking
2. `kb_get` — Retrieve specific entry by ID with tags and relationships
3. `kb_list` — List entries by resource type
4. `kb_tags` — Tag frequency cloud
5. `kb_related` — Recursive builds_on chain + shared tag discovery
6. `kb_semantic_search` — Vector similarity via LanceDB (integrated post-build)

All tools tested against live database. Server configured in `.mcp.json` for automatic availability to all Claude Code sessions in this repo.

## Lessons Learned
1. The official `mcp` PyPI package includes FastMCP — no need for the standalone `fastmcp` package
2. MCP servers go in `.mcp.json` (project scope), NOT `.claude/settings.json`
3. Tools are model-controlled (Claude decides when to search); resources are app-controlled (require @ mentions)
4. FTS5 match errors need try/except with phrase-quoted fallback

## Recommendations
1. Use `/mcp` command in Claude Code to verify server connection
2. Future: expose individual KB entries as MCP resources for @ mention access
3. Future: add coordination tools (v2) only if domain output justifies it
