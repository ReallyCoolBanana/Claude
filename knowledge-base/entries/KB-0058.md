# Local GPU AI Hub Controller — Consolidated Research Synthesis (20-Agent Deep Dive)

## Context
Comprehensive research synthesis from 20 parallel agents investigating how to build a local AI hub controller on an RTX 4070 Super (12GB VRAM) that orchestrates specialized sub-AIs to accelerate the pointer network (310 nodes, 4,809 edges, 7 domains) and serve Claude sessions via MCP. This entry consolidates findings from 7 deep-dive agents, 4 network structure agents, 1 CPU model agent, and 8 web research agents.

---

## 1. Hub Brain Model Selection

### Winner: Phi-4 Mini 3.8B (Q5_K_M)
| Metric | Value |
|--------|-------|
| VRAM | ~3.5 GB |
| Speed | ~90+ tok/s on 4070S |
| ARC-C | 83.7% |
| GSM8K | 88.6% |
| Context | 128K |
| License | MIT |
| Tool calling | Native `<\|tool\|>` format |

**Why Phi-4 Mini wins:** Best reasoning-per-GB ratio. Native function calling is critical for an orchestrator emitting structured task dispatches. At 3.5 GB, leaves **8.5 GB free** for sub-AIs — no other 7B+ model provides this headroom.

**Fallback:** Llama 3.1 8B Instruct (Q4_K_M, ~5.5 GB, 89% IFEval — strongest instruction following).

**Emerging contenders:**
- Qwen3-8B: Dual-mode (thinking + non-thinking), native tool calling, outperforms Qwen2.5-14B. ~6 GB VRAM.
- Qwen3.5-9B: MMLU-Pro 82.5 — beats models 3x its size. ~6.5 GB.
- Neither fits comfortably alongside sub-AIs; Phi-4 Mini remains optimal for the always-resident hub role.

## 2. Sub-AI Specializations and VRAM Budget

### Always-On (4 GB total)
| Sub-AI | Model | VRAM | Role |
|--------|-------|------|------|
| Hub Brain | Phi-4 Mini 3.8B Q5_K_M | 3.5 GB | Task decomposition, routing, aggregation |
| Embedder | nomic-embed-text-v1.5 | 0.5 GB | Text → 768-dim vectors at ~5000 articles/min |

### On-Demand (swap into remaining 8 GB)
| Sub-AI | Model | VRAM | Role |
|--------|-------|------|------|
| Search | FAISS GPU (IVF-PQ) + reranker | 1-3 GB | Semantic nearest neighbor lookup |
| Graph AI | PyKEEN / cuGraph | 1-2 GB | Link prediction, community detection |
| Summarizer | Qwen3-4B Q4_K_M or Phi-4 Mini (reuse hub) | 3-5 GB | Article summarization |
| Reranker | cross-encoder/ms-marco-MiniLM-L-6-v2 | 0.4 GB | Precision filter after search |
| Classifier | distilbert fine-tuned | 0.3 GB | Fast intent routing (< 5ms) |

### Additional Roles Identified by Research
- **Classifier/Router**: Fine-tuned DistilBERT (~300MB) as pre-filter before hub. Handles simple routing in <5ms, freeing the hub for complex decomposition only.
- **Reranker/Quality Gate**: Cross-encoder that turns 80% FAISS precision into 95%+. Triggered after every search.
- **Image Embedder**: CLIP ViT-L/14 (~2 GB) for multimodal pointer network edges.

## 3. VRAM Management Strategy

### Recommended: llama.cpp Router Mode
The newest llama.cpp feature (December 2025) provides:
- **Multi-process isolation**: Each model runs in its own process; crashes don't cascade
- **LRU eviction**: Least-recently-used model auto-unloaded when hitting limits
- **On-demand loading**: Models loaded only when requested
- **Per-model presets**: `presets.ini` for context size, GPU layers, etc.
- **Web UI**: Built-in model dropdown for manual control

### VRAM Allocation Plan (12 GB)
```
┌─────────────────────────────────────────────────┐
│  ALWAYS RESIDENT (4.0 GB)                        │
│  ├── Phi-4 Mini Hub Brain: 3.5 GB               │
│  └── Embedder (nomic-embed): 0.5 GB             │
│                                                   │
│  SWAP ZONE (7.5 GB available)                    │
│  ├── Search (FAISS GPU): 1-3 GB                  │
│  ├── Summarizer: 3-5 GB                          │
│  ├── Graph AI: 1-2 GB                            │
│  └── Reranker: 0.4 GB                            │
│                                                   │
│  RESERVED (0.5 GB)                               │
│  └── CUDA overhead + scratch memory              │
└─────────────────────────────────────────────────┘
```

### Model Lifecycle
1. Hub receives request → classifies intent
2. VRAM Manager checks what's loaded (`nvidia-smi` or `pynvml`)
3. If needed model not loaded: find LRU model → unload → load needed model
4. Execute task → return result
5. Model stays loaded for `keep_alive` period (default 5 min), then eligible for eviction

### Key Gotchas (from research)
- Ollama v0.7.0 has sporadic VRAM leak bugs — VRAM not freed after unload
- vLLM's `LLM` object deletion doesn't fully release GPU memory — use Sleep Mode instead
- llama.cpp `--mmap` enables faster reloads by memory-mapping GGUF files
- KV cache quantization (`q8_0`) reduces VRAM by ~50% with minimal quality loss

## 4. Vector Search: FAISS GPU for Wikipedia Scale

### Recommended Configuration
| Parameter | Value |
|-----------|-------|
| Embedding model | nomic-embed-text-v1.5 (768-dim) |
| Index type | `OPQ32,IVF4096,PQ32` on GPU |
| VRAM usage | 3-5 GB for 6-7M vectors |
| nprobe | 32-64 (tune for recall target) |
| Recall | 90-95% at nprobe=32 |
| Single query latency | 1-5 ms |
| Batch throughput | 10,000-50,000 QPS |
| Build time | 5-15 minutes (with cuVS) |

### Why FAISS over Qdrant/Milvus
- **Raw speed**: Sub-ms to few ms vs 30-40ms (Qdrant at 50M vectors)
- **VRAM efficiency**: 3-5 GB (IVF-PQ) vs 8-20 GB (Qdrant/Milvus)
- **GPU native**: Mature GPU support via cuVS

### When to use Qdrant instead
- Need metadata filtering (FAISS has none)
- Need zero operational overhead (FAISS requires DIY persistence/concurrency)
- Need full CRUD without manual index management

### Incremental Updates Pattern
1. Train IVF-PQ on initial corpus (~6M vectors)
2. Daily/weekly: `add_with_ids()` for new articles, `remove_ids()` for deleted
3. Monthly: evaluate recall drift; retrain if needed (minutes on GPU)
4. Shadow index for zero-downtime rebuilds

## 5. Serving Architecture

### Recommended Stack
```
Claude Code ──stdio──► MCP Server (Python) ──HTTP──► FastAPI Hub (:8000) ──► GPU Sub-AIs
```

**MCP Server** (stdio transport, Python via FastMCP):
- Spawned by Claude Code as child process
- Proxies requests to FastAPI hub via HTTP
- 7 tools exposed:

| Tool | Sub-AI | Purpose |
|------|--------|---------|
| `gpu_embed` | Embedder | Generate embeddings for text |
| `gpu_embed_batch` | Embedder | Batch-embed documents |
| `gpu_summarize` | Summarizer | Summarize articles |
| `gpu_search` | Search | Semantic nearest-neighbor |
| `gpu_predict_links` | Graph AI | Predict missing edges |
| `gpu_hub_status` | Hub | VRAM, models, queue depth |
| `gpu_cluster_detect` | Graph AI | Community detection |

**FastAPI Hub** (single process, single worker per GPU):
- FAISS GPU index loaded at startup
- Async endpoints with `run_in_executor` for FAISS calls
- Request batching (10ms window) for throughput
- Periodic index persistence to disk

### MCP Configuration (add to `.mcp.json`)
```json
{
  "mcpServers": {
    "gpu-hub": {
      "command": "python",
      "args": ["storage/mcp-server/gpu_hub_server.py"],
      "env": {
        "GPU_HUB_URL": "http://localhost:8000"
      }
    }
  }
}
```

## 6. Task Queue and Scheduling

### Recommended: SQLite-Backed Queue (extend existing `work_stealing.py`)
The existing coordination infrastructure provides ~70-80% of what's needed:

| Existing Component | Reuse For |
|-------------------|-----------|
| `coordinator_hub.py` (AgentReporter + agent_status table) | GPU sub-AI status tracking |
| `work_stealing.py` (work_queue table + atomic steal) | GPU task queue with priority |
| `direct_channels.py` (named peer channels) | Sub-AI-to-sub-AI communication |
| `help_protocol.py` (idle detection) | VRAM-aware idle model detection |
| `bus_cli.py` (JSONL message bus) | GPU hub event logging |

**Extensions needed:**
- `gpu_agent_status` supplementary table: `vram_used_mb`, `vram_allocated_mb`, `model_loaded`, `gpu_utilization_pct`
- Priority levels: `critical` (Claude waiting) > `batch` (background embedding) > `maintenance` (retrain)
- Deadline-aware scheduling for interactive vs batch requests

### Two-Layer Queue Design
1. **Hot layer**: `asyncio.PriorityQueue` in FastAPI process (zero latency, no persistence)
2. **Persistent layer**: SQLite WAL queue (survives restarts, queryable, reuses existing patterns)

## 7. Pointer Network Integration

### New Edge Type: `semantic_similarity`
```json
{
  "to": "KB-0032",
  "weight": 5,
  "reasons": ["semantic_similarity:0.87"],
  "strength": "supporting"
}
```

**Weight mapping**: cosine_similarity × 10 → weight 1-9
**Strength mapping**: ≥7 → primary, ≥5 → supporting, ≥3 → related, <3 → tangential

### Link Prediction Pipeline
1. Convert pointer-network.json to PyKEEN triples: `(source_id, edge_type, target_id)`
2. Train RotatE (best for mixed relation types) — trivial VRAM for 310 nodes
3. Predict top-k missing edges with confidence scores
4. Human-in-the-loop: Claude reviews before adding
5. Export via the Pointer Network Sync service

### Scale Migration Path
| Node Count | Storage | Query Engine |
|------------|---------|-------------|
| <1,000 | JSON | PNQ (current) |
| 1K-50K | SQLite WAL | SQL + BFS |
| 50K+ | Neo4j | Cypher queries |

## 8. Network Architecture: Hybrid Blackboard + Event-Driven

The pure hub-spoke from KB-0056 has limitations. Research recommends a **hybrid** approach:

### Blackboard Architecture
```
┌──────────────────────────────────────────────────────┐
│                BLACKBOARD (SQLite WAL)                │
│  ┌────────────┬────────────┬────────────┬──────────┐ │
│  │ Task Queue │ VRAM State │ Results    │ Events   │ │
│  └─────┬──────┴─────┬──────┴─────┬──────┴────┬─────┘ │
│        │            │            │           │        │
│  ┌─────▼───┐  ┌─────▼───┐  ┌────▼────┐  ┌──▼─────┐ │
│  │Embedder │  │ Search  │  │ Graph   │  │Summary │ │
│  │ (0.5GB) │  │ (1-3GB) │  │ (1-2GB) │  │(3-5GB) │ │
│  └─────────┘  └─────────┘  └─────────┘  └────────┘ │
│                                                       │
│  Hub Brain reads blackboard, makes decisions,         │
│  writes back — but sub-AIs can also read/write        │
│  directly for simple pipelines (embed → search)       │
└──────────────────────────────────────────────────────┘
```

**Why hybrid wins:**
- Sub-AIs can chain directly (embed → search) without hub round-trip
- Blackboard provides shared state visible to all components
- Hub only intervenes for complex multi-step tasks
- Saves 4-6 GB VRAM if hub can be unloaded during simple pipelines

## 9. CPU Offloading Opportunities

### Models That Run Well on CPU
| Model | CPU Speed | Use Case |
|-------|-----------|----------|
| Qwen2-0.5B | 50-80 tok/s | Simple routing/classification |
| Model2Vec | 20K+ sentences/sec | Bulk static embedding |
| DistilBERT classifier | <5ms inference | Intent detection pre-filter |
| cross-encoder (small) | ~10ms/pair | Reranking (small batches) |

### CPU/GPU Split Strategy
- **CPU always-on**: Classifier, simple routing, health checks, queue management
- **GPU on-demand**: Embedding generation, search, summarization, GNN training
- **Benefit**: Frees GPU VRAM entirely for compute-heavy tasks

## 10. Security and Reliability

### Sandboxing: Bubblewrap (bwrap)
- Each sub-AI worker launched in bwrap sandbox
- Read-only bind mounts for model weights and libraries
- `--unshare-net` for sub-AIs that don't need network
- GPU passthrough via `/dev/nvidia*` bind mount (Ada Lovelace has per-client GPU address spaces)

### Systemd Hardening
- `ProtectSystem=strict`, `ProtectHome=read-only`
- `MemoryMax=` per service to prevent OOM cascading
- `Restart=on-failure` with `RestartSec=5s`

### Graceful GPU Degradation
- Gaming detection: if VRAM pressure > threshold, automatically unload non-critical models
- Fall back to CPU inference for routing/classification
- Resume GPU models when VRAM becomes available

## 12. Real-World Lessons from the Community

- **Two GPUs ≠ 2x performance**: Expect 1.4-1.6x on consumer hardware without NVLink
- **Pop!_OS > Ubuntu Server** for NVIDIA driver stability (no kernel update breakage)
- **Ollama** is the easiest entry point but hit VRAM bugs at scale; llama.cpp gives finer control
- **LocalAI** is the most feature-complete OpenAI-compatible gateway (MCP support, P2P inference, multi-backend)
- **vLLM** is production-grade but overkill for single-GPU hobby use
- **llama-swap** (third-party) is purpose-built for model hot-swapping behind a proxy

## Recommendations

1. **Start with Phi-4 Mini + nomic-embed-text-v1.5** — the 4 GB always-on foundation
2. **Use llama.cpp router mode** for VRAM management — it's purpose-built for this
3. **Extend existing coordination infra** (70-80% reusable) rather than building from scratch
4. **Deploy MCP server as stdio proxy** to FastAPI hub — matches existing `.mcp.json` pattern
5. **SQLite WAL for task queue** — proven pattern already in the codebase
6. **FAISS GPU with IVF-PQ** for Wikipedia-scale search — nothing else matches the speed on single GPU
7. **CPU offload classification/routing** to free GPU VRAM for heavy tasks
8. **Hybrid blackboard architecture** over pure hub-spoke — saves VRAM, enables direct sub-AI chaining
9. **Used RTX 3090 ($700)** is the best Tier 1 upgrade when ready to scale
10. **Do NOT over-engineer**: Start with Phase 1-3, validate the concept, then expand
