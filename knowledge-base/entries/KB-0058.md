# Nemo-Maxxing Memory Architecture v3: Comprehensive Analysis & Implementation Plan

## Context

Analysis of a disk-first, unified 3D memory system designed for a single NVIDIA DGX Spark (128GB unified memory, 4TB NVMe, Blackwell GB10 GPU). Core thesis: intelligence lives in the memory system, not model size. A small controller model orchestrates retrieval; any external model consumes memory via MCP API.

This document synthesizes findings from 6 parallel research efforts covering hardware feasibility, Neo4j graph memory, LanceDB/cuVS vector search, the Nemotron model ecosystem, MCP API design, and the nightly analyzer subsystem.

## Architecture Overview (v3 — Controller-Centric API Design)

### Components
1. **Controller Model** (~2-3GB): Frozen backbone + LoRA heads for task classification, strategy selection, retrieval orchestration, score ingestion. Never generates final answers.
2. **Neo4j Graph** (20-28GB in RAM): Four typed edge types (structural, temporal, causal, entity) + path pointers to LanceDB content.
3. **LanceDB on NVMe** (disk-first, memory-mapped): Vectors + content. cuVS (CAGRA + DiskANN) for GPU-accelerated search via NeMo Retriever.
4. **Embedding Model** (~1-4GB): Always-loaded for intent-aware embedding.
5. **Nemotron Reranker** (~1-2GB): Fuses retrieval signals into unified ranking.
6. **MCP API Layer**: Model-agnostic endpoints (/retrieve, /score, /ingest, /query_meta, /status).
7. **Nightly Analyzer** (loaded off-hours): Large model for edge weight updates, causal inference, path optimization, condensation, emergence detection.

### Two-Phase Retrieval
- **Phase 1**: Navigate Neo4j typed edges in RAM (no NVMe I/O) — 1-20ms
- **Phase 2**: Pull LanceDB content only for winning candidates — 3-25ms warm, 25-120ms cold
- **Rerank**: Nemotron reranker fuses signals — 5-15ms
- **Total**: 25-65ms warm, 40-120ms cold

## Critical Findings & Required Architecture Changes

### 1. Memory Budget Crisis (HIGH RISK)

**Problem**: Nemotron 3 Super 120B-A12B in native NVFP4 actually needs 77-87GB (not 64-72GB). Mixed-precision layers, KV cache, and CUDA runtime add 15-25% overhead.

**Impact**: Nighttime headroom drops to ~16GB. MTP/speculative decoding causes OOM.

**Solutions** (pick one):
- **Option A**: Use GGUF Q4_K_M variant (~64GB) — minor quality trade-off, fits the original budget
- **Option B**: Use Nemotron-3-Nano-30B-A3B-NVFP4 (~20GB, ~70 tok/s vs ~14 tok/s) — dramatically more practical unless 120B reasoning quality is specifically required
- **Option C**: Accept 77-87GB footprint, reduce Neo4j page cache to 8-12GB at night, accept degraded graph performance during analysis

**Recommendation**: Option B for most tasks, Option A for causal inference passes that need stronger reasoning.

### 2. Thermal Constraints (HIGH RISK)

**Problem**: DGX Spark throttles at ~100W in the 1.13L chassis. Reports of spontaneous reboots under sustained load.

**Mitigation**:
- Use Acer OEM variant (10-14°C cooler)
- External cooling solution
- Burst scheduling: 45 min inference / 15 min cool-down
- Monitor temps programmatically, graceful shutdown at threshold

### 3. Embedding Model Does Not Exist (MEDIUM RISK)

**Problem**: "llama-embed-nemotron-reasoning-3b" is not a publicly available model. Referenced in NVIDIA research (BRIGHT benchmark) but no download.

**Alternatives**:
- **llama-nemotron-embed-1b-v2** (~1B, commercial, Matryoshka embeddings, 8192 context) — compact, fits always-loaded role
- **omni-embed-nemotron-3b** (~3B, multimodal text/image/audio/video) — closest to the "3B" spec
- **llama-embed-nemotron-8b** (~7.5B, #1 on multilingual MTEB) — best quality but larger

**Recommendation**: omni-embed-nemotron-3b for multimodal capability, or llama-nemotron-embed-1b-v2 for minimal footprint.

### 4. No Direct LanceDB + cuVS Integration (MEDIUM RISK)

**Problem**: cuVS (CAGRA/DiskANN) does not integrate directly with LanceDB. LanceDB uses PyTorch for GPU indexing.

**Solution**: Deploy through **NeMo Retriever**, which uses LanceDB as default vector store with cuVS acceleration. This adds an infrastructure layer but is the supported path.

### 5. Reranker Cannot Natively Fuse 5 Signals (LOW RISK)

**Problem**: llama-nemotron-rerank-1b-v2 is a standard cross-encoder (query, document) → score. It doesn't natively fuse structural/semantic/temporal/causal/entity signals.

**Solutions**:
- **Phase 1**: Reciprocal Rank Fusion (RRF) at score level — simple, no model changes
- **Phase 2**: Prompt-based fusion — format all 5 signal scores as structured text in the reranker's 8192 context
- **Phase 3**: Custom fine-tune the reranker on multi-signal inputs

### 6. Neo4j vs Memgraph (RECOMMENDATION)

Neo4j works but Memgraph offers 8-25x faster traversals (pure in-memory C++, Bolt/Cypher compatible). Neo4j has the better ecosystem (GDS, agent-memory library, LangChain).

**Recommendation**: Prototype with Neo4j (ecosystem), benchmark with Memgraph, switch if latency is critical. They're Bolt-compatible — migration is straightforward.

## MCP API Design

### Overview
MCP (Model Context Protocol) is Anthropic's open protocol for connecting AI models to external tools and data sources. It provides a standardized JSON-RPC 2.0 transport layer that any model can use, making it ideal as the model-agnostic API for this memory system.

### Endpoint Definitions

#### /retrieve
```json
{
  "name": "memory_retrieve",
  "description": "Retrieve relevant memories for a query using two-phase graph+vector search",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "description": "Natural language query"},
      "memory_types": {
        "type": "array",
        "items": {"enum": ["temporary", "operational", "facts", "episodic", "meta"]},
        "description": "Filter by memory type (default: all)"
      },
      "max_results": {"type": "integer", "default": 10},
      "min_relevance": {"type": "number", "default": 0.5, "minimum": 0, "maximum": 1},
      "edge_types": {
        "type": "array",
        "items": {"enum": ["structural", "temporal", "causal", "entity"]},
        "description": "Edge types to traverse in Phase 1 (default: all)"
      },
      "max_hops": {"type": "integer", "default": 3, "minimum": 1, "maximum": 5}
    },
    "required": ["query"]
  }
}
```

### Cross-Model Scoring Consensus

The `/score` endpoint enables the architecture's key innovation — multiple models evaluating the same retrievals:

1. **During retrieval**: Each model that calls `/retrieve` gets a `retrieval_id`
2. **After use**: The model calls `/score` with its assessment of each result's relevance/accuracy/usefulness
3. **Aggregation**: The controller accumulates scores by `model_id`. Strategies:
   - Weighted mean (weight by model's historical accuracy)
   - Bayesian aggregation (treat each model as an independent observer)
   - Outlier detection (flag when one model strongly disagrees)
4. **Nightly integration**: Accumulated scores feed the nightly analyzer for edge weight updates

### MCP Server Implementation
- **Runtime**: Python (FastMCP library) — aligns with Neo4j/LanceDB Python clients
- **Concurrency**: asyncio for non-blocking I/O to both Neo4j and LanceDB
- **Transport**: stdio for local models, HTTP/SSE for remote models (Claude, GPT)
- **Authentication**: API key per model for scoring attribution

## Nightly Analyzer Implementation Plan

### Schedule (8-hour window, 1 AM - 9 AM)

| Phase | Time | Task | Model |
|-------|------|------|-------|
| Load | 0:00-0:30 | Pre-checks, load analyzer model | — |
| Inference | 0:30-2:00 | Edge weight decay + LLM analysis | 120B or 30B |
| Inference | 2:00-3:00 | Causal inference | 120B or 30B |
| Inference | 3:00-3:45 | Path pointer optimization | 120B or 30B |
| Inference | 3:45-4:45 | Condensation | 120B or 30B |
| Inference | 4:45-5:30 | Emergence detection | 120B or 30B |
| Transition | 5:30-6:00 | Unload analyzer, free RAM | — |
| Training | 6:00-7:30 | LoRA fine-tune controller (Unsloth QLoRA) | Controller |
| Validation | 7:30-8:00 | Consistency checks, LoRA eval, metrics | — |

### Processing Capacity (per night, 30B-A3B at ~70 tok/s)

| Task | Analysis Units | Coverage |
|------|---------------|----------|
| Edge weight analysis | ~2,000 | ~80,000 edges |
| Causal inference | ~800 | ~800 causal chains |
| Path optimization | ~600 | ~3,000 paths |
| Condensation | ~800 | ~800 node clusters |
| Emergence detection | ~600 | ~600 neighborhoods |

With the 30B model's 5x higher throughput, nightly coverage is dramatically better than the 120B.

### Consistency Guarantees
- Neo4j ACID transactions for atomic batch application
- Pre-analysis snapshot for full rollback capability
- Pre-commit invariant checking (no orphans, weights in range, no broken path pointers)
- Write-ahead logging for crash recovery
- Neo4j MVCC allows controller reads during analyzer writes

## Implementation Roadmap

### Phase 1: Foundation (Weeks 1-3)
- [ ] Set up DGX Spark with external cooling solution
- [ ] Install Neo4j, configure JVM heap and page cache
- [ ] Deploy LanceDB on NVMe, benchmark mmap performance
- [ ] Load Nemotron Nano 4B Q4_K_M as controller backbone
- [ ] Load embedding model (llama-nemotron-embed-1b-v2)
- [ ] Basic MCP server with /retrieve and /ingest endpoints

### Phase 2: Graph + Vector Integration (Weeks 4-6)
- [ ] Define Neo4j schema: 5 memory types as labeled nodes, 4 typed edges
- [ ] Implement path pointer storage on edges (LanceDB vector IDs)
- [ ] Build two-phase retrieval pipeline (graph traverse → vector fetch)
- [ ] Deploy reranker with RRF for initial signal fusion
- [ ] Implement /score endpoint and scoring accumulator
- [ ] Integration test: end-to-end retrieve → score cycle

### Phase 3: Nightly Analyzer (Weeks 7-9)
- [ ] Benchmark Nemotron 30B-A3B on DGX Spark (memory, throughput, thermals)
- [ ] Build nightly orchestrator with systemd timer
- [ ] Implement edge weight decay (mechanical, no LLM)
- [ ] Implement LLM-driven edge weight analysis
- [ ] Implement condensation pipeline
- [ ] Implement emergence detection
- [ ] Add consistency manager with snapshot/rollback

### Phase 4: LoRA Training + Cross-Model Consensus (Weeks 10-12)

### Phase 5: Optimization + Hardening (Weeks 13-16)
