# JSONL Message Bus: Technical Reference

## Executive Summary

This document provides a comprehensive technical reference for using JSONL (JSON Lines) files as a message bus for live inter-agent communication. It covers POSIX atomic write guarantees, file watching patterns, schema design, concurrency edge cases, performance characteristics, and practical agent usage patterns. The approach is well-suited for AI agent teams running as separate processes in git worktrees that need lightweight, dependency-free real-time communication via append-only shared files.

## 1. POSIX Atomic Write Guarantees

### 1.1 What POSIX Guarantees

POSIX provides two distinct atomicity guarantees that are frequently conflated:

**For pipes and FIFOs:** Writes of `PIPE_BUF` bytes or fewer are guaranteed atomic and non-interleaving. Writes larger than `PIPE_BUF` may have data interleaved with other writers on arbitrary boundaries.

**For regular files with `O_APPEND`:** The file offset is set to the end of the file prior to each write, and the adjustment of the file offset and the write operation are performed as an atomic step. However, POSIX does **not** guarantee that the write data itself will not be interleaved with data from other concurrent writers.

This is a critical distinction: `O_APPEND` guarantees you will not overwrite another writer's data (no seek/write race), but it does **not** guarantee your bytes will be contiguous in the file.

### 1.2 PIPE_BUF Size Limits

| Platform | PIPE_BUF |
|----------|----------|
| POSIX minimum | 512 bytes |
| Linux | 4,096 bytes |
| macOS | 512 bytes |
| FreeBSD | 512 bytes |
| Solaris | 5,120 bytes |

On Linux, `PIPE_BUF` is defined in `<limits.h>` as 4096 bytes.

### 1.3 Practical Behavior on Local Linux Filesystems

Despite the strict POSIX wording, empirical testing on Linux shows stronger guarantees in practice:

- **Linux kernel 4.2+ with ext4:** Atomic write behavior observed for writes of at least 1 MB, possibly unlimited. The kernel holds an inode mutex during the entire `write()` syscall for regular files.
- **Earlier Linux kernels with ext4:** Atomic only up to 4096 bytes reliably.
- **tmpfs:** Some reports of corruption above 1008 bytes in certain configurations.

**Critical caveat:** These are implementation details, not guarantees. They can change between kernel versions.

### 1.4 The Safe Rule for Our Message Bus

Keep each JSON message (including the trailing `\n`) under **4096 bytes** when written via a single `write()` syscall. This provides:
- Guaranteed atomicity on pipes (per POSIX)
- Reliable atomicity on local Linux ext4/xfs (per kernel implementation)
- A comfortable safety margin for typical JSON messages

### 1.5 O_APPEND in Python

```python
import os

# Open with O_APPEND for atomic seek-to-end + write
fd = os.open("bus.jsonl", os.O_WRONLY | os.O_APPEND | os.O_CREAT, 0o644)

# Write a complete message in a single syscall
message = '{"type":"info","team":"TEAM-01","ts":1710100000,"body":"hello"}\n'
encoded = message.encode("utf-8")
assert len(encoded) < 4096, "Message exceeds atomic write limit"
os.write(fd, encoded)

os.close(fd)
```

**Important:** Do NOT use Python's buffered `open()` with `print()` or `file.write()` for concurrent writers. Buffered I/O may split a logical write into multiple `write()` syscalls, breaking atomicity. Always use `os.open()` + `os.write()` for the raw syscall, or use `open()` with buffering disabled and explicit flush:

```python
# Alternative: unbuffered file object
f = open("bus.jsonl", "ab", buffering=0)
f.write(message.encode("utf-8"))  # Single write() syscall
```

### 1.6 NFS and Network Filesystems

**NFS completely breaks `O_APPEND` atomicity.** The NFS protocol has no native atomic append operation. Instead, the client must:
1. Query the current file size
2. Issue a write at that offset

This two-step process creates a race condition between clients. Even `flock()` is unreliable on NFS (emulated via `fcntl()` byte-range locks since Linux 2.6.12, with known issues).

**Recommendation:** Never use a JSONL message bus on NFS. Use only local filesystems (ext4, xfs, btrfs, tmpfs). If agents are on different machines, use a proper message broker or TCP sockets instead.

## 2. File Watching & Polling Patterns

### 2.1 inotify on Linux

`inotify` provides kernel-level event-driven file change notifications with sub-millisecond latency. For watching a JSONL bus file, use `IN_MODIFY` events.

**Using `inotify-simple` (recommended for simplicity):**

```python
import os
from inotify_simple import INotify, flags

def watch_jsonl(filepath, callback):
    """Watch a JSONL file for new lines using inotify."""
    inotify = INotify()
    watch_flags = flags.MODIFY
    wd = inotify.add_watch(filepath, watch_flags)

    with open(filepath, "r") as f:
        f.seek(0, os.SEEK_END)  # Start at end of file

        while True:
            events = inotify.read()  # Blocks until modification
            for line in f:
                line = line.strip()
                if line:
                    callback(line)
```

**Key inotify limits:**
- Default `max_user_watches`: 8192 (tunable via `/proc/sys/fs/inotify/max_user_watches`)
- Does **not** work on NFS, `/proc`, `/sys`, or FUSE filesystems
- Events can be coalesced — multiple rapid writes may produce a single `IN_MODIFY`

### 2.2 Python `watchdog` Library (Cross-Platform)

```python
import os
import time
from watchdog.observers import Observer
from watchdog.events import FileSystemEventHandler

class JSONLHandler(FileSystemEventHandler):
    def __init__(self, filepath, callback):
        self.filepath = filepath
        self.callback = callback
        self.file = open(filepath, "r")
        self.file.seek(0, os.SEEK_END)

    def on_modified(self, event):
        if event.src_path == self.filepath:
            for line in self.file:
                line = line.strip()
                if line:
                    self.callback(line)

def watch_with_watchdog(filepath, callback):
    handler = JSONLHandler(filepath, callback)
    observer = Observer()
    observer.schedule(handler, os.path.dirname(filepath), recursive=False)
    observer.start()
    try:
        while True:
            time.sleep(1)
    except KeyboardInterrupt:
        observer.stop()
    observer.join()
```

`watchdog` uses `inotify` on Linux, `kqueue` on macOS, and `ReadDirectoryChangesW` on Windows.

### 2.3 Simple Polling (No Dependencies)

For maximum simplicity and portability, a polling-based tail is often the best choice for an agent system:

```python
import os
import time
import json

class JSONLTail:
    """Poll a JSONL file for new lines. No external dependencies."""

    def __init__(self, filepath, poll_interval=0.1):
        self.filepath = filepath
        self.poll_interval = poll_interval
        self.position = 0
        self._file = None

    def seek_to_end(self):
        """Start reading from the current end of file."""
        if os.path.exists(self.filepath):
            self.position = os.path.getsize(self.filepath)

    def seek_to_offset(self, offset):
        """Start reading from a specific byte offset (for replay)."""
        self.position = offset

    def poll_once(self):
        """Read any new complete lines since last poll. Returns list of parsed objects."""
        messages = []
        try:
            current_size = os.path.getsize(self.filepath)
        except OSError:
            return messages

        if current_size <= self.position:
            return messages

        with open(self.filepath, "r") as f:
            f.seek(self.position)
            data = f.read()
            # Only process complete lines (ending with \n)
            if not data.endswith("\n"):
                # Keep partial line for next poll
                last_newline = data.rfind("\n")
                if last_newline == -1:
                    return messages  # No complete lines yet
                data = data[:last_newline + 1]

            self.position += len(data.encode("utf-8"))

            for line in data.strip().split("\n"):
                line = line.strip()
                if line:
                    try:
                        messages.append(json.loads(line))
                    except json.JSONDecodeError:
                        pass  # Skip corrupt/partial lines

        return messages

    def follow(self, callback):
        """Continuously poll for new messages, calling callback for each."""
        self.seek_to_end()
        while True:
            messages = self.poll_once()
            for msg in messages:
                callback(msg)
            if not messages:
                time.sleep(self.poll_interval)
```

### 2.4 Comparison of Approaches

| Approach | Latency | CPU Usage | Dependencies | Portability |
|----------|---------|-----------|--------------|-------------|
| `inotify` direct | <1 ms | Near zero | `inotify-simple` | Linux only |
| `watchdog` | <1 ms (Linux) | Near zero | `watchdog` | Cross-platform |
| Polling (100ms) | 0-100 ms | Minimal | None | Universal |
| Polling (1s) | 0-1 s | Negligible | None | Universal |

**Recommendation for agent systems:** Use polling at 100-200ms intervals. The simplicity and zero-dependency nature outweighs the marginal latency improvement from inotify. For agent-to-agent communication, 100ms latency is imperceptible.

## 3. JSONL Schema & Best Practices

### 3.1 Message Schema

Every message on the bus should follow a consistent envelope schema:

```json
{
  "id": "msg-uuid-here",
  "type": "info|blocker|phase-signal|heartbeat|request|response",
  "channel": "global|team-03|topic-build",
  "team": "TEAM-03",
  "ts": 1710100000.123,
  "ttl": 300,
  "body": {}
}
```

**Field definitions:**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | string | Yes | Unique message ID (UUID4 or `{team}-{counter}`) |
| `type` | string | Yes | Message type for routing/filtering |
| `channel` | string | Yes | Channel name for pub/sub filtering |
| `team` | string | Yes | Sender team identifier |
| `ts` | float | Yes | Unix timestamp with fractional seconds |
| `ttl` | int | No | Time-to-live in seconds (for expiry) |
| `body` | object | Yes | Type-specific payload |
| `in_reply_to` | string | No | Message ID this is responding to |

### 3.2 Message Types

```json
// Info: general announcements
{"id":"m-001","type":"info","channel":"global","team":"TEAM-03","ts":1710100000.0,
 "body":{"message":"Starting phase 2 analysis"}}

// Blocker: something is blocked, needs attention
{"id":"m-002","type":"blocker","channel":"global","team":"TEAM-05","ts":1710100001.0,
 "body":{"blocked_on":"API rate limit","severity":"high","context":"OpenAlex requests"}}

// Phase signal: coordination checkpoint
{"id":"m-003","type":"phase-signal","channel":"global","team":"TEAM-02","ts":1710100002.0,
 "body":{"phase":"research","status":"complete","artifact":"entries/KB-0020.md"}}

// Heartbeat: liveness indicator
{"id":"m-004","type":"heartbeat","channel":"global","team":"TEAM-07","ts":1710100003.0,
 "body":{"status":"active","progress":0.65,"current_task":"Analyzing results"}}

// Request/Response: direct team-to-team queries
{"id":"m-005","type":"request","channel":"team-03","team":"TEAM-01","ts":1710100004.0,
 "body":{"action":"get_status","params":{}}}

{"id":"m-006","type":"response","channel":"team-01","team":"TEAM-03","ts":1710100005.0,
 "in_reply_to":"m-005","body":{"status":"active","phase":"writing"}}
```

### 3.3 Handling Partial/Corrupt Lines

A writer crashing mid-write will leave a partial JSON line at the end of the file. Handling strategy:

1. **Readers must always try/catch JSON parsing per line.** Never assume every line is valid.
2. **Only process lines that end with `\n`.** A line without a trailing newline is potentially incomplete.
3. **On startup, truncate the last partial line** if the bus file does not end with `\n`:

```python
def repair_bus_file(filepath):
    """Remove trailing partial line after a crash."""
    with open(filepath, "rb+") as f:
        f.seek(0, os.SEEK_END)
        size = f.tell()
        if size == 0:
            return
        f.seek(size - 1)
        if f.read(1) != b"\n":
            # Find last complete line
            f.seek(0)
            data = f.read()
            last_newline = data.rfind(b"\n")
            if last_newline >= 0:
                f.seek(last_newline + 1)
                f.truncate()
```

4. **Never embed literal newlines in JSON values.** Use `\n` escaping (which `json.dumps()` does by default).

### 3.4 File Rotation Strategies

When a JSONL bus file grows too large, rotate it:

**Strategy 1: Size-based rotation by the coordinator**

```python
import os
import time

MAX_BUS_SIZE = 10 * 1024 * 1024  # 10 MB

def maybe_rotate(bus_path):
    if os.path.getsize(bus_path) > MAX_BUS_SIZE:
        timestamp = int(time.time())
        archive_path = f"{bus_path}.{timestamp}"
        os.rename(bus_path, archive_path)
        # Touch new file so writers don't fail
        open(bus_path, "a").close()
        return archive_path
    return None
```

**Strategy 2: Epoch-based files**

Instead of rotating a single file, use time-windowed filenames:

```
bus/global.2026-03-11T10.jsonl
bus/global.2026-03-11T11.jsonl
```

Readers watch the current epoch file. Writers always append to the current epoch file. This avoids the rename race entirely.

**Recommended approach:** Epoch-based files with hourly windows. This eliminates rotation races and provides natural archiving.

### 3.5 Line Delimiter Handling

- Always terminate every JSON object with exactly one `\n` character.
- Use `json.dumps(obj, ensure_ascii=True) + "\n"` to guarantee no embedded literal newlines.
- The `ensure_ascii=True` flag escapes all non-ASCII characters, preventing encoding-related line breaks.
- Do not use `\r\n` — stick to Unix line endings.

## 4. Concurrency Edge Cases & Mitigations

### 4.1 Multiple Writers: What Can Go Wrong

**Scenario 1: Interleaved bytes (theoretical)**

If two processes write messages simultaneously and the kernel does not guarantee atomic writes for the message size, bytes from both messages could be interleaved:

```
Process A writes: {"type":"info","team":"TEAM-01"}\n
Process B writes: {"type":"info","team":"TEAM-02"}\n
Interleaved result: {"type":"info","te{"type":"info","team":"TEAM-02"}\nam":"TEAM-01"}\n
```

**Mitigation:** Keep messages under 4096 bytes and use raw `write()` syscalls (not buffered I/O). On local Linux filesystems, this is safe in practice.

**Scenario 2: Buffered I/O splitting writes**

Python's `print()` or `file.write()` with buffering may internally split a message into multiple `write()` syscalls:

```python
# DANGEROUS: buffered I/O
f = open("bus.jsonl", "a")
f.write(big_json_string + "\n")  # May be split into multiple write() calls
```

**Mitigation:** Use `os.write()` or `open(..., buffering=0)`.

**Scenario 3: Writer crashes mid-line**

A process is killed (SIGKILL) or crashes between starting a `write()` and completing it. On local filesystems, a `write()` that has been issued to the kernel is atomic — either all bytes are written or none. A crash before `write()` returns typically means the write either completes or does not happen at all. The real risk is in application-level buffering where the data has not been flushed.

### 4.2 Reader Seeing Partial Lines

If a reader calls `read()` at the exact moment a writer is in the middle of a `write()` syscall, can it see a partial line?

- On local Linux filesystems with `O_APPEND` and writes under the inode mutex: **No.** The read will see either the complete write or not see it at all.
- On NFS: **Yes.** This is another reason to avoid NFS.
- With buffered I/O: **Yes.** If the writer's buffer is flushed in chunks.

**Mitigation:** Readers should always check that a line ends with `\n` before parsing. The `JSONLTail.poll_once()` implementation above handles this by only processing data up to the last `\n`.

### 4.3 When to Use File Locking

**File locking (`fcntl.flock`) is NOT needed when:**
- All writers use `O_APPEND` with raw `write()` syscalls
- Each message fits in a single `write()` under 4096 bytes
- The filesystem is local (ext4, xfs, btrfs, tmpfs)

**File locking IS needed when:**
- Messages may exceed 4096 bytes
- Writers use buffered I/O
- The filesystem is a network filesystem
- You need to coordinate multi-message transactions (e.g., "write header + body atomically")

```python
import fcntl

def locked_write(filepath, message_bytes):
    """Write with advisory locking for extra safety."""
    fd = os.open(filepath, os.O_WRONLY | os.O_APPEND | os.O_CREAT, 0o644)
    try:
        fcntl.flock(fd, fcntl.LOCK_EX)  # Blocks until lock acquired
        os.write(fd, message_bytes)
        # Lock released automatically when fd is closed
    finally:
        os.close(fd)
```

**For our agent system:** Locking is unnecessary if we follow the "messages under 4096 bytes, raw write(), local filesystem" rules. Avoiding locks improves throughput and eliminates deadlock risks.

### 4.4 Race Condition: File Rotation During Read/Write

If a coordinator rotates (renames) the bus file while a writer has it open:
- The writer continues writing to the old (renamed) file via its existing file descriptor.
- New writers opening the path get the new file.
- Readers tracking by path will switch to the new file; readers with an open fd continue reading the old file.

**Mitigation:** Use epoch-based files instead of rename-based rotation. Alternatively, writers should periodically re-open the file (e.g., every 100 messages).

## 5. Performance Characteristics

### 5.1 Throughput

JSONL append is fundamentally O(1) per message — no file rewriting or parsing required.

**Estimated throughput on local SSD (single writer):**

| Message Size | Write Mode | Throughput |
|-------------|------------|------------|
| 200 bytes | `os.write()`, no fsync | ~100,000-500,000 msg/sec |
| 200 bytes | `os.write()` + fsync per write | ~2,000-10,000 msg/sec |
| 200 bytes | `os.write()` + fsync every 100ms | ~50,000-200,000 msg/sec |
| 2 KB | `os.write()`, no fsync | ~50,000-200,000 msg/sec |

For our agent use case (10-50 agents sending a few messages per second each), throughput is a non-issue. Even the slowest approach handles orders of magnitude more than needed.

### 5.2 Latency

| Component | Latency |
|-----------|---------|
| `os.write()` to page cache | ~1-10 microseconds |
| `fsync()` to SSD | ~0.1-2 milliseconds |
| `inotify` notification | <1 millisecond |
| Polling (100ms interval) | 0-100 ms average 50ms |
| Polling (1s interval) | 0-1000 ms average 500ms |

**End-to-end latency (writer append to reader processing):**
- With inotify: ~1-5 ms
- With 100ms polling: ~50-100 ms average
- With 1s polling: ~500-1000 ms average

### 5.3 Disk I/O Impact

Frequent small appends without fsync are coalesced by the kernel's page cache and written in batches (typically every 5-30 seconds via `pdflush`/`writeback`). Impact is minimal.

With fsync per write, each message causes a disk flush. On SSD this is tolerable (0.1-2ms). On HDD, this can be severely limiting (~5-10ms per fsync).

**Recommendation for agent bus:** Do not fsync. The page cache provides sufficient durability for ephemeral inter-agent messages. If the system crashes, losing the last few seconds of bus messages is acceptable — agents will re-announce their state on restart via heartbeats.

### 5.4 fsync Tradeoffs

| Strategy | Data Loss on Crash | Performance Impact |
|----------|-------------------|-------------------|
| No fsync | Up to 30s of messages | None |
| fsync every 1s | Up to 1s of messages | Moderate |
| fsync per write | None | Severe (up to 50x slower) |
| fdatasync per write | None | Severe (slightly less than fsync) |

`fdatasync()` is faster than `fsync()` because it skips metadata (modification time) flushing — one disk write instead of two.

For an agent message bus, **no fsync** is the right choice. Messages are ephemeral coordination signals, not durable records.

## 6. Agent Usage Guide

### 6.1 Channel Organization

```
bus/
  global.jsonl          # All agents read, broadcast announcements
  team-01.jsonl         # Only TEAM-01 reads (direct messages to TEAM-01)
  team-02.jsonl
  ...
  topic-build.jsonl     # Agents interested in build status subscribe
  topic-blockers.jsonl  # Blocker alerts
```

**Channel types:**
- **global:** All agents subscribe. Used for phase signals, heartbeats, and broadcast announcements.
- **team-{N}:** Direct messages to a specific team. Only that team polls this file.
- **topic-{name}:** Interest-based channels. Agents subscribe to topics relevant to their work.

### 6.2 Publishing a Message

```python
import json
import os
import time
import uuid

class BusWriter:
    """Append messages to JSONL bus channels."""

    def __init__(self, bus_dir, team_id):
        self.bus_dir = bus_dir
        self.team_id = team_id
        os.makedirs(bus_dir, exist_ok=True)

    def publish(self, channel, msg_type, body, in_reply_to=None):
        msg = {
            "id": f"{self.team_id}-{uuid.uuid4().hex[:8]}",
            "type": msg_type,
            "channel": channel,
            "team": self.team_id,
            "ts": time.time(),
            "body": body,
        }
        if in_reply_to:
            msg["in_reply_to"] = in_reply_to

        line = json.dumps(msg, ensure_ascii=True, separators=(",", ":")) + "\n"
        encoded = line.encode("utf-8")
        assert len(encoded) < 4096, f"Message too large: {len(encoded)} bytes"

        filepath = os.path.join(self.bus_dir, f"{channel}.jsonl")
        fd = os.open(filepath, os.O_WRONLY | os.O_APPEND | os.O_CREAT, 0o644)
        try:
            os.write(fd, encoded)
        finally:
            os.close(fd)

    def heartbeat(self, status="active", progress=None, current_task=None):
        body = {"status": status}
        if progress is not None:
            body["progress"] = progress
        if current_task:
            body["current_task"] = current_task
        self.publish("global", "heartbeat", body)

    def alert_blocker(self, blocked_on, severity="high", context=None):
        body = {"blocked_on": blocked_on, "severity": severity}
        if context:
            body["context"] = context
        self.publish("global", "blocker", body)
        self.publish("topic-blockers", "blocker", body)

    def signal_phase(self, phase, status, artifact=None):
        body = {"phase": phase, "status": status}
        if artifact:
            body["artifact"] = artifact
        self.publish("global", "phase-signal", body)
```

### 6.3 Subscribing to Channels

```python
import json
import os
import time
import threading

class BusReader:
    """Subscribe to one or more JSONL bus channels."""

    def __init__(self, bus_dir, poll_interval=0.2):
        self.bus_dir = bus_dir
        self.poll_interval = poll_interval
        self.subscriptions = {}  # channel -> file position
        self.handlers = {}       # message_type -> [callback]
        self._running = False

    def subscribe(self, channel):
        """Subscribe to a channel, starting from current end of file."""
        filepath = os.path.join(self.bus_dir, f"{channel}.jsonl")
        # Create file if it doesn't exist
        if not os.path.exists(filepath):
            open(filepath, "a").close()
        self.subscriptions[channel] = os.path.getsize(filepath)

    def subscribe_from_beginning(self, channel):
        """Subscribe and replay all existing messages."""
        filepath = os.path.join(self.bus_dir, f"{channel}.jsonl")
        if not os.path.exists(filepath):
            open(filepath, "a").close()
        self.subscriptions[channel] = 0

    def on(self, msg_type, callback):
        """Register a handler for a message type."""
        if msg_type not in self.handlers:
            self.handlers[msg_type] = []
        self.handlers[msg_type].append(callback)

    def poll(self):
        """Poll all subscribed channels once. Returns list of new messages."""
        all_messages = []
        for channel, position in list(self.subscriptions.items()):
            filepath = os.path.join(self.bus_dir, f"{channel}.jsonl")
            try:
                current_size = os.path.getsize(filepath)
            except OSError:
                continue

            if current_size <= position:
                continue

            with open(filepath, "r") as f:
                f.seek(position)
                data = f.read()

            if not data.endswith("\n"):
                last_nl = data.rfind("\n")
                if last_nl == -1:
                    continue
                data = data[:last_nl + 1]

            self.subscriptions[channel] = position + len(data.encode("utf-8"))

            for line in data.strip().split("\n"):
                line = line.strip()
                if not line:
                    continue
                try:
                    msg = json.loads(line)
                    msg["_channel"] = channel
                    all_messages.append(msg)
                except json.JSONDecodeError:
                    continue  # Skip corrupt lines

        # Sort by timestamp
        all_messages.sort(key=lambda m: m.get("ts", 0))

        # Dispatch to handlers
        for msg in all_messages:
            msg_type = msg.get("type", "")
            for handler in self.handlers.get(msg_type, []):
                handler(msg)
            for handler in self.handlers.get("*", []):
                handler(msg)

        return all_messages

    def run(self):
        """Run the poll loop in the current thread."""
        self._running = True
        while self._running:
            messages = self.poll()
            if not messages:
                time.sleep(self.poll_interval)

    def run_in_background(self):
        """Run the poll loop in a daemon thread."""
        thread = threading.Thread(target=self.run, daemon=True)
        thread.start()
        return thread

    def stop(self):
        self._running = False
```

### 6.4 Example: Complete Agent Integration

```python
# Agent startup
bus = BusWriter("bus/", "TEAM-05")
reader = BusReader("bus/", poll_interval=0.2)

# Subscribe to relevant channels
reader.subscribe("global")
reader.subscribe("team-05")
reader.subscribe("topic-blockers")

# Handle incoming messages
def on_blocker(msg):
    if msg["team"] != "TEAM-05":  # Not our own blocker
        print(f"ALERT: {msg['team']} is blocked on {msg['body']['blocked_on']}")

def on_phase_signal(msg):
    print(f"{msg['team']} completed phase: {msg['body']['phase']}")

reader.on("blocker", on_blocker)
reader.on("phase-signal", on_phase_signal)

# Start background polling
reader.run_in_background()

# Announce presence
bus.heartbeat(status="active", current_task="Starting research")

# ... do work ...

# Report blocker
bus.alert_blocker("API rate limit hit", severity="high", context="OpenAlex")

# Signal phase completion
```

### 6.5 Heartbeat Protocol

Agents should send heartbeats every 30-60 seconds. A coordinator can detect dead agents by checking for missing heartbeats:

```python
def check_agent_health(reader, timeout=120):
    """Check which agents have gone silent."""
    now = time.time()
    last_seen = {}

    # Replay global channel from beginning
    filepath = os.path.join(reader.bus_dir, "global.jsonl")
    with open(filepath, "r") as f:
        for line in f:
            try:
                msg = json.loads(line.strip())
                if msg.get("type") == "heartbeat":
                    last_seen[msg["team"]] = msg["ts"]
            except (json.JSONDecodeError, KeyError):
                continue

    dead_agents = []
    for team, ts in last_seen.items():
        if now - ts > timeout:
            dead_agents.append((team, now - ts))

    return dead_agents
```

## 7. Gotchas & Limitations

- **Do NOT use buffered I/O for writing.** Python's `print()`, `file.write()` with default buffering, and `logging.FileHandler` all use buffered I/O that can split writes. Use `os.open()` + `os.write()` or `open(..., buffering=0)`.
- **Keep messages under 4096 bytes.** This is the safe atomic write limit. If a message body is too large, store the data in a separate file and reference it by path in the bus message.
- **Never use NFS or network filesystems.** Atomic append semantics are fundamentally broken on NFS. All agents must access the bus files on a local filesystem.
- **Readers must handle corrupt lines gracefully.** Always wrap `json.loads()` in try/except per line. A crash during write can leave a partial JSON line.
- **The last line may be incomplete.** When reading, only process lines terminated by `\n`. Buffer any trailing content without a newline for the next read cycle.
- **File rotation creates a brief window for lost messages.** If using rename-based rotation, writers with open file descriptors continue writing to the old file. Prefer epoch-based files to avoid this.
- **inotify has limits.** The default `max_user_watches` (8192) may be too low if monitoring many channels. Polling is simpler and more reliable for moderate channel counts.
- **No ordering guarantee across channels.** Messages in different `.jsonl` files have no global ordering. Use timestamps for approximate ordering. If strict ordering is required, use a single channel.
- **No delivery guarantee.** This is a best-effort bus. If a reader is down when a message is published, it will see it when it starts (if reading from a past offset), but there is no acknowledgment or retry mechanism.
- **No backpressure.** Writers never block (except for the brief `write()` syscall). If readers fall behind, messages accumulate in the file. Implement TTL-based expiry and file rotation to manage growth.
- **`os.fstat()` vs. `os.stat()` caveats.** When checking file size for polling, `os.stat()` on the path always reflects the latest state. If you hold a file descriptor, `os.fstat()` also works but may not reflect the latest data if another process extended the file (kernel typically updates this promptly on local filesystems).
- **Ensure `ensure_ascii=True` in `json.dumps()`.** This prevents multi-byte characters from causing unexpected line-break-like sequences in certain encodings.
