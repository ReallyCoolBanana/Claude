# Deep Bug Analysis: Coordination Modules (Round 2)

## Context
Comprehensive audit of all 18 coordination and prototype modules to find NEW bugs not previously identified in BUG-HP-001 through BUG-HP-014, BUG-DC-001 through BUG-DC-004, BUG-WS-001 through BUG-WS-003, BUG-WS-010, BUG-CH-001, BUG-CH-002, and other known issues (race conditions in registration, missing WAL checkpoints, file handle leaks in bus_cli.py, duplicate _retry_on_busy decorator).

## Method
Line-by-line manual review of all modules, focusing on concurrency, resource management, error handling, data integrity, logic errors, security, memory growth, and signal handling.

### BUG-NEW-001: Signal handler calls sys.exit() -- non-reentrant, skips finally blocks
- **Module**: multi_team_runner.py
- **Line(s)**: 639-645
- **Severity**: High
- **Category**: signal
- **Description**: The `_signal_handler` function calls `runner.stop()` followed by `sys.exit(0)`. Signal handlers in Python run asynchronously between bytecodes. Calling `sys.exit()` from a signal handler raises `SystemExit` in the main thread, which can interrupt code in arbitrary locations -- including inside SQLite transactions, file writes, or while holding locks. Additionally, `runner.stop()` acquires `_shared_conn_lock` and does I/O; if the signal fires while the main thread already holds that lock, a deadlock occurs.
- **Impact**: Deadlock on shutdown if the signal fires while the main thread holds `_shared_conn_lock`. Possible database corruption if `sys.exit()` interrupts a mid-transaction SQLite write. `finally` blocks in the foreground loop may be skipped.
- **Fix**: Set a flag or event in the signal handler and let the main loop handle the actual shutdown. The foreground loop already checks `runner._stop_event`, so the handler should just call `runner._stop_event.set()` and return, letting the `finally:` block in `main()` call `runner.stop()`.

### BUG-NEW-002: `_bus_write` in multi_team_runner.py uses weak channel sanitization
- **Module**: multi_team_runner.py
- **Line(s)**: 193
- **Severity**: Medium
- **Category**: security
- **Description**: The `_bus_write` function sanitizes channel names with `channel.replace("/", "_").replace("..", "_")`. This only strips `/` and `..` but allows other dangerous characters like spaces, newlines, null bytes, and special filesystem characters. Contrast with the canonical `sanitize_channel` in `bus_core.py` (line 112) which uses `re.sub(r'[^a-zA-Z0-9_-]', '_', name)`. The same weak sanitization is present in `sdk_launcher.py` at line 115.
- **Impact**: A malicious or buggy channel name containing characters like `\x00`, `\n`, or shell metacharacters could create unexpectedly named files, cause file I/O errors, or enable path traversal on certain filesystems.
- **Fix**: Replace the `str.replace` sanitization in both `multi_team_runner._bus_write` and `sdk_launcher._bus_write` with the canonical `re.sub(r'[^a-zA-Z0-9_-]', '_', channel)` pattern used in `bus_core.sanitize_channel`.

### BUG-NEW-003: `sdk_launcher.AgentProcess.start()` leaks file handle on success
- **Module**: sdk_launcher.py
- **Line(s)**: 258-266
- **Severity**: High
- **Category**: resource-leak
- **Description**: In `AgentProcess.start()`, `log_fh = open(self._log_path, "a")` opens a file handle that is passed to `asyncio.create_subprocess_exec` as `stdout=log_fh`. On the error path (`FileNotFoundError`), the file handle is closed explicitly. However, on the **success** path, `log_fh` is never closed and no reference is stored. The subprocess inherits the fd, but the Python file object is leaked. Over many agent starts/restarts, this accumulates open file descriptors.
- **Impact**: File descriptor exhaustion over time, especially with frequent agent restarts. Each restart opens a new fd that is never closed on the Python side.
- **Fix**: Store `log_fh` as `self._log_fh` and close it in the `stop()` method, or use `subprocess.DEVNULL` for stdout and redirect output within the agent command itself.

### BUG-NEW-004: `bus_core.bus_read` double-counts trailing empty segment from split
- **Module**: bus_core.py
- **Line(s)**: 417-451
- **Severity**: Medium
- **Category**: logic
- **Description**: `bus_read` uses `data.split(b"\n")` which, for data ending with `\n`, produces a trailing empty `b""` element. The loop processes all elements including this empty one. While the `if not raw_line.strip()` check skips it, the `consumed_bytes` calculation on line 425 adds `line_len + sep_len` for this empty element. Since the last element has `sep_len = 0` (line 422: `1 if i < len(lines) - 1 else 0`), this adds `0 + 0 = 0`, which is harmless. However, the real issue is that if data does NOT end with `\n` (partial write), the last element is the incomplete line. The code at line 442 correctly checks `if i == len(lines) - 1 and not data.endswith(b"\n")` and breaks. BUT: if the incomplete last line happens to be valid JSON, the code at line 448-451 would have already parsed it and added it to `msgs` AND advanced `consumed_bytes`. This means a partially-written valid JSON line (missing its newline terminator) gets consumed and its offset advanced, so if the writer completes the line later, the reader has already skipped past part of the data.
- **Impact**: On rare occasions where a concurrent writer produces a line that is valid JSON before the final `\n` is written, the reader may consume it prematurely and then advance the offset past it, causing the complete line to be partially re-read or missed entirely.
- **Fix**: Check for partial last line BEFORE attempting JSON parsing, not after. Move the `if i == len(lines) - 1 and not data.endswith(b"\n"): break` check to the very beginning of the loop body (before attempting decode/parse).

### BUG-NEW-005: `dashboard.py` leaks DB connections when `_shared_db` is not set
- **Module**: dashboard.py
- **Line(s)**: 150-161, 164-181
- **Severity**: Medium
- **Category**: resource-leak
- **Description**: `_get_db()` creates a new connection when `_shared_db` is not set (line 157-160). The functions `_get_agents()`, `_get_phase_signals()`, `_get_findings_summary()`, and `_get_runner_state()` track `is_shared` and close the connection in the `finally` block if it was not shared. However, the `--json` mode in `main()` (line 601-613) calls these functions without entering the `_SharedDB` context manager, so each function opens AND closes its own connection. This is not a leak per se, but it means 5+ separate connections are opened sequentially instead of sharing one. More importantly, if an exception occurs between `_get_db()` returning a connection and the function's `try:` block, the connection leaks.
- **Impact**: Minor: unnecessary connection churn in JSON mode. In pathological cases (exception during fetch), connections could leak.
- **Fix**: Wrap the `--json` output path in a `_SharedDB` context manager, the same way `render_dashboard` does.

- **Module**: think_tank.py

### BUG-NEW-007: `help_protocol.auto_assign_idle_teams` uses stale idle teams list
- **Module**: help_protocol.py
- **Line(s)**: 758, 793-797
- **Severity**: Medium
- **Category**: concurrency
- **Description**: `auto_assign_idle_teams()` fetches `all_idle_teams` once (line 758) and iterates over it for all open requests. When a team is assigned to a request, it is added to `assigned_teams` (a local set) to prevent double-assignment within the same invocation. However, when no capabilities are required (line 791-793), the fallback is `helpers = list(all_idle_teams)`, which includes teams that may have already been assigned in previous iterations of the outer loop. The `assigned_teams` check on line 805 catches this for the current invocation, but if two separate processes call `auto_assign_idle_teams()` concurrently, both will see the same idle teams and could try to assign the same team to different requests. The `BEGIN IMMEDIATE` on line 815 prevents corrupted state, but one of the two transactions will fail silently (the request status check on line 840 will show it's no longer "open" and break), potentially leaving a request unassigned when a valid idle team was available.
- **Impact**: Under concurrent auto-assignment, some help requests may be skipped even when idle teams are available, because two coordinators raced on the same request and the loser didn't retry with a different request.
- **Fix**: After a failed claim (request already taken on line 840-842), `continue` to the next helper instead of `break`, so the current request can be retried with a different idle team.

### BUG-NEW-008: `coordinator_hub.CoordinatorDashboard.send_instruction` -- verify_exists TOCTOU
- **Module**: coordinator_hub.py
- **Line(s)**: 573-589
- **Severity**: Medium
- **Category**: concurrency
- **Description**: `send_instruction()` with `verify_exists=True` performs a SELECT to check if the target agent exists (line 575-578), then does an INSERT (line 583-588), both under the same `self._lock`. However, the lock only serializes access through this particular `CoordinatorDashboard` instance. Another process (or another `CoordinatorDashboard` instance) could delete the agent from `agent_status` between the SELECT and the INSERT. The instruction would be inserted for a non-existent agent, which is the very condition `verify_exists` is supposed to prevent.
- **Impact**: Instructions could be sent to agents that no longer exist, wasting resources and potentially causing confusion when the instruction is never read.
- **Fix**: Use `BEGIN IMMEDIATE` to hold a write lock during the check-then-insert sequence, preventing concurrent modifications to the `agent_status` table.

### BUG-NEW-009: `work_stealing.PipelineManager.start_stage` -- non-atomic check-then-update
- **Module**: work_stealing.py
- **Line(s)**: 576-592
- **Severity**: Medium
- **Category**: concurrency
- **Description**: `start_stage()` reads the current status of a stage (SELECT on line 578-581), checks if it's "ready" (line 584), then updates it to "in_progress" (line 588-591). This is done under `self._lock` but without `BEGIN IMMEDIATE`. Two different processes could both read status="ready" simultaneously, both pass the check, and both set it to "in_progress" -- meaning two teams could start working on the same pipeline stage.
- **Impact**: Two teams could simultaneously claim and work on the same pipeline stage, leading to duplicated work and potentially conflicting outputs.
- **Fix**: Wrap the SELECT + UPDATE in a `BEGIN IMMEDIATE` transaction, or use an atomic `UPDATE ... WHERE status = 'ready'` and check `rowcount` to ensure exactly one writer succeeds.

### BUG-NEW-010: `work_stealing.complete_work` -- non-atomic authorization check
- **Module**: work_stealing.py
- **Line(s)**: 295-318
- **Severity**: Medium
- **Category**: concurrency
- **Description**: `complete_work()` reads `claimed_by` and `owner_team` from the work item (SELECT on line 303-306), checks authorization (line 309), then updates the status (line 314-317). This is under `self._lock` but without `BEGIN IMMEDIATE`. Between the SELECT and UPDATE, another process could reclaim or reassign the work item (e.g., via `reclaim_abandoned_work`), meaning the authorization check was against stale data.
- **Impact**: A team could complete a work item that was reclaimed from it, overwriting the new assignment's expected state.
- **Fix**: Use `BEGIN IMMEDIATE` to make the check-then-update atomic, or use `UPDATE ... WHERE id = ? AND (claimed_by = ? OR owner_team = ?)` and check `rowcount`.

### BUG-NEW-011: `bus_cli.py` read_msgs uses text mode -- offset tracking is broken for non-ASCII
- **Module**: bus_cli.py
- **Line(s)**: 60-81
- **Severity**: High
- **Category**: data-integrity
- **Description**: `read_msgs()` opens the file in text mode (`"r"` on line 66), reads data as a string, then computes the new offset as `since_offset + len(data.encode("utf-8"))` (line 69). The `f.seek(since_offset)` on line 67 performs a text-mode seek using a value that was computed as a byte offset. On systems where text mode might differ from binary mode (e.g., Windows with CRLF translation), or when multi-byte UTF-8 characters are present, the text-mode `seek` with a byte offset is undefined behavior. Even on Linux, `f.seek()` in text mode with a non-zero position is only valid if the position was returned by `f.tell()`, not computed from byte lengths.
- **Impact**: After the first read containing non-ASCII data, subsequent reads could seek to the wrong position, missing messages or re-reading partial data. This could cause JSON parse errors or duplicate message delivery.
- **Fix**: Open the file in binary mode (`"rb"`) as done in `direct_channels._bus_read` and `bus_core.bus_read`.

### BUG-NEW-012: `sdk_launcher.SDKLauncher._heartbeat_loop` -- unprotected shared DB access
- **Module**: sdk_launcher.py
- **Line(s)**: 836-857
- **Severity**: High
- **Category**: concurrency
- **Description**: The `_heartbeat_loop` iterates over `self._agents` and executes multiple `self._db.execute()` calls followed by `self._db.commit()`. This DB connection is shared with `AgentProcess._update_db()` (which is called from `health_check` in the health check task) and `_store_launcher_state()`. None of these accesses are synchronized with a lock. The `_db` connection has `check_same_thread=False` but SQLite connections are not thread-safe for concurrent writes from different asyncio tasks running on the same thread or from the health check coroutine.
- **Impact**: Concurrent database writes from the heartbeat loop, health check loop, and agent crash handlers could corrupt the SQLite connection state, causing "cannot operate on a closed database" errors or silently dropped writes.
- **Fix**: Add a `threading.Lock` (or `asyncio.Lock` since this is async code) around all `self._db` access, or use separate connections per coroutine.

### BUG-NEW-013: `prototype/agent_comm/bus.py` BusReader.poll() -- incorrect offset on partial line without complete prefix
- **Module**: prototype/agent_comm/bus.py
- **Line(s)**: 143-154
- **Severity**: Medium
- **Category**: logic
- **Description**: When `raw` does not end with `\n`, the code splits on the last `\n` (line 148: `raw.rsplit(b"\n", 1)`). If there is exactly one `\n` in the data, `parts[0]` is the complete line(s) before it, and `parts[1]` is the partial line after. The offset is advanced by `len(complete_part)` where `complete_part = parts[0] + b"\n"` (line 152). However, if `raw` contains NO `\n` at all (a single incomplete line), `rsplit` returns a list of length 1 (line 149), and the function correctly returns empty. BUT: if `raw` starts with `\n` (e.g., due to a concurrent writer finishing a previous partial line), `parts[0]` is `b""`, `complete_part` is `b"\n"`, and `line_bytes_list` is `[b""]`. The loop processes this empty line, produces no message, and the offset advances by 1 byte (the `\n`). This is actually correct but wasteful. The real bug is that if the previously partial line is now complete (preceding `\n` arrived), the reader has already advanced past the partial line's start in a previous poll, so the first part of the line is lost.
- **Impact**: If a partial line was seen in a previous poll (returning empty), and the writer then finishes the line, the next poll may read only the portion after the previous offset, producing a corrupt/incomplete line that fails JSON parsing.
- **Fix**: This is inherent to the offset-tracking design. The `bus_core.bus_read` in direct_channels already handles this correctly by not advancing past incomplete lines. The prototype BusReader should adopt the same pattern.

- **Module**: sdk_dashboard.py
- **Line(s)**: 933

- **Category**: logic

### BUG-NEW-015: `coordinator_hub.AgentReporter.update_status` resets error_message unconditionally
- **Module**: coordinator_hub.py
- **Line(s)**: 296
- **Severity**: Medium
- **Category**: logic
- **Description**: `update_status()` uses an INSERT...ON CONFLICT that always sets `error_message = NULL` (line 296). This means if an agent had previously called `report_error()` to set an error message, and then calls `update_status()` (e.g., to report recovery to "working" status), the error message is unconditionally cleared even if the caller didn't intend to clear it. More problematic: if a monitoring system reads the agent status between `report_error()` and a subsequent `update_status()`, it may see the error briefly; but the error history is permanently lost.
- **Impact**: Error messages are silently cleared by any subsequent status update, making it impossible to track error history and difficult for monitors to reliably detect errors.
- **Fix**: Only clear `error_message` when the new status is not "error", or add a separate `clear_error()` method and preserve the error message in `update_status()`.

### BUG-NEW-016: `help_protocol.fulfill_help` lacks BEGIN IMMEDIATE -- non-atomic read-then-write
- **Module**: help_protocol.py
- **Line(s)**: 549-588

### BUG-NEW-017: `direct_channels.DirectChannels.__del__` calls `self.close()` which acquires a lock
- **Module**: direct_channels.py
- **Line(s)**: 287-292
- **Severity**: Medium
- **Category**: concurrency
- **Description**: The `__del__` method calls `self.close()`, which acquires `self._lock`. Python's garbage collector can invoke `__del__` at arbitrary points, including during interpreter shutdown when other objects may already be finalized. If `__del__` is called while another thread holds `self._lock`, it will block the GC thread. During interpreter shutdown, the threading module may already be torn down, causing `self._lock` operations to raise exceptions.
- **Impact**: Potential deadlock or exception during garbage collection or interpreter shutdown.
- **Fix**: Remove the `__del__` method. Instead, rely on explicit `close()` calls or context managers (which the class already supports). If a safety net is desired, use `try: self.close() except Exception: pass` pattern without acquiring the lock, or check if the lock is acquirable with a timeout.

### BUG-NEW-018: `multi_team_runner._run_cleanup` -- DELETE without BEGIN IMMEDIATE
- **Module**: multi_team_runner.py
- **Line(s)**: 553-570
- **Severity**: Low
- **Category**: concurrency
- **Description**: `_run_cleanup()` executes two DELETE statements and a COMMIT under `_shared_conn_lock`. However, it doesn't use `BEGIN IMMEDIATE`, so SQLite is in autocommit mode for the first DELETE. The two DELETEs are not atomic with respect to other writers -- a new rate_limit row could be inserted between the first DELETE and the second DELETE by another process, and the rowcount sum would be inaccurate. More importantly, if the commit fails, the first DELETE may have already been applied while the second hasn't.
- **Impact**: Non-atomic cleanup: partial cleanup state if commit fails after first DELETE succeeds. Minor inconsistency in reported cleanup counts.
- **Fix**: Add `conn.execute("BEGIN IMMEDIATE")` before the DELETEs to make them atomic.

- **Module**: sdk_launcher.py
- **Line(s)**: 295-336
- **Severity**: Medium
- **Category**: security

### BUG-NEW-021: `bus_core.bus_read` returns offset=0 when file does not exist, discarding caller's offset
- **Module**: bus_core.py
- **Line(s)**: 404
- **Severity**: Low
- **Category**: logic
- **Description**: When the channel file does not exist, `bus_read` returns `([], 0)` (line 404). If the caller had a non-zero offset from a previous read and the file was temporarily deleted (e.g., by `repair_bus_file` in `bus.py` or a cleanup operation), the caller's offset is reset to 0. On the next read (after the file is recreated), the reader re-reads all messages from the beginning, causing duplicate message delivery.
- **Impact**: After a file rotation or repair, all messages in the recreated file are delivered as duplicates.
- **Fix**: Return `([], offset)` instead of `([], 0)` when the file does not exist, preserving the caller's position. Alternatively, if the file was recreated (offset > file size), reset to 0 but log a warning.

## Lessons Learned

1. **Non-atomic check-then-act patterns are pervasive**: Many modules perform SELECT-check-UPDATE sequences under a Python-level lock but without `BEGIN IMMEDIATE`. This only protects against concurrent access from the same process -- other processes can still interleave.

2. **Signal handlers must be minimal**: The `_signal_handler` in `multi_team_runner.py` does too much work (DB writes, file I/O, lock acquisition). Signal handlers should only set a flag.

3. **Channel sanitization is inconsistent**: Three different sanitization patterns exist across the codebase (`re.sub`, `str.replace`, and the canonical `bus_core.sanitize_channel`). The non-canonical versions have weaker security properties.

4. **Module-level `logging.basicConfig`**: This anti-pattern in `think_tank.py` was already identified and fixed in `multi_team_runner.py` but not propagated to all modules.

5. **`__del__` with locks is dangerous**: Python's `__del__` is unreliable and should not perform operations that could block or fail.

## Recommendations

1. **Immediate priority**: Fix BUG-NEW-001 (signal handler deadlock), BUG-NEW-003 (fd leak), BUG-NEW-011 (broken offset tracking), and BUG-NEW-012 (unprotected shared DB).

2. **Short-term**: Audit all check-then-act patterns (BUG-NEW-008, 009, 010, 016) and wrap them in `BEGIN IMMEDIATE` transactions.

3. **Medium-term**: Standardize on `bus_core.sanitize_channel` everywhere (BUG-NEW-002), fix the logging pattern (BUG-NEW-006), and remove `__del__` methods (BUG-NEW-017).

4. **Testing**: Add concurrent-writer tests that verify atomicity of `start_stage`, `complete_work`, `send_instruction(verify_exists=True)`, and `fulfill_help`.
