# FAISS GPU-Accelerated Vector Search for Wikipedia-Scale (6-7M Vectors)

## Context
Research into using FAISS with GPU acceleration for Wikipedia-scale vector search (6-7 million article vectors) on consumer hardware (RTX 4070 Super, 12GB VRAM). Covers index selection, memory budgets, throughput, incremental updates, alternatives (Qdrant, Milvus), and serving via FastAPI.

## Hardware Baseline: RTX 4070 Super
- 12 GB GDDR6X VRAM
- ~504 GB/s memory bandwidth
- 7168 CUDA cores, Ada Lovelace architecture
- FAISS GPU indexes are primarily memory-bandwidth limited (not compute limited), so the 504 GB/s bandwidth is the key spec.
- No RTX 4070 Super-specific FAISS benchmarks exist; extrapolate from H100/A100 benchmarks by ~5-10x slowdown factor.

## Memory Requirements by Index Type and Dimension

### Raw vector storage (float32)
| Dimension | Per Vector | 6M Vectors | 7M Vectors |
|-----------|-----------|------------|------------|
| 384       | 1,536 B   | 8.6 GB     | 10.0 GB    |
| 768       | 3,072 B   | 17.2 GB    | 20.0 GB    |
| 1024      | 4,096 B   | 22.9 GB    | 26.7 GB    |

**Conclusion:** Flat indexes do NOT fit in 12GB VRAM for any dimension at 6M+ vectors (except 384-dim barely, without overhead).

### IVF-PQ (Inverted File + Product Quantization)
PQ compresses each vector to M bytes (where M = number of subquantizers, typically 8-64).

| Config (PQ bytes) | Per Vector | 6M Vectors (index data) | + IDs (8B each) | Total Index |
|--------------------|-----------|-------------------------|-----------------|-------------|
| PQ8                | 8 B       | 48 MB                   | 48 MB           | ~96 MB      |
| PQ16               | 16 B      | 96 MB                   | 48 MB           | ~144 MB     |
| PQ32               | 32 B      | 192 MB                  | 48 MB           | ~240 MB     |
| PQ64               | 64 B      | 384 MB                  | 48 MB           | ~432 MB     |

**GPU overhead adds significantly:**
- Precomputed lookup tables for GpuIndexIVFPQ: 100s MB to GBs depending on nlist and PQ parameters
- Default scratch memory: 1.5 GB (configurable down to 0)
- Real-world report: 5.2M vectors at 144-dim with IVF2500,PQ48 used ~4.8 GB GPU memory
- Real-world report: 56M vectors fit in IVFPQ on RTX 2080 Ti using ~6.9 GB / 11.3 GB VRAM

**Estimated total VRAM for 6M vectors on GPU (IVF-PQ):**
| Dimension | PQ Config | Estimated VRAM |
|-----------|-----------|----------------|
| 384       | PQ16      | 2-4 GB         |
| 768       | PQ32      | 3-5 GB         |
| 768       | PQ64      | 4-6 GB         |
| 1024      | PQ64      | 5-8 GB         |

All configurations fit within 12 GB VRAM. Use `useFloat16=True` and `INDICES_CPU` to save further.

### HNSW (CPU only in FAISS; CAGRA for GPU graphs)
Memory = (d * 4 + M * 2 * 4) bytes per vector, where M = number of links.

| Dimension | HNSW M=32 per vector | 6M Vectors |
|-----------|---------------------|------------|
| 384       | 1,792 B             | 10.0 GB    |
| 768       | 3,328 B             | 18.6 GB    |
| 1024      | 4,352 B             | 24.3 GB    |

HNSW is CPU/RAM only in FAISS. Very fast queries but heavy on RAM. For 768-dim at 6M vectors, need ~19 GB RAM.

### CAGRA (GPU graph index via cuVS, Faiss >= 1.10)
- GPU-native graph-based index, built from the ground up for GPU
- Can be converted to HNSW for CPU deployment
- Build 12x faster than CPU HNSW, search 4.7x lower latency
- VRAM usage: comparable to HNSW but on GPU; likely needs >12 GB for 768-dim at 6M vectors
- Best pattern: build CAGRA on GPU, export to CPU HNSW for serving

## Optimal IVF-PQ Configuration for 6-7M Vectors

| Parameter       | Recommended              | Notes |
|----------------|--------------------------|-------|
| nlist          | 2,500 - 4,096            | Rule: sqrt(N) to C*sqrt(N), sqrt(6M) ~ 2,449 |
| m (PQ subs)    | 32 or 64                 | Must divide dimension d evenly |
| nbits          | 8                        | Standard; FAISS requires >= 8 for IVF-PQ |
| nprobe         | 16 - 128                 | Higher = better recall, slower; tune empirically |
| Training data  | >= 1000 * nlist vectors  | ~2.5-4M vectors for training |
| Pre-processing | OPQ recommended          | Rotates vectors for better PQ compression |

**Index factory string:** `"OPQ32,IVF4096,PQ32"` or `"OPQ64,IVF4096,PQ64"`

## Throughput Benchmarks

### Build Time (cuVS-accelerated, Faiss 1.10+, H100 GPU)
- IVF-PQ/IVF-Flat build: up to 4.7x faster than classic GPU FAISS
- CAGRA graph build: up to 12.3x faster than CPU HNSW
- For 6M vectors at 768-dim, expect IVF-PQ training+build in minutes on GPU

### Query Throughput (H100 benchmarks, extrapolate ~5-10x for RTX 4070 Super)
- IVF-PQ search latency: up to 8x lower than classic GPU at 95% recall
- CAGRA batch throughput: up to 18x higher than CPU HNSW (millions of QPS on H100)
- Single-query latency: sub-millisecond on H100; expect low single-digit ms on RTX 4070 Super
- GPU FAISS general: 5-10x faster than CPU on single GPU

### CPU Baseline (for comparison)
- FAISS CPU (IVF-PQ, 1M vectors, 128-dim): thousands of QPS on multi-core Xeon
- HNSW CPU: very fast queries (~microseconds per query) but slow build

### Estimated RTX 4070 Super Performance (6M vectors, 768-dim, IVF-PQ32)
- Build time: 5-15 minutes (with cuVS)
- Single query latency: 1-5 ms (nprobe=32, k=10)
- Batch throughput (batch=1000): 10,000-50,000 QPS
- Recall at nprobe=32: ~90-95% (depends on data distribution)

## FAISS vs Qdrant vs Milvus (Single Machine)

| Aspect              | FAISS (GPU)           | Qdrant               | Milvus Standalone     |
|---------------------|----------------------|----------------------|----------------------|
| Type                | Library              | Database (Rust)      | Database (Go/C++)    |
| Raw search speed    | Fastest              | Very fast            | Fast                 |
| GPU support         | Native, mature       | GPU HNSW (2025)      | GPU IVF (via Knowhere)|
| Filtering           | None built-in        | Best-in-class        | Hybrid search        |
| CRUD operations     | Manual (add/remove)  | Full CRUD            | Full CRUD            |
| Persistence         | Manual save/load     | Built-in             | Built-in             |
| Replication/HA      | None                 | Built-in             | Built-in             |
| Concurrent access   | Manual locking       | Built-in             | Built-in             |
| RAM (6M, 768d)      | 2-6 GB (IVF-PQ GPU)  | ~8-20 GB             | ~8-20 GB             |
| Incremental updates | Add vectors OK; periodic retrain | Native | Native              |
| Operational overhead| High (DIY)           | Low                  | Medium               |
| Latency (p99)       | Sub-ms to few ms     | 30-40 ms (50M vecs)  | Varies               |

**Key takeaway:** FAISS wins on raw speed and GPU utilization. Qdrant wins on operational simplicity and filtering. Milvus wins on feature completeness. For a single-machine Wikipedia search with no metadata filtering needed, FAISS + GPU is the performance leader.

### Qdrant Specific Numbers
- 1M vectors, 1536-dim: worst p95 latency 2.85s (t3.2xlarge, 8 vCPU)
- 50M vectors, 768-dim at 99% recall: p50 30.75ms, p95 36.73ms, p99 38.71ms
- GPU HNSW indexing added in 2025 for faster ingestion
- ~8.6 GB RAM for 1M vectors at 1536-dim (including index)

## Incremental Index Updates

### What works
- **Flat indexes:** Full add/remove/update via `IndexIDMap` + `add_with_ids()` + `remove_ids()`
- **IVF indexes:** Train once on representative sample, then `add()` new vectors indefinitely
- **IVF-PQ on GPU:** `GpuIndexIVFPQ.add()` appends vectors to existing inverted lists

### Limitations
- No in-place update; must remove + re-add
- Adding vectors to IVF does NOT update centroids; if data distribution drifts, recall degrades
- Periodic retrain recommended (e.g., monthly maintenance window)
- HNSW: supports incremental add but not remove (without workarounds)
- CAGRA: if exported with `base_level_only=False`, the resulting HNSW allows adds

### Practical Pattern for Wikipedia
1. Train IVF-PQ on initial full corpus (~6M vectors)
2. Daily/weekly: add new/updated article vectors via `add_with_ids()`
3. Remove deleted articles via `remove_ids()`
4. Monthly: evaluate recall drift; retrain if needed (takes minutes on GPU)
5. Keep a shadow index for zero-downtime rebuilds

## FAISS + FastAPI Serving Pattern

### Architecture
```
Client -> FastAPI (uvicorn) -> FAISS GPU Index (in-process)
                            -> Embedding Model (in-process or separate)
```

### Key Design Decisions
1. **Single process:** FAISS GPU index lives in the FastAPI process; use async endpoints but FAISS calls are synchronous (run in threadpool via `run_in_executor`)
2. **Index loading:** Load index at startup (`faiss.read_index()` then `faiss.index_cpu_to_gpu()`)
3. **Concurrency:** FAISS GPU handles batch queries efficiently; batch incoming requests with a short time window (e.g., 10ms) for throughput
4. **Workers:** Single worker per GPU (FAISS GPU is not multi-process safe on same device); use multiple GPUs for multiple workers
5. **Persistence:** Periodically save CPU copy of index to disk

### Minimal Example Pattern
```python
from fastapi import FastAPI
import faiss
import numpy as np

app = FastAPI()
res = faiss.StandardGpuResources()
res.setTempMemory(512 * 1024 * 1024)  # 512MB scratch

cpu_index = faiss.read_index("wiki.index")
gpu_index = faiss.index_cpu_to_gpu(res, 0, cpu_index)

@app.post("/search")
async def search(vectors: list[list[float]], k: int = 10):
    xq = np.array(vectors, dtype=np.float32)
    distances, indices = gpu_index.search(xq, k)
    return {"distances": distances.tolist(), "indices": indices.tolist()}

@app.post("/add")
async def add(vectors: list[list[float]], ids: list[int]):
    xb = np.array(vectors, dtype=np.float32)
    ids_arr = np.array(ids, dtype=np.int64)
    gpu_index.add_with_ids(xb, ids_arr)
    return {"status": "ok", "total": gpu_index.ntotal}
```

## Recommendations for Wikipedia-Scale (6-7M vectors, RTX 4070 Super)

### Recommended Configuration
- **Embedding dimension:** 384 (e.g., all-MiniLM-L6-v2) preferred for VRAM efficiency; 768 workable
- **Index type:** `OPQ32,IVF4096,PQ32` on GPU
- **VRAM usage:** ~3-5 GB (leaves room for embedding model on same GPU)
- **Recall:** 90-95% at nprobe=32-64
- **Latency:** 1-5 ms single query, sub-ms in batch
- **Throughput:** 10,000-50,000+ QPS in batch mode

### If you need metadata filtering
Use Qdrant instead. FAISS has no native filtering; bolting it on is fragile and slow.

### If you need zero operational overhead
Use Qdrant or Milvus Standalone. FAISS requires building your own persistence, concurrency, and update logic.

### If you need maximum raw speed
Use FAISS GPU with IVF-PQ. Nothing else comes close on a single machine with a GPU.
