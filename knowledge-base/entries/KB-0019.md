# Architecture & Integration Analysis: Live Communication System

## Executive Summary

This entry analyzes how the proposed JSONL message bus (KB-0015) and SQLite WAL shared state (KB-0016) integrate with the existing repository infrastructure, including git worktrees, existing tools, the coordinator pattern, and SOPs. The central architectural question is **file placement**: both systems require all processes to access shared files on a local filesystem, which conflicts with the current worktree-based isolation model. This analysis provides a concrete directory structure, migration path, and SOP changes needed for adoption.

**Recommendation: CONDITIONAL YES.** The system is sound and addresses real gaps (no live heartbeats, no real-time blocker alerts, no shared rate-limit state). Adoption should be incremental, starting with a single coordinator + sub-teams operation, using a shared directory at the repository root (`storage/coordination/`) that is excluded from git via `.gitignore`.

## 1. Git Worktree Integration

### 1.1 The Critical Placement Question

Current pattern (from SOPs section 3.2 and KB-0009): agents work in isolated git worktrees under `.claude/worktrees/`. Each worktree is a full checkout of the repository at a specific branch, with its own working directory.

The JSONL bus and SQLite DB both have a hard requirement: **all processes must access the same files on a local filesystem** (KB-0015 section 1.6; KB-0016 section 1.3). This creates a tension:

| Placement | Communication Works? | Git Isolation Works? |
|-----------|---------------------|---------------------|
| Inside each worktree | No -- agents cannot see each other's files | Yes |
| In the main repo checkout | Partially -- worktrees are separate directories | Yes |
| Outside the repo entirely (e.g., `/tmp/claude-coordination/`) | Yes | Yes, but discovery is hard |
| Shared directory within repo root, gitignored | Yes | Yes |

### 1.2 Recommendation: Shared Coordination Directory

Place all coordination infrastructure at a fixed, well-known path relative to the **original repository root** (not worktrees):

```
$REPO_ROOT/storage/coordination/
  bus/                    # JSONL message bus channels
    global.jsonl
    team-01.jsonl
    topic-blockers.jsonl
    ...
  state.db                # SQLite WAL shared state
  state.db-wal            # WAL file (auto-created by SQLite)
  state.db-shm            # Shared memory file (auto-created by SQLite)
```

### 1.3 How Agents Find the Shared Directory

Agents in worktrees need a reliable way to locate the coordination directory. Three approaches, in order of preference:

**Approach 1: Environment variable (recommended)**
The coordinator sets `CLAUDE_COORD_DIR` before launching sub-teams. All agents read this variable.

```python
import os
COORD_DIR = os.environ.get("CLAUDE_COORD_DIR",
    os.path.join(os.path.dirname(__file__), "..", "..", "storage", "coordination"))
```

**Approach 2: Resolve via `git rev-parse`**
Each agent can find the main repo root regardless of worktree:

```python
import subprocess
def get_repo_root():
    """Get the common dir (main repo) even from a worktree."""
    result = subprocess.run(
        ["git", "rev-parse", "--git-common-dir"],
        capture_output=True, text=True, check=True
    )
    git_common = result.stdout.strip()
    # git-common-dir returns the .git directory of the main checkout
    return os.path.dirname(os.path.abspath(git_common))
```

**Approach 3: Symlink from each worktree**
During worktree setup, create a symlink: `$WORKTREE/.coordination -> $REPO_ROOT/storage/coordination/`. This is fragile and not recommended.

**Recommendation:** Use Approach 1 (environment variable) as the primary method with Approach 2 as a fallback. The coordinator should export `CLAUDE_COORD_DIR` before spawning sub-agents, and agents should use `git rev-parse --git-common-dir` as a fallback if the variable is unset.

### 1.4 Worktree Lifecycle Implications

- **Worktree creation:** No changes needed. The coordination directory lives outside worktrees.
- **Worktree deletion/cleanup:** No impact on coordination files. However, if an agent's worktree is deleted while the agent is running, any open file descriptors to bus files remain valid (the kernel keeps the file alive until all descriptors close).
- **Branch merges:** Coordination files are gitignored, so merges do not affect them. This is correct -- coordination state is ephemeral per-operation, not persistent across sessions.

## 2. Existing Tool Integration

### 2.1 handoff_tracker.py (SCR-0019)

**Relationship: Complement, not replace.**

`handoff_tracker.py` operates on persistent team session logs (Markdown files in `teams/sessions/`). It extracts action items from "Handoff Notes" sections and tracks whether subsequent teams addressed them. This is a **post-hoc, cross-session** tool.

The JSONL bus + SQLite system operates **within a single coordinated operation**, providing live communication. These serve different time horizons:

| Dimension | handoff_tracker.py | Live Communication |
|-----------|-------------------|-------------------|
| Time horizon | Cross-session (days/weeks) | Within-operation (minutes) |
| Data persistence | Permanent (committed to git) | Ephemeral (gitignored, cleaned between ops) |
| Communication model | Async written notes | Near-real-time messages |
| Use case | "What did TEAM-0009 leave for us?" | "TEAM-05 is blocked on rate limits right now" |

**Integration point:** At operation end, the coordinator should extract key messages from the bus (blockers encountered, phase completions, important decisions) and include them in the team session log's Handoff Notes. This makes live communication artifacts available to `handoff_tracker.py` for cross-session tracking.

### 2.2 kb_validator.py (SCR-0012)

**No changes needed.** `kb_validator.py` validates KB entries and `index.json` consistency. The coordination directory contains no KB entries (it is gitignored ephemeral state), so `kb_validator.py` never touches it.

### 2.3 index_rebuilder.py (SCR-0013)

**No changes needed.** Like `kb_validator.py`, this scans `knowledge-base/entries/` and `teams/sessions/`. The coordination directory is outside its scope.

### 2.4 cross_ref_checker.py (SCR-0014)

**No changes needed.** Cross-references exist between KB entries (`builds_on` fields). The coordination system has no cross-references to validate.

### 2.5 fast_validate (SCR-0016, Go)

**Recommended extension: add coordination health check.**

The Go tool currently validates repository structure in <2ms. A new check could verify:
- Coordination directory exists and is writable (if an operation is active)
- SQLite DB is accessible and not corrupted (attempt to open and read schema version)
- Bus files are not excessively large (warn if any channel exceeds 10 MB)
- No stale lock files (`state.db-wal` exists but DB is not being used)

This should be an **optional check** (`--check-coordination` flag) since the coordination directory only exists during active operations. Adding it should not increase baseline validation time significantly.

### 2.6 Sonnet Research API queue_manager.py

**Recommended update: integrate rate-limit state.**

Currently, `queue_manager.py` maintains its own in-process rate limiter (`RATE_LIMIT_REQUESTS_PER_MINUTE` from config). With the SQLite shared state, multiple instances of the Sonnet Research API (across teams) could share rate-limit tracking:

```python
# Instead of per-process rate counting:
coordinator.check_rate_limit("anthropic-api", cost=1)  # Returns True if allowed

# This prevents Team A and Team B from independently using 50 req/min each,
# totaling 100 req/min against a 50 req/min limit.
```

This is a **nice-to-have**, not a blocker. The queue_manager would need a conditional import: use shared SQLite rate limits if `CLAUDE_COORD_DIR` is set, fall back to per-process limits otherwise.

## 3. Coordinator Pattern Evolution

### 3.1 Current Pattern (from KB-0009 and SOPs)

The coordinator currently:
- Has **read-only access** to all team outputs (git worktree files)
- Polls file outputs (completed KB entries, scripts, etc.)
- Produces synergy reports and health scores
- Routes findings between teams by reading one team's output and informing another
- Has no mechanism for real-time communication during phases

### 3.2 Enhanced Pattern with Live Communication

With the bus + SQLite system, the coordinator gains:

**New read capabilities:**
- Live heartbeats from all agents (detect dead/stuck teams in real-time)
- Blocker alerts as they happen (not after the team has already timed out)
- Phase completion signals (know instantly when a team finishes, not by polling for file existence)

**New write capabilities (required):**
- Send commands to teams: "pause", "switch to fallback", "skip this subtask"
- Broadcast global announcements: "Rate limit hit, all teams reduce API calls"
- Update shared rate-limit state so all teams respect collective limits
- Signal phase transitions: "Phase 1 complete, Phase 2 teams may start"

### 3.3 Does the Coordinator Need Write Access?

**Yes, the coordinator must have write access to both the bus and SQLite DB.**

This is a departure from the current "read-only coordinator" pattern, but it is necessary and safe:
- Bus writes are append-only (no data corruption risk)
- SQLite writes are serialized by the write lock (no concurrent write corruption)
- The coordinator writes to different channels/tables than agents (coordinator writes to `global` and `team-*` channels; agents write to their own team channel and `global`)

The coordinator should be the **only agent that writes to `team-*` channels** (sending directives to specific teams). Teams write to `global` and `topic-*` channels. This convention prevents teams from sending unauthorized commands to each other.

### 3.4 How Coordination Changes

| Operation | Current Pattern | Enhanced Pattern |
|-----------|----------------|-----------------|
| Detect dead team | Poll for file output; notice absence after phase timeout | SQLite heartbeat check: no heartbeat for 120s = alert |
| Handle blocker | Not detected until post-mortem | Bus blocker message triggers coordinator intervention |
| Phase transition | Manual phase ordering; hope teams finish in time | Phase signals in SQLite; coordinator gates Phase N+1 on Phase N completion |
| Rate limit sharing | Each team has independent limits | SQLite rate_limits table provides collective tracking |
| Dynamic re-tasking | Not possible mid-operation | Coordinator sends commands via team-specific bus channels |
| Progress tracking | No real-time visibility | Heartbeat progress field gives percentage estimates |

### 3.5 Coordinator Implementation Sketch

    def __init__(self, coord_dir):
        self.bus = BusWriter(os.path.join(coord_dir, "bus"), "COORDINATOR")
        self.reader = BusReader(os.path.join(coord_dir, "bus"))
        self.db = AgentCoordinator(os.path.join(coord_dir, "state.db"), "COORDINATOR")

    def launch_operation(self, teams):
        # 1. Initialize SQLite schema
        # 2. Create bus channel files
        # 3. Export CLAUDE_COORD_DIR
        # 4. Launch sub-agents in worktrees
        # 5. Start monitoring loop
        pass

    def monitoring_loop(self):
        while self.operation_active:
            # Check heartbeats
            dead_teams = self.db.get_stale_agents(timeout=120)
            if dead_teams:
                self.handle_dead_teams(dead_teams)

            # Process bus messages
            messages = self.reader.poll()
            for msg in messages:
                if msg["type"] == "blocker":
                    self.handle_blocker(msg)
                elif msg["type"] == "phase-signal":
                    self.handle_phase_completion(msg)

            time.sleep(1)

## 4. SOP Changes Required

### 4.1 New Pre-Mission Checklist Items

Add to SOPs section 2 ("Pre-Mission Checklist"):

- [ ] **Initialize coordination directory** (if using live communication):
  ```bash
  mkdir -p storage/coordination/bus
  python3 storage/scripts/init_coordination.py  # Creates SQLite schema + empty bus files
  ```
- [ ] **Set `CLAUDE_COORD_DIR`** environment variable to the absolute path of `storage/coordination/`
- [ ] **Verify `.gitignore`** includes coordination file patterns (see section 5.3)
- [ ] **Decide bus channels:** At minimum, create `global.jsonl`. Add `team-{N}.jsonl` for each team, plus any topic channels needed.

### 4.2 New SOPs for Message Bus Usage

Add a new section to SOPs (section 3.7):

**3.7 Live Communication Protocol**

1. **Heartbeats:** All agents send a heartbeat every 30 seconds via the bus (`type: heartbeat` to `global` channel) and update the SQLite `agents` table. Include progress percentage and current task description.
2. **Blockers:** Immediately publish a `blocker` message to both `global` and `topic-blockers` channels when blocked. Include severity and context.
3. **Phase signals:** When completing a major phase, publish a `phase-signal` message to `global` with the phase name, status, and artifact path.
4. **Message size:** Keep all messages under 4096 bytes. If payload is large, write data to a file and reference the path in the message body.
5. **Channel discipline:**
   - Agents write to: `global`, `topic-*`, and their own `team-{N}` channel
   - Coordinator writes to: `global` and any `team-{N}` channel (directives)
   - Agents read: `global`, `topic-*` channels they care about, and their own `team-{N}` channel
6. **Rate-limit coordination:** Before making external API calls, check `coordinator.check_rate_limit(api_name, cost=1)`. If denied, wait and retry.

### 4.3 Team Session Log Template Changes

Add a new optional section to `teams/TEAM_LOG_TEMPLATE.md`:

```markdown

- Messages sent: N

```

### 4.4 New Cleanup/Maintenance Procedures

Add to SOPs section 4 ("Post-Mission Checklist"):

## 6. Migration Path

### 6.1 Incremental Adoption

Yes, this system can be adopted incrementally. The key design principle: **if the coordination directory does not exist or `CLAUDE_COORD_DIR` is not set, all coordination features are no-ops.** This means:

- Teams that do not use live communication continue to work exactly as before
- The coordinator can optionally enable live communication for specific operations
- A single operation can mix teams that use the bus with teams that do not

### 6.2 Minimum Viable Deployment (Phase 1)

Deploy in three steps:

**Step 1: Infrastructure (1 team, ~30 minutes)**
- Create `storage/coordination/` directory structure
- Implement `coordination_bus.py` with BusWriter and BusReader
- Implement `coordination_state.py` with AgentCoordinator
- Implement `init_coordination.py`
- Add `.gitignore` rules
- Register scripts in `index.json`

**Step 2: Integration Test (1 team, ~15 minutes)**
- Write a multi-process test: spawn 5 writer processes and 1 reader process
- Verify messages arrive correctly, no corruption
- Verify SQLite concurrent access works (5 readers + 1 writer)
- Benchmark: measure end-to-end latency and throughput

**Step 3: Pilot Operation (1 coordinated operation)**
- Run a coordinator + 3 sub-teams operation with live communication enabled
- Coordinator monitors heartbeats and bus messages
- Compare operational visibility to a non-bus operation

### 6.3 Full Deployment (Phase 2)

After a successful pilot:
- Update SOPs with the new checklist items (section 4 of this document)
- Update the team session log template
- Extend `fast_validate` with optional coordination health check
- Train the enhanced coordinator pattern into standard operations

### 6.4 Rollback Plan

Rollback is straightforward because the system is additive:

1. **Immediate rollback:** Delete `storage/coordination/` and unset `CLAUDE_COORD_DIR`. All agents fall back to the existing file-polling pattern.
2. **Code rollback:** The `coordination_bus.py` and `coordination_state.py` modules are standalone. Removing them does not affect any existing code (no existing tool imports them).
3. **SOP rollback:** Remove the new checklist items. Pre-existing checklist items remain valid.
4. **Git rollback:** Since coordination data files are gitignored, there is nothing to revert in git history beyond the script files themselves.

### 6.5 Testing Before Full Deployment

1. **Unit tests:** Test BusWriter/BusReader with single-process sequential writes; verify JSON parsing, position tracking, partial-line handling.
2. **Concurrency tests:** Spawn N processes writing to the same JSONL file simultaneously; verify no corruption (all lines parse as valid JSON).
3. **SQLite contention test:** Spawn N processes doing concurrent reads + 1 writer doing rapid inserts; verify no `database is locked` errors with `busy_timeout=5000`.
4. **Integration test:** Simulate a mini-operation with a coordinator + 3 mock agents, each sending heartbeats and phase signals. Verify the coordinator detects a "dead" agent (one that stops sending heartbeats).
5. **Pilot operation:** Run a real multi-team operation (e.g., a small research + build task) with the bus enabled alongside the existing file-polling pattern. Compare outcomes.

## 7. Dependencies & Requirements

### 7.1 Python Dependencies

**Python stdlib only.** Both KB-0015 and KB-0016 are designed around Python standard library modules:

| Module | Usage | Stdlib? |
|--------|-------|---------|
| `os` | File operations, `O_APPEND`, `O_CREAT` | Yes |
| `json` | JSON serialization/deserialization | Yes |
| `sqlite3` | SQLite database access | Yes |
| `time` | Timestamps, sleep | Yes |
| `uuid` | Message IDs | Yes |
| `threading` | Background polling thread | Yes |
| `subprocess` | `git rev-parse` for worktree resolution | Yes |

No external packages are required. This aligns with the existing repository convention: "Archive/validation tools: Pure Python stdlib only" (SOPs section 6.1).

The `inotify-simple` and `watchdog` libraries mentioned in KB-0015 are explicitly **not recommended** for this deployment. Polling at 100-200ms intervals is sufficient and avoids external dependencies.

### 7.2 OS-Level Requirements

- **Local filesystem:** ext4, xfs, or btrfs. No NFS, no FUSE, no network filesystems. Both JSONL atomic writes and SQLite WAL's shared memory file require local filesystem semantics.
- **Linux kernel 4.2+:** For reliable atomic append writes up to 4096 bytes. Current environment reports Linux 6.18.5, which is well above this threshold.
- **No special kernel modules:** inotify is not required (we use polling). No special sysctls needed.

### 7.3 Memory & Disk Requirements

| Resource | Estimate | Notes |
|----------|----------|-------|
| SQLite DB size | < 1 MB | Schema is small; rows are ephemeral |
| SQLite WAL file | < 4 MB | Auto-checkpoints at 1000 pages |
| SQLite SHM file | 32 KB | Fixed size |
| JSONL bus files (total) | < 50 MB per operation | Depends on duration and message frequency |
| Memory per agent | ~5 MB additional | BusReader position tracking, SQLite connection |

For a typical operation (10 agents, 30-minute duration, heartbeats every 30s, ~100 messages per agent): total bus size is approximately 10 * 100 * 200 bytes = 200 KB. Well within limits.

### 7.4 Constrained Environments

In environments with limited resources:
- **Read-only filesystem:** The coordination system will not work. Fall back to the existing file-polling pattern. The `init_coordination.py` script should detect this and warn.
- **No `/tmp` access:** Not an issue; we use the repo's own `storage/coordination/` directory.
- **Low disk space:** JSONL files can be rotated or truncated by the coordinator. SQLite auto-checkpoints keep WAL size bounded.
- **No `sqlite3` module:** Extremely unlikely in any standard Python 3 installation, but if absent, the system can fall back to JSONL-only mode (no structured state queries, but basic communication still works).

## Recommendation

**CONDITIONAL YES.** Adopt the JSONL bus + SQLite WAL system with the following conditions:

1. **File placement:** Use `storage/coordination/` in the main repository root, not inside worktrees. Agents discover it via `CLAUDE_COORD_DIR` environment variable with `git rev-parse --git-common-dir` as fallback.

2. **Gitignore all ephemeral files.** Only commit the Python modules (`coordination_bus.py`, `coordination_state.py`, `init_coordination.py`), the directory structure (`.gitkeep`), and a README. Never commit `.jsonl`, `.db`, `-wal`, or `-shm` files.

3. **Incremental adoption.** Start with a pilot operation before updating SOPs. Allow mixed operations where some teams use the bus and others do not.

4. **Coordinator gets write access.** This is a necessary departure from the current read-only coordinator pattern. Write access is safe due to the append-only (bus) and serialized-write (SQLite) guarantees.

5. **stdlib only.** No external packages. Polling at 100-200ms intervals, not inotify.

6. **Clean between operations.** Coordination state is ephemeral. Delete all bus and DB files after each operation completes. Archive first if post-mortem analysis is desired.

The system addresses three concrete gaps identified in prior operations: no live heartbeat monitoring (coordinators could not detect dead agents until phase timeout), no real-time blocker communication (teams blocked silently), and no shared rate-limit state (teams independently exceeded collective API limits). The implementation cost is modest (3 Python modules, ~500 lines total), the rollback is trivial, and there are zero new external dependencies.
