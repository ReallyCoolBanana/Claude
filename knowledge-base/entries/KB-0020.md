# Live Prototype Testing: Data Gathering Benchmark Results

## Context

Following the prototype build and testing phase (KB-0018) and architecture analysis (KB-0019), we needed to validate both prototypes under real-world conditions — actual multi-agent data gathering with live API calls, not just synthetic unit tests. This entry documents the first live testing operation.

## Method

### Team Structure: TEAM-0020

**Phase 1 — Think Tank (3 parallel teams, 9 simulated agents):**
- Think Tank Alpha: Communication architecture design
- Think Tank Beta: Coordination strategy with state machine
- Think Tank Gamma: Benchmark methodology specification

**Phase 2 — Data Gathering Teams (3 parallel teams):**
- Data Team A: Prototype A (JSONL + SQLite) with live OpenAlex + HN APIs
- Data Team B: Prototype B (FIFO + mmap) with live OpenAlex + HN APIs
- Data Team C: Baseline (file-polling, no proto) with same APIs

**Phase 3 — Automated Benchmark (36 runs):**
- 4 scenarios × 3 prototypes × 3 repetitions
- Synthetic data sources with configurable latency/rate limits
- Comparison report with statistical analysis

### Custom SOP Created
`teams/SOPs-prototype-testing.md` — 9 sections covering pre-test, think tank, data gathering, benchmarking, metrics, scoring, and archiving procedures. Does not overwrite the main `SOPs.md`.

## Key Findings

1. **Both prototypes are production-viable.** Overhead is <1% across all scenarios, well under the 10% PASS threshold.

2. **Proto A collects fewer data points due to active rate limiting.** SQLite BEGIN IMMEDIATE correctly enforces collective rate limits (1071 denials in S1 vs 0 for baseline/Proto B). This is a *feature*, not a bug — it prevents API abuse.

3. **Proto B has lower raw overhead (0.1-0.4%)** than Proto A (0.2-0.8%), likely because mmap operations avoid the SQLite transaction overhead. However, Proto B's rate limiter is weaker (no denials = no enforcement).

4. **Communication adds negligible latency.** JSONL bus adds ~0.2 ms per message. This is invisible compared to API call latency (150-2200 ms).

5. **Heartbeats work reliably.** Both prototypes maintained heartbeat loops during active data gathering without dropping beats.

6. **Failure injection handled cleanly.** S4 showed 0 errors even when agents were killed mid-run. The coordination layer degrades gracefully.

## Lessons Learned

1. **Rate limiting is the biggest differentiator.** Proto A's SQLite-based rate limiter actively prevents over-calling APIs. Proto B's mmap-based limiter needs configuration to be effective.

2. **Think tank phase is valuable.** The Alpha/Beta/Gamma plans produced actionable architecture (channel design, state machine, metrics framework) that directly informed test execution.

3. **Synthetic benchmarks complement but don't replace live tests.** The automated benchmark (synthetic data) showed negligible overhead, but the live tests revealed that real API latency (100-2200ms) completely dominates — communication overhead is irrelevant at that scale.

4. **Proto B's FIFO spillover works transparently.** When no reader is attached, messages go to spillover files. This means bus_file_bytes=0 for FIFOs but data is still preserved.

## Recommendations

1. **Use Proto A for production data gathering** — active rate limiting prevents API abuse and the overhead is negligible.
2. **Reserve Proto B for latency-critical operations** where sub-millisecond coordination matters and rate limits are enforced externally.
3. **Next test: multi-process (not thread) benchmarks** — the current tests use threads within a single process. Real agent teams would be separate processes.
4. **Integrate the benchmark runner into CI** — `proto_benchmark_runner.py` should run as a regression check before any coordinator changes.
