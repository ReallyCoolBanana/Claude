# Failure Mode Analysis: JSONL Bus + SQLite WAL Shared State

## Executive Summary

This document presents a systematic failure mode analysis of the proposed inter-agent communication system comprising a JSONL append-only message bus (KB-0015) and a SQLite WAL shared state database (KB-0016). We analyzed 26 distinct failure modes across six categories: race conditions, crash recovery, resource exhaustion, split-brain/consistency, stale state, and environmental factors.

**Overall assessment: CONDITIONAL GO for prototype.** The research in KB-0015 and KB-0016 already addresses the majority of failure modes with sound mitigations. However, three critical gaps must be resolved before production deployment: (1) the TOCTOU race in rate-limit checking, (2) the git worktree split-brain problem, and (3) the absence of a coordinator watchdog/self-healing mechanism. The remaining risks are low-to-medium severity and manageable with the proposed mitigations.

## Detailed Analysis

### 1. Race Conditions

#### RC-1: JSONL Interleaved Bytes from Concurrent Writers

**Scenario:** Two agents call `os.write()` simultaneously on the same JSONL file. If the message exceeds the atomic write limit, bytes from both messages could interleave, producing two corrupt lines instead of two valid ones.

**Likelihood: Low.** KB-0015 specifies keeping messages under 4096 bytes and using raw `os.write()` with `O_APPEND`. On Linux ext4/xfs, the kernel holds an inode mutex during the entire write() syscall, providing atomicity well beyond 4096 bytes in practice (observed up to 1 MB). The 4096-byte limit provides a conservative safety margin.

**Severity: High.** Interleaved bytes would corrupt two messages simultaneously, and the corruption would be silent (readers would simply skip the malformed lines via try/except on json.loads).

**Mitigated by research: Yes.** KB-0015 Section 1.4 establishes the 4096-byte rule; Section 4.1 details the scenarios; Section 1.5 provides correct Python code using `os.open()` + `os.write()`.

**Residual risk:** An agent developer using Python's buffered `open("a")` + `f.write()` instead of the prescribed `os.write()` pattern. The API wrapper should enforce the correct write path and reject messages over the size limit.

#### RC-2: SQLite SQLITE_BUSY Under Heavy Write Contention

**Scenario:** Many agents attempt writes simultaneously. SQLite serializes all writes; contending agents receive SQLITE_BUSY. If all agents retry at the same interval, a thundering-herd effect can cause cascading failures where retries themselves cause further contention.

**Likelihood: Medium.** With 5-15 agents doing infrequent writes (heartbeats every 30s, rate-limit checks per API call), contention should be rare. However, burst scenarios are possible (e.g., all agents hitting a rate limit simultaneously and writing blocker records).

**Severity: Medium.** Writes are delayed but not lost. The 30-second busy_timeout provides substantial headroom. The worst case is a heartbeat arriving late, which could trigger false-positive stale-agent detection.

**Mitigated by research: Yes.** KB-0016 Section 3.3 specifies exponential backoff with jitter and deadline-based timeouts. Section 3.2 mandates BEGIN IMMEDIATE to ensure busy_timeout is respected.

**Residual risk:** If an agent holds a long write transaction (e.g., bulk inserting rate-limit records), all other writers block. Mitigation: keep write transactions minimal — single INSERT statements, commit immediately.

#### RC-3: Reader Sees Partial JSONL Line Mid-Write

**Scenario:** A reader calls `read()` at the exact moment a writer is mid-`write()`. The reader could see an incomplete JSON line at the end of the file.

**Likelihood: Low.** On local Linux filesystems with `O_APPEND` and writes under the inode mutex, the read() will see either the complete write or not see it at all. This is only a real concern with buffered I/O or network filesystems.

**Severity: Medium.** A partial line would fail JSON parsing. If the reader updates its file position past the partial data, the remainder of the message (completed by a subsequent syscall) would also be unparsable.

**Mitigated by research: Yes.** KB-0015 Section 2.3 (`JSONLTail.poll_once()`) only processes data up to the last `\n` character, buffering any trailing partial content for the next poll cycle. Section 4.2 explicitly addresses this scenario.

#### RC-4: TOCTOU in Rate-Limit Check-Then-Increment

**Scenario:** Agent A calls `check_rate_limit("api.example.com")` which reads the count as 9 (limit is 10). Agent B simultaneously calls the same check and also reads 9. Both agents proceed to make an API call and both call `record_api_call()`. The actual count is now 11, exceeding the limit.

**Likelihood: High.** This is a classic time-of-check-to-time-of-use (TOCTOU) race. The current KB-0016 implementation (Section 7.3) performs the check as a read-only query and the increment as a separate write — these are not in the same transaction. With multiple agents hitting the same API, this race is virtually guaranteed to occur.

**Severity: High.** Exceeding API rate limits triggers 429 responses, potential API key bans, and cooldown periods that affect all agents. This directly undermines one of the primary use cases for the shared state system.

**Mitigated by research: No.** KB-0016 Section 7.3 shows `check_rate_limit()` as a standalone read and `record_api_call()` as a standalone write. There is no atomic check-and-reserve operation.

**Recommended fix:** Combine check and increment into a single `BEGIN IMMEDIATE` transaction:

```python
def reserve_api_call(self, api_endpoint):
    """Atomically check rate limit AND reserve a slot. Returns True if allowed."""
    conn = self._get_conn()
    try:
        conn.execute("BEGIN IMMEDIATE")
        config = conn.execute("""
            SELECT max_calls, window_seconds, cooldown_until
            FROM rate_limit_config WHERE api_endpoint = ?
        """, (api_endpoint,)).fetchone()

        if config is None:
            conn.execute("COMMIT")
            return True

        if config["cooldown_until"]:
            in_cooldown = conn.execute(
                "SELECT datetime('now') < ? AS cd", (config["cooldown_until"],)
            ).fetchone()["cd"]
            if in_cooldown:
                conn.execute("COMMIT")
                return False

        count = conn.execute("""
            SELECT COUNT(*) as cnt FROM rate_limits
            WHERE api_endpoint = ? AND called_at > datetime('now', ? || ' seconds')
        """, (api_endpoint, -config["window_seconds"])).fetchone()["cnt"]

        if count >= config["max_calls"]:
            conn.execute("COMMIT")
            return False

        conn.execute("""
            INSERT INTO rate_limits (api_endpoint, agent_id, called_at)
            VALUES (?, ?, datetime('now'))
        """, (api_endpoint, self.agent_id))
        conn.execute("COMMIT")
        return True
    except Exception:
        conn.execute("ROLLBACK")
        raise
```

This ensures the check and the insert are inside the same IMMEDIATE transaction, preventing any other agent from reading a stale count between the check and the increment.

### 2. Crash Recovery

#### CR-1: Agent Crashes Mid-Write to JSONL

**Scenario:** An agent is killed (SIGKILL) or crashes during an `os.write()` call. The JSONL file may contain a partial JSON line at the end.

**Likelihood: Low.** On local Linux filesystems, a `write()` syscall that has entered the kernel is atomic at the filesystem level — it either completes fully or does not happen. The risk is primarily from application-level buffering (which is avoided by using raw `os.write()`). Process crashes between buffering and writing are the main concern.

**Severity: Medium.** A corrupt last line causes that one message to be lost. It does not affect prior messages. Readers will skip it via JSON parse error handling.

**Mitigated by research: Yes.** KB-0015 Section 3.3 provides a `repair_bus_file()` function that truncates trailing partial lines. Readers already skip corrupt lines in `poll_once()`.

#### CR-2: Agent Crashes Mid-SQLite Transaction

**Scenario:** An agent process dies (SIGKILL, OOM kill) while in the middle of a SQLite write transaction. The WAL file contains incomplete frames.

**Likelihood: Low.** SQLite transactions are typically very short (sub-millisecond for single INSERTs). The window for a crash during a transaction is tiny.

**Severity: Low.** SQLite's WAL contains checksums on every frame. On the next connection to the database, WAL recovery runs automatically: valid committed frames are replayed; partial/corrupt frames are discarded. The database self-heals with no manual intervention and no data corruption. Only uncommitted data from the crashed transaction is lost.

**Mitigated by research: Yes.** KB-0016 Section 6.1 documents this behavior explicitly.

#### CR-3: Coordinator Crashes — Orphaned Sub-Teams

**Scenario:** The coordinator agent crashes or is killed. Sub-team agents continue working but have no one polling for their heartbeats, phase signals, or blocker reports. No one performs data cleanup, file rotation, or stale-agent reaping. Sub-teams may complete their work but have no one to collect results or coordinate the next phase.

**Likelihood: Medium.** Coordinators are long-running processes subject to the same crash risks as any other agent (OOM, context limit, user intervention). KB-0009 documents the coordinator pattern but does not address coordinator failure.

**Severity: Critical.** Without a coordinator: (1) dead agents are never detected; (2) phases never advance; (3) blockers are never escalated; (4) data cleanup stops, leading to resource exhaustion (RE-1, RE-2); (5) the overall operation stalls indefinitely.

**Mitigated by research: No.** Neither KB-0015 nor KB-0016 addresses coordinator failure. KB-0009 describes the coordinator pattern but assumes it remains alive.

**Recommended fix:** Implement a coordinator watchdog:
1. **Coordinator heartbeat:** The coordinator writes its own heartbeat to the SQLite database.
2. **Sub-team self-monitoring:** Each sub-team checks the coordinator's heartbeat. If stale beyond a threshold (e.g., 5 minutes), sub-teams enter a degraded mode: save current work, write results to known locations, and exit gracefully.
3. **External watchdog (optional):** A lightweight shell script or cron job checks the coordinator's PID and heartbeat, restarting it if necessary.
4. **Stateless coordinator restart:** Design the coordinator to reconstruct its state from the SQLite database on startup — all agent registrations, phase signals, and blockers are already persisted.

#### CR-4: Heartbeat Monitor Itself Dies

**Scenario:** The process responsible for monitoring heartbeats and detecting dead agents (typically the coordinator) crashes. Dead agents go undetected. Their stale state persists in the database, potentially causing incorrect decisions (e.g., waiting for a phase completion signal from a dead agent).

**Likelihood: Medium.** Same crash risks as CR-3.

**Severity: High.** Without heartbeat monitoring, the system loses its ability to self-heal. Dead agents appear active. Phase gates that wait for all agents to signal completion will wait forever.

**Mitigated by research: No.** The heartbeat check function exists (KB-0016 Section 7.6, KB-0015 Section 6.5), but there is no mechanism to ensure the monitor itself stays alive.

**Recommended fix:** (1) Distribute heartbeat checking — every agent periodically checks the coordinator's heartbeat. (2) Use process-level liveness checks (`os.kill(pid, 0)` on the PID stored in the agents table) as a secondary signal. (3) Consider a "buddy system" where pairs of agents monitor each other.

### 3. Resource Exhaustion

#### RE-1: JSONL Files Growing Unbounded — Disk Full

**Scenario:** In a long-running operation, JSONL bus files accumulate messages indefinitely. With 10 agents sending heartbeats every 30 seconds plus info/phase messages, the global channel could grow by approximately 50-100 KB per hour (200-byte heartbeats). Over 24 hours: ~1-2 MB. With verbose message bodies and many channels: potentially tens of MB. If no cleanup runs and operations span days, disk space could be exhausted.

**Likelihood: Medium.** The growth rate is modest for short operations, but without enforced rotation, long-running or repeated operations will accumulate files.

**Severity: High.** Disk full causes all writes (JSONL and SQLite) to fail simultaneously, crashing the entire system. Recovery requires manual cleanup.

**Mitigated by research: Partial.** KB-0015 Section 3.4 describes epoch-based file rotation and size-based rotation strategies. However, these are presented as options, not mandatory components. No automatic cleanup is specified.

**Recommended fix:** Make rotation mandatory in the prototype. Use epoch-based files (hourly windows) with automatic deletion of files older than the retention period (e.g., 2 hours). The coordinator should run cleanup on startup and periodically.

#### RE-2: SQLite WAL File Growing During Long-Running Reads

**Scenario:** An agent opens a read transaction (even implicitly via a SELECT) and holds the connection open for a long time. While the read is held, checkpointing cannot advance past the reader's snapshot. New writes accumulate in the WAL file without being transferred to the main database. The WAL can grow to hundreds of MB or more.

**Likelihood: Low.** The proposed patterns use short-lived connections or short read transactions. The risk is from a bug where a connection is held open (e.g., iterating a large result set slowly, or a leaked connection from an exception).

**Severity: Medium.** A large WAL degrades read performance (readers must scan the WAL index) and consumes disk space. It does not cause data loss. The WAL is cleaned up once the long-running reader closes its connection.

**Mitigated by research: Yes.** KB-0016 Section 8 warns about this. Auto-checkpoint at 1000 pages is enabled by default. The context-manager pattern (`get_db()`) ensures connections are closed promptly.

**Residual risk:** If an agent crashes with an open read transaction, the WAL grows until the OS reclaims the file descriptors. On Linux, this happens when the process terminates (even via SIGKILL), so the window is bounded by the crash detection time.

#### RE-3: Too Many Agents Polling Same File — I/O Contention

**Scenario:** 50 agents all polling the global JSONL channel at 100ms intervals. Each poll issues a `stat()` + `open()` + `seek()` + `read()` + `close()`. That is 500 file operations per second on a single file.

**Likelihood: Low.** For the proposed scale (5-15 agents, 200ms polling), this is negligible. Even at 50 agents, the kernel page cache means the actual disk I/O is near zero — all reads hit cached pages.

**Severity: Low.** Slightly increased CPU from syscall overhead, but no functional impact.

**Mitigated by research: Yes.** KB-0015 Section 5.1 benchmarks throughput well in excess of what is needed. Section 5.3 notes that frequent small operations are coalesced by the page cache.

#### RE-4: File Descriptor Limits with Many Channel Files

**Scenario:** Each agent subscribes to N channels. If the `BusReader` keeps file handles open for each channel, and each agent also has connections for SQLite, logging, and other I/O, the per-process file descriptor limit (typically 1024 by default on Linux) could be approached.

**Likelihood: Low.** With a typical setup of 5-10 channels per agent, fd usage is modest. The proposed `poll_once()` implementation opens and closes files per poll cycle.

**Severity: Medium.** Exceeding fd limits causes `OSError: [Errno 24] Too many open files`, which would crash the polling loop.

**Mitigated by research: Partial.** The `BusReader.poll()` implementation in KB-0015 opens/closes files per poll, which is safe but slightly less efficient. The `BusWriter` opens/closes per write, which is also safe.

**Recommended fix:** Document the fd budget. With epoch-based files and many channels, a single agent might have: 1 SQLite connection (3 fds: .db, .wal, .shm) + N channel fds per poll cycle. Keep N under 100 and this is a non-issue. Alternatively, raise `ulimit -n` on the system.

### 4. Split-Brain / Consistency

#### SB-1: Git Worktrees Have Separate JSONL/SQLite Copies

**Scenario:** Each agent team works in a separate git worktree (e.g., `/home/user/Claude-worktree-01/`, `/home/user/Claude-worktree-02/`). If the JSONL bus files and SQLite database are stored inside the git repository (e.g., `bus/global.jsonl`, `coordination.db`), each worktree has its own independent copy. Agents in worktree-01 write to `/home/user/Claude-worktree-01/bus/global.jsonl`; agents in worktree-02 write to `/home/user/Claude-worktree-02/bus/global.jsonl`. These are completely separate files — no inter-worktree communication occurs.

**Likelihood: High.** Git worktrees are the recommended mechanism for running multiple agent teams (KB-0009). If the prototype places communication files inside the repo without explicit guidance to the contrary, this failure is virtually guaranteed.

**Severity: Critical.** This is not a degraded mode — it is a total failure of the communication system. Agents believe they are communicating but are talking to themselves. Rate limits are not shared. Heartbeats are invisible to the coordinator. Phase signals are never received.

**Mitigated by research: No.** Neither KB-0015 nor KB-0016 mentions git worktrees or addresses file placement relative to worktree boundaries. KB-0009 documents the worktree-based team structure but does not discuss shared file placement.

**Recommended fix:** Place all communication files in a location outside any git worktree. Options:
1. **Shared parent directory:** `/home/user/Claude/.agent-comm/` (the main repo root, not a worktree). All worktrees are children of this directory structure.
2. **XDG-compliant path:** `$XDG_RUNTIME_DIR/claude-agents/` (e.g., `/run/user/1000/claude-agents/`). This is a tmpfs, so it is fast but volatile across reboots — acceptable for ephemeral coordination data.
3. **Explicit absolute path:** Set via environment variable `AGENT_COMM_DIR=/home/user/.claude-agent-comm`. All agents read this env var to locate the bus and database.

Option 3 is the most robust. The prototype must resolve and validate this path at startup, and all agents must use the exact same canonical path (see EN-5).

#### SB-2: Agents in Different Worktrees Cannot See Each Other's Messages

**Scenario:** Direct consequence of SB-1. Even if agents are "correctly" using the JSONL bus and SQLite coordination, they are operating in isolated universes if files are worktree-local.

**Likelihood: High.** Same as SB-1.

**Severity: Critical.** Same as SB-1.

**Mitigated by research: No.** Same as SB-1.

**Recommended fix:** Same as SB-1. This is the same root cause.

#### SB-3: Clock Skew Between Agents (Timestamp-Based Ordering)

**Scenario:** JSONL messages use `time.time()` for timestamps. If agents run on different machines (unlikely in current setup) or if the system clock is adjusted (NTP correction, manual change), timestamp-based ordering of messages could be incorrect.

**Likelihood: Low.** All agents run on the same machine. `time.time()` reads the same system clock. NTP adjustments are typically sub-millisecond and do not affect ordering at the granularity agents operate (100ms+ polling intervals).

**Severity: Low.** Message ordering is approximate anyway (KB-0015 Section 7 acknowledges no ordering guarantee across channels). Within a single JSONL file, messages are ordered by append position, which is correct regardless of timestamps.

**Mitigated by research: Partial.** KB-0015 uses timestamps for approximate ordering. KB-0016 uses autoincrement IDs for message ordering, which provides strict ordering within the SQLite messages table regardless of clock issues.

**Recommended fix:** For critical ordering, use SQLite autoincrement IDs (already in KB-0016 schema). For JSONL, append order is the ground truth; timestamps are metadata only.

#### SB-4: No Global Message Ordering Across Channels

**Scenario:** Agent A posts to channel `topic-build` at timestamp T. Agent B posts to channel `global` at timestamp T+1ms. A reader polling both channels may process the `global` message before the `topic-build` message, depending on polling order.

**Likelihood: Medium.** This will happen routinely with multiple channels.

**Severity: Low.** For the proposed use cases (heartbeats, phase signals, blockers), strict global ordering is not required. Each message type is independently meaningful.

**Mitigated by research: Yes.** KB-0015 Section 7 explicitly acknowledges this: "No ordering guarantee across channels." The recommendation to use a single channel for strict ordering is provided.

### 5. Stale State

#### SS-1: Dead Agent's Heartbeat Never Cleared

**Scenario:** An agent crashes without calling `close()` (which sets status to 'terminated'). Its last heartbeat remains in the database with status='active'. Without the coordinator running the stale-agent check, this agent appears permanently active.

**Likelihood: Medium.** Crashes without cleanup are common (SIGKILL, OOM kill, uncaught exceptions that bypass finally blocks).

**Severity: Medium.** False-active agents could cause: (1) phase gates waiting for their completion signal indefinitely; (2) overestimation of active agent count; (3) messages sent to the dead agent's channel that are never read.

**Mitigated by research: Partial.** KB-0016 Section 7.6 (`get_system_status()`) queries for stale agents (no heartbeat in 120 seconds). KB-0015 Section 6.5 provides `check_agent_health()`. However, there is no automatic reaping — these are query functions, not cleanup routines.

**Recommended fix:** Add an automatic reaping function to the coordinator:
```python
def reap_dead_agents(self, timeout=300):
    """Mark agents with stale heartbeats as terminated."""
    conn = self._get_conn()
    conn.execute("""
        UPDATE agents SET status = 'terminated'
        WHERE status = 'active'
          AND last_heartbeat < datetime('now', ? || ' seconds')
    """, (-timeout,))
    conn.commit()
```
Run this every 60 seconds in the coordinator's poll loop.

#### SS-2: Blocker Posted But Not Read Before Action Taken

**Scenario:** Agent A posts a blocker message ("API rate limit hit for api.example.com"). Agent B, which has not yet polled, proceeds to call the same API and also gets rate-limited. The blocker message exists in the bus/database, but the polling interval means there is always a window where agents act on stale information.

**Likelihood: Medium.** With 200ms polling intervals, there is a 0-200ms window where an agent may not have received the latest blocker. For rate-limit scenarios where multiple agents hit the same endpoint in rapid succession, this window is significant.

**Severity: Medium.** Redundant API failures, additional rate-limit penalties, wasted time.

**Mitigated by research: No.** Neither KB-0015 nor KB-0016 addresses this scenario explicitly. The rate-limit checking in KB-0016 mitigates the specific case of API rate limits (by checking the shared counter before calling), but the general "blocker not yet propagated" problem is inherent to any polling-based system.

**Recommended fix:** For rate limits specifically, the atomic check-and-reserve fix (RC-4) eliminates this window. For general blockers, accept the polling-interval latency as inherent to the design. If sub-second propagation is critical, consider adding a Unix socket notification sidecar (mentioned in KB-0016 Section 8) to trigger immediate re-polls.

#### SS-3: Rate-Limit Counter Not Decremented After Window Expires

**Scenario:** The rate-limit tracking counts API calls within a time window. If old records are never deleted, the rate_limits table grows indefinitely, and COUNT queries become slower.

**Likelihood: Low.** The count query uses a time-windowed WHERE clause (`called_at > datetime('now', '-N seconds')`), so old records do not affect the count. The concern is purely about storage growth and query performance.

**Severity: Low.** Even without cleanup, the indexed query remains fast for thousands of records. The data retention SQL in KB-0016 Section 4.3 handles this.

**Mitigated by research: Yes.** KB-0016 Section 4.3 provides cleanup SQL to delete rate_limits records older than the max window.

#### SS-4: Old Messages Accumulating, Slowing Down Polling

**Scenario:** In the SQLite messages table, old messages accumulate. An agent that starts fresh (since_id=0) must scan through all historical messages. Even with the `(channel, id)` index, initial catchup could involve thousands of rows.

**Likelihood: Medium.** Over hours of operation, the messages table could grow to thousands or tens of thousands of rows. New agents joining late or agents restarting would replay all of them.

**Severity: Medium.** Slow initial poll, increased memory usage during catchup, wasted processing of expired/irrelevant messages.

**Mitigated by research: Partial.** KB-0016 Section 4.3 provides retention SQL, and messages have an `expires_at` column. However, there is no automatic cleanup loop, and the poll query already filters by `expires_at`. The residual risk is the table scan for cleanup and the initial catchup for new agents.

**Recommended fix:** (1) New agents should start with `since_id = MAX(id) - buffer` rather than 0. (2) Run periodic cleanup to DELETE expired messages. (3) Add `LIMIT` to initial catchup queries (already in KB-0016 Section 7.5).

### 6. Environmental

#### EN-1: File Permissions Preventing Agent Writes

**Scenario:** The JSONL bus directory or SQLite database file is created with restrictive permissions (e.g., 0600 owned by a different user). Other agent processes running as the same or different user cannot write.

**Likelihood: Low.** In the typical setup, all agents run as the same OS user. The `BusWriter` creates files with mode 0o644. However, if the bus directory is created by root or with umask 077, agents may fail.

**Severity: High.** Total communication failure for affected agents. Writes raise `PermissionError`.

**Mitigated by research: No.** Neither KB-0015 nor KB-0016 addresses file permissions or initialization scripts.

**Recommended fix:** The initialization script should create the bus directory and database file with appropriate permissions, verify write access, and fail fast with a clear error message if permissions are wrong.

#### EN-2: Disk I/O Latency Spikes Causing Timeouts

**Scenario:** A disk I/O spike (e.g., from a large git operation, system backup, or another process doing heavy writes) delays SQLite writes or JSONL appends. If the delay exceeds the busy_timeout, SQLite writes fail.

**Likelihood: Low.** SSDs have consistent low-latency I/O. The 30-second busy_timeout in KB-0016 provides substantial headroom. JSONL appends do not have timeouts — `os.write()` blocks until complete, which on local filesystems should be sub-millisecond.

**Severity: Medium.** Failed SQLite writes would need retry. Slow JSONL appends would delay message delivery.

**Mitigated by research: Partial.** The 30-second busy_timeout and retry logic in KB-0016 Section 3.3 handle transient delays. However, there is no monitoring or alerting for I/O latency.

#### EN-3: Python GIL Impact on Multi-Threaded Polling

**Scenario:** An agent uses a background thread for the polling loop (as shown in KB-0015 `BusReader.run_in_background()` and KB-0016 `AgentPoller`). The GIL might prevent the polling thread from running while the main thread is doing CPU-intensive work.

**Likelihood: Low.** The GIL is released during I/O operations (`read()`, `write()`, SQLite queries). The polling thread spends most of its time in I/O or sleeping, both of which release the GIL. More importantly, each agent is a separate OS process, so the GIL is per-process and does not affect inter-agent concurrency.

**Severity: Low.** Even in the worst case, the polling thread would be delayed by one GIL acquisition cycle (typically <10ms), adding marginal latency to message delivery.

**Mitigated by research: N/A.** This is a non-issue in practice. Agents are separate processes; the GIL is irrelevant to inter-process communication.

#### EN-4: Communication Files on /tmp — Cleaned Up

**Scenario:** An implementer places the bus directory or SQLite database on `/tmp` for performance (tmpfs). A system cleanup process (systemd-tmpfiles, tmpreaper, or a manual `rm -rf /tmp/*`) deletes the files while agents are running.

**Likelihood: Low.** This requires an explicit bad decision by the implementer, or a system administrator cleaning /tmp.

**Severity: Critical.** All communication state is lost. Running agents would get `FileNotFoundError` on next poll/write. The SQLite database would be irrecoverably lost (though agents could reconstruct state via heartbeats on restart).

**Mitigated by research: No.** Neither KB-0015 nor KB-0016 specifies where files should be stored. The example code uses placeholder paths.

**Recommended fix:** Explicitly document: never use /tmp. Use a project-local directory (e.g., `$AGENT_COMM_DIR` or `~/.claude-agent-comm/`). Verify the directory exists on startup.

#### EN-5: SQLite Opened Via Different Filesystem Paths

**Scenario:** Two processes open the same SQLite database via different filesystem paths (e.g., one uses `/home/user/Claude/coordination.db`, another uses `/home/user/Claude/../Claude/coordination.db`, or one follows a symlink). SQLite uses the path string for lock identification. Different paths = different lock namespaces = concurrent write access without mutual exclusion = database corruption.

**Likelihood: Low.** Requires a configuration error where different agents use differently-constructed paths to the same file.

**Severity: Critical.** Silent database corruption. No error is raised; writes simply interleave without locking.

**Mitigated by research: Yes.** KB-0016 Section 6.3 (item 4) and Section 8 both warn about this. The recommendation is to use the same filesystem path for all processes.

**Recommended fix:** Canonicalize the database path at startup using `os.path.realpath()`. Store the canonical path in an environment variable or configuration file that all agents read.

#### EN-6: .db-wal and .db-shm Files Deleted While Database In Use

**Scenario:** A user or cleanup script deletes the WAL or SHM files while agents have the database open. The SHM file manages reader/writer coordination; the WAL file contains uncommitted data.

**Likelihood: Low.** Requires deliberate (if uninformed) action.

**Severity: Critical.** Deleting the WAL while in use causes data loss (uncommitted transactions). Deleting the SHM causes coordination failure between readers and writers, potentially leading to corruption.

**Mitigated by research: Yes.** KB-0016 Section 8 warns: "The -shm and -wal files must not be deleted while the database is in use."

**Recommended fix:** Document this clearly. Consider placing the database in a directory with a `DO_NOT_DELETE.txt` marker file.

## Critical Findings

The following five risks **must** be addressed before moving from prototype to production:

### 1. TOCTOU Race in Rate-Limit Checking (RC-4) — MUST FIX

The current `check_rate_limit()` + `record_api_call()` pattern is fundamentally broken for concurrent agents. Two agents can simultaneously read the count as below-limit and both proceed, exceeding the limit. The fix is straightforward: combine check and insert into a single `BEGIN IMMEDIATE` transaction. This is a required change to the KB-0016 API.

### 2. Git Worktree Split-Brain (SB-1, SB-2) — MUST FIX

This is the single most dangerous failure mode because it is silent and catastrophic. If communication files are placed inside git worktrees, the entire communication system fails without any error message. Agents believe they are communicating but are operating in isolation. The fix requires a design decision about where to place shared files — outside all worktrees, at a canonical absolute path.

### 3. Coordinator Single Point of Failure (CR-3, CR-4) — MUST FIX

The coordinator is a single point of failure with no watchdog, no self-healing, and no graceful degradation. If it crashes, the entire multi-team operation stalls. The fix requires: (a) coordinator heartbeating itself; (b) sub-teams checking coordinator liveness; (c) stateless coordinator restart capability; (d) optional external watchdog.

### 4. No Enforced Data Cleanup (RE-1, SS-4) — SHOULD FIX

Data retention is described but not enforced. Without automatic cleanup, JSONL files and SQLite tables grow unbounded. For short operations this is benign; for operations spanning hours or days, it causes performance degradation and eventually disk exhaustion.

### 5. Startup Validation Missing (EN-1, EN-4, EN-5) — SHOULD FIX

There is no startup validation to catch configuration errors early: wrong file permissions, files on /tmp, non-canonical paths, missing directories. A startup check routine that validates the communication environment would catch these issues before they cause silent failures.

## Recommendation

**CONDITIONAL GO for prototype**, with three mandatory conditions:

1. **Fix the TOCTOU rate-limit race (RC-4)** before any multi-agent testing involving shared API access. This is a one-function change that is critical for correctness.

2. **Establish a shared communication directory outside git worktrees (SB-1)** as a foundational design decision. All code examples, initialization scripts, and documentation must reference an absolute path that all agents share. Suggested: environment variable `AGENT_COMM_DIR` defaulting to `~/.claude-agent-comm/`.

3. **Implement basic coordinator resilience (CR-3)** before any multi-team operation. At minimum: coordinator heartbeats itself, sub-teams detect coordinator death within 5 minutes, sub-teams save work and exit gracefully.

Two additional improvements are strongly recommended for any operation lasting more than 1 hour:

4. **Enforce automatic data cleanup** (epoch-based JSONL rotation with deletion, periodic SQLite message/rate-limit purge).

5. **Add startup validation** (directory exists, permissions correct, path is canonical, not on /tmp or NFS).

With these conditions met, the JSONL + SQLite architecture is sound for the proposed scale (5-15 agent teams on a single machine) and should proceed to prototype.
