# Building MCP Servers with FastMCP (Python) for Claude Code

## Context
Research into building MCP (Model Context Protocol) servers using FastMCP in Python to connect Claude Code to local FastAPI services. Covers installation, code patterns, configuration, error handling, streaming, type annotations, testing, common pitfalls, complex parameters, performance, and proxying to local AI services.

---

## 1. Installation: `pip install fastmcp` vs `pip install mcp`

There are **two separate PyPI packages**:

| Package | Install | Import | Version (Mar 2026) | Maintainer |
|---------|---------|--------|---------------------|------------|
| `fastmcp` | `pip install fastmcp` | `from fastmcp import FastMCP` | 3.1.0 | PrefectHQ (Jared Lowin) |
| `mcp` | `pip install mcp` | `from mcp.server.fastmcp import FastMCP` | 1.26.0 | Anthropic |

**Use `pip install fastmcp`** (the standalone v3.x package) for new projects. It is actively maintained, has far more features, and is downloaded ~1M times/day. The `mcp` package bundles an older FastMCP v1.x internally.

```bash
# Recommended
pip install fastmcp

# Verify
fastmcp version

# With optional extras
pip install "fastmcp[tasks]"

# Or with uv
uv add fastmcp
```

Requires Python >= 3.10.

## 2. Stdio MCP Server That Proxies to a FastAPI Backend

### Approach A: Manual proxy — MCP tool calls httpx to hit FastAPI

This is the simplest and most reliable pattern. Your MCP server is a thin shim that forwards calls.

```python
#!/usr/bin/env python3
"""mcp_proxy_server.py — stdio MCP server proxying to a local FastAPI service."""

import httpx
from fastmcp import FastMCP
from fastmcp.exceptions import ToolError

mcp = FastMCP(name="FastAPIProxy")

BACKEND = "http://127.0.0.1:8000"

@mcp.tool
async def search_items(query: str, limit: int = 10) -> list[dict]:
    """Search items in the backend database."""
    async with httpx.AsyncClient() as client:
        try:
            resp = await client.get(
                f"{BACKEND}/api/search",
                params={"q": query, "limit": limit},
                timeout=30.0,
            )
            resp.raise_for_status()
            return resp.json()
        except httpx.HTTPStatusError as e:
            raise ToolError(f"Backend returned {e.response.status_code}: {e.response.text}")
        except httpx.ConnectError:
            raise ToolError(f"Cannot connect to backend at {BACKEND}. Is it running?")

@mcp.tool
async def create_item(name: str, description: str, tags: list[str] = None) -> dict:
    """Create a new item in the backend."""
    async with httpx.AsyncClient() as client:
        try:
            resp = await client.post(
                f"{BACKEND}/api/items",
                json={"name": name, "description": description, "tags": tags or []},
                timeout=30.0,
            )
            resp.raise_for_status()
            return resp.json()
        except httpx.HTTPStatusError as e:
            raise ToolError(f"Create failed: {e.response.status_code}: {e.response.text}")

@mcp.tool
async def get_health() -> dict:
    """Check backend health status."""
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"{BACKEND}/health", timeout=5.0)
        return resp.json()

if __name__ == "__main__":
    mcp.run()  # stdio transport by default
```

### Approach B: Auto-generate MCP from FastAPI OpenAPI spec (FastMCP 3.0+)

```python
from fastapi import FastAPI
from fastmcp import FastMCP

# Your existing FastAPI app
app = FastAPI()

@app.get("/api/search")
async def search(q: str, limit: int = 10):
    return [{"id": 1, "name": "Example", "query": q}]

# Convert to MCP server — uses OpenAPIProvider under the hood
mcp = FastMCP.from_fastapi(app=app, name="MyAPI-MCP")

if __name__ == "__main__":
    mcp.run()  # stdio
```

**Note:** The auto-generated approach works but hand-curated MCP tools typically outperform auto-converted ones because you can optimize descriptions and parameter names for LLM consumption.

### Approach C: Use `mcp-proxy` to bridge stdio to a remote HTTP MCP server

If your FastAPI app already serves an MCP endpoint (via `mcp.streamable_http_app()`):

```json
{
  "mcpServers": {
    "my-api": {
      "command": "mcp-proxy",
      "args": ["http://127.0.0.1:8000/mcp"]
    }
  }
}
```

## 3. Claude Code MCP Discovery: `.mcp.json` Format

### File format

```json
{
  "mcpServers": {
    "my-server": {
      "command": "/path/to/python",
      "args": ["/absolute/path/to/mcp_proxy_server.py"],
      "env": {
        "BACKEND_URL": "http://127.0.0.1:8000"
      }
    }
  }
}
```

**All paths must be absolute.** Relative paths will fail.

### Where the file goes — three scopes

| Scope | Location | Shared? |
|-------|----------|---------|
| Project | `.mcp.json` in project root | Yes, commit to git |
| Local | `.claude/.mcp.json` (gitignored) | No, your machine only |
| User | `~/.claude.json` | No, all your projects |

**Known issue:** `.claude/.mcp.json` sometimes fails to load. Workaround: place `.mcp.json` in the project root.

### CLI management

```bash
# Add a server
claude mcp add my-server -- python /abs/path/to/mcp_proxy_server.py

# Add with scope
claude mcp add my-server --scope user -- python /abs/path/to/server.py

# Add with env vars
claude mcp add my-server -e BACKEND_URL=http://localhost:8000 -- python /abs/path/to/server.py

# List configured servers
claude mcp list

# Remove
claude mcp remove my-server

# Use an env file
claude mcp add my-server --env-file .env -- python /abs/path/to/server.py
```

### Using with uv/fastmcp CLI (recommended for dependency management)

```json
{
  "mcpServers": {
    "my-server": {
      "command": "fastmcp",
      "args": ["run", "/abs/path/to/server.py", "--with", "httpx"]
    }
  }
}
```

## 4. Error Handling in MCP Tools

### Use `ToolError` for client-visible errors

```python
from fastmcp.exceptions import ToolError

@mcp.tool
def divide(a: float, b: float) -> float:
    """Divide a by b."""
    if b == 0:
        raise ToolError("Division by zero is not allowed.")
    return a / b
```

When `ToolError` is raised, the MCP response has `isError: true` and the message is sent to the LLM. The LLM can then try a corrected request.

### Two categories of errors

1. **Protocol errors** (invalid JSON-RPC, nonexistent tool) — handled automatically by the SDK with standard JSON-RPC error codes.
2. **Tool execution errors** — return a successful JSON-RPC response with `isError` flag. This is what `ToolError` produces.

### Masking internal errors

```python
mcp = FastMCP(name="MyServer", mask_error_details=True)
```

With `mask_error_details=True`:
- `ToolError` messages pass through to the client (intentional, client-visible errors)
- Unexpected exceptions are masked — no stack traces or credentials leak

### Middleware for error handling (FastMCP 2.9+)

```python
from fastmcp.server.middleware.error_handling import ErrorHandlingMiddleware

mcp = FastMCP(name="MyServer")
mcp.add_middleware(ErrorHandlingMiddleware())
```

## 5. Streaming Responses

### Current state (March 2026)

**True streaming of intermediate tool results is NOT supported by the MCP protocol spec.** Tools return all results at once.

What IS supported:

- **Progress reporting** via `Context`:

```python
from fastmcp import FastMCP, Context

@mcp.tool
async def long_task(query: str, ctx: Context) -> dict:
    """A long-running task with progress updates."""
    await ctx.report_progress(progress=0, total=100)
    # ... do work ...
    await ctx.report_progress(progress=50, total=100)
    # ... more work ...
    await ctx.report_progress(progress=100, total=100)
    return {"result": "done"}
```

- **Log messages** via Context:

```python
await ctx.info("Processing step 1...")
await ctx.warning("Rate limit approaching")
```

- **Streamable HTTP transport** supports server-to-client notifications during tool execution, but the final tool result is still returned as one complete response.

## 6. Type Annotations for Parameters and Return Values

FastMCP uses Pydantic's `TypeAdapter` to generate JSON Schema from Python type hints.

### Supported types

All types supported by Pydantic work: `int`, `float`, `str`, `bool`, `list`, `dict`, `Optional`, `Literal`, `Enum`, `datetime`, `UUID`, and any Pydantic `BaseModel`.

### Basic annotations

```python
@mcp.tool
def process(
    name: str,
    count: int,
    threshold: float = 0.5,
    tags: list[str] = None,
    options: dict[str, int] = None,
) -> dict:
    """Process with typed parameters."""
    return {"name": name, "count": count}
```

### Complex objects with Pydantic models

```python
from pydantic import BaseModel, Field

class SearchFilter(BaseModel):
    field: str = Field(description="Field to filter on")
    operator: str = Field(description="Comparison operator: eq, gt, lt, contains")
    value: str = Field(description="Value to compare against")

class SearchRequest(BaseModel):
    query: str = Field(description="Search query string")
    filters: list[SearchFilter] = Field(default=[], description="Optional filters")
    page: int = Field(default=1, ge=1)
    per_page: int = Field(default=20, ge=1, le=100)

@mcp.tool
def search(request: SearchRequest) -> dict:
    """Search with complex filters."""
    return {"query": request.query, "filter_count": len(request.filters)}
```

### Field descriptions become tool documentation

Use `Annotated` with `Field` for inline parameter documentation:

```python
from typing import Annotated
from pydantic import Field

@mcp.tool
def fetch_logs(
    service: Annotated[str, Field(description="Service name to fetch logs for")],
    lines: Annotated[int, Field(description="Number of log lines", ge=1, le=1000)] = 100,
) -> str:
    """Fetch recent logs from a service."""
    return f"Last {lines} lines from {service}"
```

### Known issue: Claude Code JSON string serialization

Claude Code sometimes serializes Pydantic model parameters as JSON strings instead of objects, causing validation failures. FastMCP's flexible validation (default) helps mitigate this by coercing compatible inputs.

### Restrictions

Functions with `*args` or `**kwargs` are NOT supported — FastMCP needs a complete parameter schema.

## 7. Testing MCP Servers Locally

### MCP Inspector (official GUI tool)

```bash
# Test a stdio server
npx @modelcontextprotocol/inspector python mcp_proxy_server.py

# Test an HTTP server
npx @modelcontextprotocol/inspector http://localhost:8000/mcp
```

Opens a browser UI where you can list tools, call them with arguments, and see responses. As of March 2025+, authentication is required by default (random session token).

### FastMCP dev mode with hot reload

```bash
# Auto-restart on code changes
fastmcp run server.py --reload

# Watch specific directories
fastmcp run server.py --reload --reload-dir ./src
```

### Programmatic testing with FastMCP Client

```python
import asyncio
from fastmcp import FastMCP, Client

mcp = FastMCP(name="TestServer")

@mcp.tool
def greet(name: str) -> str:
    return f"Hello, {name}!"

async def test():
    async with Client(mcp) as client:
        result = await client.call_tool("greet", {"name": "World"})
        print(result)  # Check result.content, result.is_error

asyncio.run(test())
```

### Unit testing individual tools with pytest

```python
import pytest

# Test the underlying function directly
def test_divide():
    assert divide(10, 2) == 5.0

def test_divide_by_zero():
    with pytest.raises(ToolError):
        divide(10, 0)
```

## 8. Common Pitfalls

### CRITICAL: stdout pollution breaks stdio servers

**The #1 cause of MCP server failures.** Stdio transport uses stdout for JSON-RPC messages. Any `print()` output corrupts the stream.

```python
# WRONG — breaks everything
print("Starting server...")  # This corrupts JSON-RPC on stdout

# RIGHT — use stderr
import sys
print("Starting server...", file=sys.stderr)

# RIGHT — use logging to stderr
import logging
logging.basicConfig(stream=sys.stderr, level=logging.DEBUG)
logger = logging.getLogger(__name__)
logger.info("Starting server...")

# RIGHT — use Context logging (goes through MCP protocol)
@mcp.tool
async def my_tool(query: str, ctx: Context) -> str:
    await ctx.info("Processing query...")  # Safe
    return "result"
```

**Also watch for:**
- Libraries that print startup banners (suppress them)
- Spinner/progress bar libraries (e.g., `rich`, `tqdm`) writing to stdout
- `warnings.warn()` — usually goes to stderr (safe), but verify

### Async vs sync

FastMCP supports both sync and async tool functions:

```python
# Both work fine
@mcp.tool
def sync_tool(x: int) -> int:
    return x * 2

@mcp.tool
async def async_tool(x: int) -> int:
    await asyncio.sleep(0.1)
    return x * 2
```

- Use **async** for I/O-bound operations (HTTP calls, file I/O, database queries)
- Use **sync** for CPU-bound or simple operations
- For CPU-bound work in async tools, use `asyncio.to_thread()` or thread/process pools
- FastMCP runs sync tools in a thread pool automatically

### Other pitfalls

- **Relative paths in `.mcp.json`** — always use absolute paths
- **Missing `if __name__ == "__main__": mcp.run()`** — server won't start
- **Forgetting `httpx` dependency** — add `--with httpx` in the config or `pip install httpx`
- **Timeout on slow backends** — set explicit timeouts in httpx calls

## 9. Complex Objects as Tool Parameters

### Lists of dicts

```python
@mcp.tool
def bulk_create(items: list[dict[str, str]]) -> dict:
    """Create multiple items at once.

    Args:
        items: List of items, each with 'name' and 'description' keys.
    """
    return {"created": len(items)}
```

### Nested Pydantic models (recommended for validation)

```python
from pydantic import BaseModel, Field

class Address(BaseModel):
    street: str
    city: str
    zip_code: str

class Contact(BaseModel):
    name: str
    email: str
    addresses: list[Address] = []
    metadata: dict[str, str] = {}

@mcp.tool
def register_contact(contact: Contact) -> dict:
    """Register a new contact with addresses."""
    return {
        "registered": contact.name,
        "address_count": len(contact.addresses),
    }
```

FastMCP automatically dereferences `$ref` entries in the generated JSON Schema so clients that don't support `$defs` references still work.

### Known issue with Claude Code

Claude Code may serialize complex Pydantic parameters as JSON strings rather than objects. FastMCP's default flexible validation coerces these, but if you hit issues, consider accepting `str` and parsing JSON manually as a fallback:

```python
import json

@mcp.tool
def flexible_create(data: str | dict) -> dict:
    """Create from JSON string or dict."""
    if isinstance(data, str):
        data = json.loads(data)
    return {"processed": True, "data": data}
```

## 10. Performance: Is stdio Fast Enough?

### For local Claude Code usage: yes

Stdio is fine for the Claude Code use case (single user, interactive, low concurrency). Claude Code sends one tool call at a time and waits for the response. The bottleneck is the LLM, not the transport.

### For production / high-concurrency: no

Benchmark data (Stacklok, 2025):
- Stdio failed at even modest concurrency: 2/50 requests succeeded
- Streamable HTTP: 290-300 req/s with shared sessions, 100% success rate
- Stdio has pipe buffer limitations that can cause **silent data loss** with large payloads

### Practical limits for large results

Returning 100 search results as JSON through stdio works fine for single requests. The JSON is serialized, sent through the pipe, and deserialized — typically completing in milliseconds for payloads under a few MB.

**However**, be aware:
- The LLM context window is the real limit, not stdio bandwidth
- 100 search results may consume significant context — consider returning summaries
- For very large payloads (>10MB), consider pagination or writing to a file and returning the path

### Recommendation

Use stdio for local Claude Code integration. Switch to Streamable HTTP only if you need multi-client access or production deployment.

## 11. MCP Servers Proxying to Local AI Services

### ollama-mcp-bridge

Extends the Ollama API with MCP tool integration. FastAPI backend, supports stdio/HTTP/SSE transports.
GitHub: https://github.com/jonigl/ollama-mcp-bridge

### MCP-Ollama Server

Bridges MCP to local LLMs via Ollama — file system, web, email, GitHub tools while keeping data private.
GitHub: https://github.com/Sethuram2003/MCP-ollama_server

### Llama.cpp Bridge MCP Server

Bridges local llama-server instances with MCP clients, providing chat interface and health monitoring.

### Example: MCP server proxying to local Ollama

```python
#!/usr/bin/env python3
"""MCP server that proxies to a local Ollama instance."""

import httpx
from fastmcp import FastMCP
from fastmcp.exceptions import ToolError

mcp = FastMCP(name="OllamaProxy")

OLLAMA_URL = "http://127.0.0.1:11434"

@mcp.tool
async def ollama_generate(
    prompt: str,
    model: str = "llama3.2",
    temperature: float = 0.7,
    max_tokens: int = 1024,
) -> str:
    """Generate text using a local Ollama model."""
    async with httpx.AsyncClient() as client:
        try:
            resp = await client.post(
                f"{OLLAMA_URL}/api/generate",
                json={
                    "model": model,
                    "prompt": prompt,
                    "stream": False,
                    "options": {
                        "temperature": temperature,
                        "num_predict": max_tokens,
                    },
                },
                timeout=120.0,
            )
            resp.raise_for_status()
            return resp.json()["response"]
        except httpx.ConnectError:
            raise ToolError(f"Cannot connect to Ollama at {OLLAMA_URL}. Is it running?")
        except httpx.HTTPStatusError as e:
            raise ToolError(f"Ollama error {e.response.status_code}: {e.response.text}")

@mcp.tool
async def ollama_list_models() -> list[dict]:
    """List available Ollama models."""
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"{OLLAMA_URL}/api/tags", timeout=10.0)
        resp.raise_for_status()
        return [
            {"name": m["name"], "size": m.get("size", "unknown")}
            for m in resp.json().get("models", [])
        ]

@mcp.tool
async def ollama_embed(text: str, model: str = "nomic-embed-text") -> list[float]:
    """Generate embeddings using a local Ollama model."""
    async with httpx.AsyncClient() as client:
        resp = await client.post(
            f"{OLLAMA_URL}/api/embed",
            json={"model": model, "input": text},
            timeout=30.0,
        )
        resp.raise_for_status()
        return resp.json()["embeddings"][0]

if __name__ == "__main__":
    mcp.run()
```

## Lessons Learned

1. **Use `pip install fastmcp` (v3.x), not `pip install mcp`** — the standalone package is far more capable and actively maintained.
2. **stdout is sacred in stdio mode** — a single `print()` will break your server silently. Use stderr for all logging.
3. **ToolError is the correct way to report errors** — it sets `isError: true` and lets the LLM retry with corrected input.
4. **True streaming is not supported by the MCP spec** — only progress notifications work. Tools must return complete results.
5. **Pydantic models work for complex parameters** but Claude Code may serialize them as JSON strings. Use flexible validation (the default).
6. **stdio performance is fine for Claude Code** (single user, interactive) but fails under concurrency. Use Streamable HTTP for production.
7. **Test with MCP Inspector** (`npx @modelcontextprotocol/inspector`) before connecting to Claude Code.
8. **Use absolute paths everywhere** in `.mcp.json` configuration.

## Recommendations

- Start with Approach A (manual httpx proxy) — it gives you full control over tool names, descriptions, and error handling.
- Use `fastmcp run server.py --reload` during development for instant feedback.
- Keep tool descriptions concise but informative — the LLM uses them to decide when to call your tool.
- For Claude Code configuration, use the CLI (`claude mcp add`) rather than hand-editing JSON.
- Pin your `fastmcp` version in requirements.txt — the API has changed significantly between v1, v2, and v3.
