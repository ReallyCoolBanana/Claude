# Multi-Process Sandbox Prototyping Framework

## Context
TEAM-0020, TEAM-0021, and TEAM-0022 all identified the same critical gap:
all Proto A testing used threads, not real OS processes. Real multi-agent
deployments spawn separate processes, which have different failure modes
for file locking, SQLite WAL access, and POSIX atomic writes. Without
multi-process testing, the production confidence was based on threading
behaviour that may not hold under true process isolation.

## Method
Built `prototype/sandbox/` — a multi-process sandbox framework that:

1. **Creates isolated temp directories** with `bus/` and `db/` subdirectories
   for each test run (auto-cleaned on exit).
2. **Spawns real OS processes** via `multiprocessing.Process` (not threads)
   for each agent, with proper coordinator-first startup ordering.
3. **Collects results** via `multiprocessing.Queue` from each child process,
   including message counts, errors, and custom data payloads.
4. **Provides inspection APIs** — `read_bus(channel)` to parse JSONL files
   and `query_db(sql)` to query SQLite state post-hoc.
5. **Supports custom behaviours** — any function matching the signature
   `(comm_dir, agent_id, team, role, config, result_queue) -> None` can be
   injected as an agent behaviour for scenario-specific testing.

### Test scenarios (11 tests, all passing):
- Basic lifecycle: single team and multi-team coordinator + worker cycles
- Cross-process messaging: messages written in one process readable in another
- Bus file integrity: no corrupt JSON after concurrent multi-process writes
- SQLite shared state: all agents registered with distinct PIDs
- Phase signal persistence: coordinator phase transitions survive in DB
- Rate limiting across processes: exactly N successes with N-slot limit
- 10-worker concurrent stress: unique message IDs, no corruption
- Process isolation verification: distinct PIDs for all agents

## Result
**11/11 tests passing** in 31 seconds. Key findings:

- Proto A's JSONL bus handles concurrent multi-process writes correctly
  (POSIX O_APPEND atomic guarantees hold as expected).
- SQLite WAL mode with busy_timeout works correctly across process boundaries.
- Rate limiting via BEGIN IMMEDIATE enforces exact limits across 4 processes.
- Each agent runs in a truly distinct OS process (verified via PID checks).

This closes the critical gap flagged by 3 previous teams.

## Lessons Learned
1. The `multiprocessing.Queue` is essential for collecting results from child
   processes — return values from `Process.target` are not accessible.
2. Coordinators must start before workers to ensure the SQLite schema and
   coordinator heartbeat are available.
3. The Proto A Coordinator class hardcodes `agent_id="coordinator"` internally,
   which differs from the user-specified agent_id — tests must account for this.

## Recommendations
1. Use the sandbox for all future coordination feature testing — it validates
   real process isolation with minimal boilerplate.
2. Custom behaviours make it easy to prototype new features: write a function,
   inject it via `AgentSpec(behaviour=my_fn)`, and collect results.
3. Next teams should add failure injection scenarios (kill -9, disk full, etc.)
   to the sandbox framework.
4. Consider adding a `Sandbox.wait_until_phase()` method for more ergonomic
   phase-gated testing.
