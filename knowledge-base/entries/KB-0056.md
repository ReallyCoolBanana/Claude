# LanceDB + cuVS + Nemotron: Disk-First GPU-Accelerated Vector Search Technical Analysis

## Context

Research into a proposed architecture combining LanceDB on NVMe (disk-first, memory-mapped) with NVIDIA cuVS for GPU-accelerated search, Nemotron embedding and reranking models, and a two-phase retrieval pattern (Neo4j graph traversal then LanceDB vector fetch). Goal: assess component maturity, realistic performance, and integration readiness.

## Method

Web research across official documentation, benchmarks, Hugging Face model cards, NVIDIA technical blogs, academic papers, and GTC 2025/2026 sessions.

## Result

### 1. LanceDB Disk-First Architecture

**How memory-mapping works:** LanceDB uses the Lance file format built on Apache Arrow columnar storage. Vectors and metadata are stored on disk and accessed via mmap(). The OS maps file regions into virtual address space; the kernel page cache transparently loads pages on demand. No explicit data loading required.

Key properties:
- Random access is a first-class design goal of Lance format (unlike Parquet, optimized for sequential scans)
- SIMD-optimized distance computations operate directly on memory-mapped data
- IVF-PQ indexes allow sub-linear search without loading full dataset
- Immutable fragment architecture enables zero-copy reads and stateless compute

**NVMe performance (January 2026 benchmarks, AWS i8g.12xlarge, 3x NVMe):**
- 1.5M aggregate IOPS across three drives
- Single random NVMe read: ~10-20us (drive spec), ~100us in practice
- 3ms latency sufficient for >0.9 recall with IVF-PQ
- 5ms latency sufficient for 0.95 recall
- 25ms target vector search latency; 50ms with metadata filtering
- Warm queries (page-cache-resident): single-digit to low double-digit ms
- Local NVMe outperformed all network storage (129s vs EBS 176s vs EFS 194s)

**Status: PRODUCTION-READY.** LanceDB OSS is mature. Enterprise adds automatic GPU indexing, NVMe cache over S3, consistent hashing.

### 2. cuVS: What It Is

NVIDIA cuVS (CUDA Vector Search) is an open-source RAPIDS library for GPU-accelerated vector search and clustering. It provides low-level building blocks (index construction, search kernels, data structures) that vector databases integrate as their GPU backend.

- Languages: C, C++, Rust, Java, Python, Go
- License: Apache 2.0
- Integrations: Faiss (v1.10+), Elasticsearch (9.3 tech preview), OpenSearch (3.0), Milvus, Weaviate, Oracle 23ai, Google AlloyDB

**CAGRA (CUDA ANNs GRAph-based):**
- Purpose-built fixed-degree graph index for GPU search
- Build times up to 12.3x faster than CPU HNSW
- Search up to 4.7x faster (Deep100M)
- Up to 18x higher throughput for offline batch search
- GPU-to-CPU interop: CAGRA graphs convert to HNSW for CPU inference

**DiskANN/Vamana (GPU-accelerated build via cuVS):**
- Microsoft Research algorithm for billion-scale SSD-resident search
- cuVS accelerates Vamana graph build: 40x+ speedup over CPU
- Hybrid architecture: PQ-compressed vectors in RAM (~8x compression), full vectors + adjacency lists on SSD
- Search alternates RAM (approximate PQ distances) and SSD (precise full-vector distances)
- <5ms latency at >95% recall@1 on billion-scale datasets
- Disk I/O is ~92.5% of search time -- NVMe speed is critical
- Caches nodes within C=3-4 hops of entry point in RAM

**How CAGRA and DiskANN work together:**
- CAGRA for GPU-resident hot data (fits in GPU memory) -- highest throughput
- DiskANN for disk-resident cold data (exceeds GPU/RAM) -- billion-scale with SSD
- cuVS builds DiskANN indexes on GPU, exports for CPU-side search

**Status: PRODUCTION-READY** (cuVS core library). Widely adopted across the vector DB ecosystem.

### 3. cuVS + LanceDB Integration: THE CRITICAL FINDING

**There is NO direct native cuVS/CAGRA/DiskANN integration within LanceDB itself as of March 2026.**

The connection is indirect through NVIDIA NeMo Retriever:
1. LanceDB's own GPU indexing uses PyTorch for IVF cluster training (CUDA/MPS), NOT cuVS. Gives 20-26x speedup for index builds.
2. NeMo Retriever uses LanceDB as its DEFAULT vector store, with cuVS providing GPU acceleration as an intermediary layer.
3. Architecture: cuVS accelerates indexing/search, LanceDB provides the storage substrate, NeMo Retriever is the glue.

If deploying via NeMo Retriever: LanceDB + cuVS works as integrated stack.
If using LanceDB standalone: GPU indexing is PyTorch-based IVF/HNSW, not cuVS CAGRA/DiskANN.

### 4. llama-embed-nemotron-reasoning-3b

**Status: REAL BUT NOT PUBLICLY RELEASED.**

- Referenced in NVIDIA's March 2026 agentic retrieval publication
- No standalone Hugging Face model card or public download
- Evaluated on BRIGHT benchmark (reasoning-intensive retrieval, ICLR 2025 Spotlight)
- Outperformed llama-nemotron-embed-vl-1b-v2 by ~19 points on BRIGHT
- Lead shrinks to ~7.5 points when coupled with gpt-oss-120b agent

**What "reasoning-aware" embedding means (BRIGHT benchmark context):**
Standard SOTA embeddings (59.0 on MTEB) collapse to 18.3 nDCG@10 on reasoning-intensive queries. Reasoning-aware approaches:
- Generate chain-of-thought reasoning before computing embeddings
- Decompose queries into sub-intents and interpretations
- Encode logical/causal structure, not just surface semantics
- Results: up to 12.2 point improvement on reasoning-intensive retrieval

**Likely specifications (inferred from Nemotron family):**
- Parameters: ~3B
- Embedding dimensions: likely 4096 (same as 8B sibling)
- Architecture: transformer decoder with bidirectional attention
- Model size: ~6GB fp16, ~3GB int8

**Production-ready alternative: llama-embed-nemotron-8b**
- 4096-dimensional embeddings, 32K token context
- #1 on multilingual MTEB (October 2025)
- 7.5B parameters
- Non-commercial/research license

### 5. NeMo Retriever

End-to-end enterprise retrieval framework bundling:
1. Document extraction (text, tables, charts)
2. Embedding (Nemotron models)
3. Vector store: LanceDB (default) or Milvus, accelerated with cuVS
4. Reranking (Nemotron reranking models)
5. Deployment via NVIDIA NIM (TensorRT/Triton optimized containers)

NeMo Retriever is the GLUE LAYER making LanceDB + cuVS + Nemotron work together. Without it, manual integration of each component is required.

**Status: PRODUCTION-READY.** Enterprise-grade, deployed at petabyte scale.

### 6. Nemotron Reranker and Multi-Signal Fusion

**Available reranking models:**

llama-nemotron-rerank-1b-v2:
- 1B parameters, Llama-3.2-1B base, cross-encoder with bidirectional attention
- 8192 token context, 26 languages, commercial license
- 3.5x smaller than nv-rerankqa-mistral-4b-v3

nv-rerankqa-mistral-4b-v3:
- 3.5B parameters (Mistral 7B, half weights), higher accuracy

**Implementing 5-signal fusion (structural, semantic, temporal, causal, entity):**

No off-the-shelf model natively fuses 5 heterogeneous signal types. Implementation options:

Option A - Score-level fusion (practical, recommended first):
Each signal produces a relevance score per candidate. Merge via Reciprocal Rank Fusion (RRF) or learned weighted combination. Reranker re-scores top-K with cross-attention.

Option B - Feature-level fusion:
Encode each signal as feature vector, concatenate with semantic embedding, train lightweight fusion head (MLP or small transformer).

Option C - Prompt-based fusion (simplest deep integration):
Format all 5 signals as structured text in reranker input within 8192 token context. Let cross-encoder attend over all signals jointly.

### 7. Page Cache Analysis: 80-100GB vs 4TB

Raw coverage: 80-100GB / 4TB = 2-2.5% of total data.
With IVF-PQ compression (~8x): effectively 16-20% of compressed index cacheable.

Zipf's law applies to retrieval access patterns (80% of queries hit 20% of data).

**Effective caching estimate:**
- Hot index metadata (centroids, graph entry points): ~1-5GB, always cached
- Top ~20% most popular IVF partitions stay resident with 80GB cache
- Realistic cache hit rate: 70-90% despite only 2.5% raw coverage
- Cache misses: +0.1-1ms per NVMe page fault

**Known mmap limitations on Linux:**
- Page table overhead: 4TB mapped = ~8GB page tables (4KB pages)
- TLB shootdowns under eviction pressure cause latency spikes
- Linux prefetches 128KB per fault (32 pages) -- wasteful for random access
- Under memory pressure, mmap is 2-20x worse than O_DIRECT

**Mitigations:**
- madvise(MADV_RANDOM) to disable sequential prefetch
- Huge pages (2MB) reduce page table overhead 512x
- Application-level LRU for hot graph nodes
- LanceDB Enterprise uses custom NVMe cache with consistent hashing

## Lessons Learned

1. The cuVS-LanceDB connection is INDIRECT through NeMo Retriever. No native cuVS plugin exists in LanceDB. This is the most important finding for architecture planning.

2. llama-embed-nemotron-reasoning-3b exists in NVIDIA research but is not publicly downloadable. Use llama-embed-nemotron-8b (4096-dim, MTEB #1) as the production alternative.

3. DiskANN on NVMe is the correct algorithm for 4TB cold storage -- designed exactly for SSD-resident billion-scale search. With cuVS, index build is 40x faster on GPU.

4. Page cache math works for typical access patterns: 80-100GB covers only 2.5% of 4TB raw, but Zipf-distributed access yields 70-90% hit rates. Warm tier emerges naturally from OS behavior.

5. The reranker is the throughput bottleneck at ~200-500 QPS per GPU. Plan 2-4 replicas for production volumes.

## Recommendations

1. Use NeMo Retriever as integration layer for LanceDB + cuVS. Do not expect native cuVS in LanceDB.

2. Substitute llama-embed-nemotron-8b for the unreleased reasoning-3b, or wait for public release.

3. Implement signal fusion via RRF initially, graduate to prompt-based fusion in the reranker's 8192 token context.

4. Tune mmap: MADV_RANDOM, huge pages, application-level hot node caching for NVMe cold tier.

5. Budget 2-4 GPU replicas for the reranker to avoid bottleneck.

6. Benchmark two-phase pattern end-to-end before committing. The 5-50ms graph overhead is acceptable for quality-sensitive apps but adds up.
