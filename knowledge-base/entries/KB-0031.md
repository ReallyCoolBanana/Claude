# Multi-Agent Coordination: Academic Research Survey (6 Areas)

## Context
Deep-dive research into academic and industry literature on multi-agent coordination, covering task allocation, LLM agent frameworks, SQLite performance, work stealing theory, optimal team sizing, and low-latency scheduling. Findings directly applicable to our Proto A coordination system.

## Method
Web research across academic papers (Nature, IEEE, arXiv, ACM), industry blogs (AWS, Google DeepMind, Turso), and framework documentation (LangGraph, CrewAI, Ray, Dask). 20+ sources analyzed.

## Result

### 1. Multi-Agent Task Allocation (2024-2025)

- **Decentralized architectures dominate**: Two-layer architecture (Scientific Reports 2025) handles partial observability and noisy feedback without central controller
- **Auction-based methods** with cost-effectiveness maximization address heterogeneous capabilities better than economic optimization alone
- **DGBA (Distributed Greedy Bundles Algorithm)**: Polynomial-time feasible allocation with approximation guarantees for submodular objectives
- **Hybrid RL + evolutionary methods** (GAPPO = Genetic Algorithms + PPO) enable adaptive allocation

**Recommendation**: Add sealed-bid auction mechanism to `coordinator_hub.py`. When tasks arrive, idle agents bid based on queue depth and task affinity. Hub awards to lowest bidder. Low-overhead, naturally load-balancing.

### 2. LLM Agent Coordination Frameworks

- **Two primary patterns validated**: Centralized (hub routes all) and decentralized (peer-to-peer). Our system supports both via `coordinator_hub.py` and `direct_channels.py`
- **DynTaskMAS**: Achieved near-linear scalability (3.5x throughput for 4x agent increase) through dynamic task management
- **Error propagation finding**: Independent agents amplified errors **17.2x**, while centralized orchestration reduced this to **4.4x**
- **Google A2A Protocol**: Establishes standards for agent interoperability with long-running task support

**Recommendation**: Add validation/review step in hub before accepting outputs. Route completed work through spot-check agent to reduce 17x→4x error amplification.

### 3. SQLite Concurrent Write Optimization

- WAL mode achieves ~70,000 reads/s and ~3,600 writes/s vs rollback mode's 291 writes/s
- **Critical PRAGMAs most people miss**: `synchronous=normal` (safe in WAL), `temp_store=memory`, `mmap_size=30000000000`
- **Checkpoint starvation**: If always at least one active reader, WAL file grows without bound. Need deliberate reader gaps
- **Turso's BEGIN CONCURRENT**: MVCC for row-level conflict detection, 4x write throughput (not in mainline SQLite yet)
- **Single most effective optimization**: Funnel all writes through a dedicated writer thread/process

**Recommendation**:
1. Set PRAGMAs: `synchronous=normal`, `temp_store=memory`, `mmap_size=30000000000`
2. Implement **write coalescing thread**: Agents push to `queue.Queue`, single thread batches into transactions. Eliminates SQLITE_BUSY entirely
3. Tune `wal_autocheckpoint` to 5000 pages, add forced checkpoints during idle
4. Use JSONL bus for high-frequency data (heartbeats), SQLite only for queryable state

### 4. Work Stealing vs Work Sharing Theory

- **Blumofe & Leiserson foundational result**: Work stealing incurs scheduling overhead ONLY when a processor is idle. When all busy, zero overhead
- **Load-dependent crossover (Van Houdt, IEEE)**: Work sharing outperforms work stealing below load ~0.618 (golden ratio inverse). Above that, work stealing wins
- **Highly variable job sizes**: Work stealing wins at even lower loads (0.5+epsilon)
- **Best modern approach**: Work sharing within local group, work stealing between groups

**Recommendation**: Two-tier approach — within a team use work sharing (coordinator pushes to shortest queues), between teams use work stealing (idle teams pull from busy teams). Add affinity-based stealing (prefer tasks similar to recently completed ones).

### 5. Optimal Team Size (Google DeepMind Study)

- **180 configurations tested**: "More agents" often hits ceiling, can degrade if not matched to task structure
- **Parallelizable tasks**: +81% improvement (Finance-Agent)
- **Sequential tasks**: -70% degradation (PlanCraft)
- **Error amplification scales with agent count** in uncoordinated systems (17.2x)
- **Predictive model** (R²=0.513): Correctly identifies optimal coordination strategy for 87% of unseen configs using just tool count and decomposability
- **"Multi-Agent Teams Hold Experts Back"**: Adding identical agents adds overhead without proportional benefit

**Recommendation**:
1. Add task decomposability scorer to coordinator
2. Dynamic scaling: start with 3-5 agents, spawn more only if queue grows faster than drain rate
3. Track marginal productivity — if Nth agent doesn't reduce time by 1/N, stop scaling
4. Use genuinely heterogeneous agents (research, coding, review) over 10 identical ones

### 6. Low-Latency Distributed Scheduling

- **Sparrow (Berkeley)**: Sub-10ms delays via decentralized stateless schedulers with batch sampling + late binding
- **Late binding**: Workers queue the probe, only get task when actually ready. Eliminates probe-to-execution delay
- **Join-the-Idle-Queue (JIQ)**: Idle workers register centrally. New tasks instantly assigned. No probing needed
- **Power-of-two-choices**: Pick 2 random workers, assign to less loaded one. Exponentially better than random with minimal overhead
- **Event-driven triggers**: React to state changes rather than polling
- **Back-pressure**: When workers overwhelmed, slow submission rather than building unbounded queues

**Recommendation**:
1. **JIQ pattern**: Maintain idle-agent queue in hub. New tasks go directly to idle agents with zero probing
2. **Late binding**: Send task offers to 2-3 candidates. First to accept wins
3. **Power-of-two-choices**: When stealing, sample 2 random peers, steal from longer queue
4. **Event-driven heartbeats**: Push state-change events (idle/busy/error) to bus instead of polling
5. **Back-pressure**: If all agents have queue depth > N, buffer new tasks

## Lessons Learned

1. **Write coalescing is the single biggest performance win** for SQLite multi-writer systems — eliminates SQLITE_BUSY contention entirely
2. **JIQ reduces scheduling latency to near-zero** for the common case (idle agents available)
3. **Don't default to max agents** — start small, scale based on task decomposability and queue growth
4. **Error amplification is real** — 17.2x for uncoordinated agents. Hub validation is cheap insurance
5. **Power-of-two-choices** is minimal code for exponentially better load balance

## Recommendations (Ranked by Impact)

1. **Write coalescing thread for SQLite** — eliminates SQLITE_BUSY entirely
2. **Join-the-Idle-Queue pattern** — near-zero scheduling latency for idle agents
3. **Dynamic team sizing** — start small, scale based on task decomposability
4. **Event-driven state changes over polling** — reduces I/O, improves responsiveness
5. **Power-of-two-choices for work stealing** — minimal code, exponentially better balance
6. **Hub validation step** — reduces 17x error amplification to 4x
