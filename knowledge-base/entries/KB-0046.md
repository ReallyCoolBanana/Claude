# Wikipedia Scraping Project: Process Review, Deficiencies, and Improvement Plan

## Context

Full retrospective on the Wikipedia AI category scraping project (KB-0044, KB-0045). Covers what worked, what failed, data gaps, tool deficiencies, and actionable improvements. Produced by reviewing all project artifacts, agent transcripts, and output data.

## What Went Well

1. **Parallel agent decomposition** — 7 agents across 12 Wikipedia articles (KB-0044) with topic-cluster assignment minimized overlap. Deduplication reduced 150+ raw citations to 85 unique papers.

2. **DBpedia SPARQL discovery** — The critical breakthrough. Batch queries for 234 articles complete in 9 seconds. The `ontology/` vs `property/` predicate distinction was caught and documented.

3. **Caching strategy** — 702 cache files enable 120x speedup on repeat queries (58s → 42ms). Per-article, per-data-type file-based caching is simple and effective.

4. **Token efficiency work** — 26 URL prefix shortcuts, 3 export formats (full/compact/LLM), 31% token savings on the LLM format. Measurable, practical savings.

5. **Reusable tool** — wikipedia_tools.py (655 lines) with CLI + Python API, batch support, and export formats. Registered as SCR-0043 with full SOP (SOP-026).

## What Went Wrong

### 1. Eight dead-end methods tested (67% failure rate)
KB-0045 documents 12 methods tested, 8 blocked. Direct Wikipedia, mobile, REST API, MediaWiki API, Wikimedia dumps, Wikidata, Google Cache, Wikiwand, wiki2, Internet Archive — all blocked by egress policy. A 30-second connectivity pre-check would have eliminated all 8 in one pass.

### 2. Cross-team re-discovery of blocked domains
TEAM-0005 (March 10) noted Wikipedia and Wikidata 403 blocks. KB-0045 (March 12) independently re-tested the same endpoints. Two days of findings were not shared because there was no "blocked domains" registry.

**Fix created**: `storage/sources/blocked-domains.json` — shared registry of blocked/accessible domains.

### 3. Agents doing redundant work
Multiple agents independently discovered the same blocks. The initial 7-agent paper crawl (KB-0044) used search-based citation reconstruction — a method that took minutes per article — when DBpedia SPARQL batch could have done it in 9 seconds if discovered first.

### 4. Testing was exploratory, not structured
No connectivity matrix was run upfront. Agents were sent to test methods individually, discovering failures in parallel rather than sequentially filtering working methods first.

**Fix created**: SOP-025 includes "egress testing protocol" — test all candidate endpoints on one article before parallelizing.

## Data Deficiencies

| Gap | Severity | Coverage |
|-----|----------|----------|
| Articles with no external links | High | 62% missing |
| Articles not in DBpedia at all | High | 42% (98/234) |
| No metadata (categories/descriptions) | Medium | 85% missing |
| No article body text or summaries | Medium | 100% missing |
| No citation context (which claim each URL supports) | Low | 100% missing |
| Paper catalog covers only 12 of 234 articles | Medium | 95% missing |
| ChatGPT and recent articles completely absent | High | Varies |

### Root causes:
- DBpedia lags Wikipedia by months — new articles not yet indexed
- `dbo:abstract` not available on public SPARQL endpoint
- External links in DBpedia represent "External links" footer, not all inline references
- No WebSearch integration in the tool for gap-filling

## Tool Deficiencies (wikipedia_tools.py)

### Critical
1. **No retry logic** — Transient SPARQL failures silently cache empty results, permanently poisoning that article's data
2. **Empty results cached as valid** — No distinction between "queried, got 0" and "never queried"
3. **No error handling for network failures** — `subprocess.TimeoutExpired` not caught

### Important
4. **No cache invalidation/TTL** — Stale data never refreshes
5. **No progress reporting** — Batch operations give no feedback during 58s runs
6. **No `--no-cache` CLI flag** — Must clear ALL cache to re-fetch one article
7. **No article existence check** — Can't distinguish "not in DBpedia" from "exists but empty"

### Minor
8. **No WebSearch integration** — Pass 2 and Pass 3 from KB-0045's recommended strategy are not implemented
9. **Fragile URL decompression ordering** — Adding new prefixes could cause collision with `h:` prefix
10. **No SPARQL response validation** — Malformed responses cause unhelpful KeyError

## Improvement Recommendations

### Process Improvements

1. **Pre-flight connectivity check (MANDATORY for all new crawls)**
   - Run `storage/sources/blocked-domains.json` check first
   - Test each target API with a single probe before parallelizing
   - Update blocked-domains registry with results

2. **Probe-then-parallelize pattern**
   - One agent, 2 minutes, tests all candidate methods on one well-known article
   - Only methods returning non-empty results get assigned to parallel teams
   - Front-loads failure detection before wasting agent time

3. **Pipeline-staged agent teams** (for data extraction)
   - Stage 1: Batch SPARQL (1 agent, 9 seconds, all articles)
   - Stage 2: WebSearch gap-fill (3 agents, covers missing articles)
   - Stage 3: Deep-dive citation extraction (3 agents, high-priority articles)
   - Each stage builds on previous stage's results

4. **Coverage audits after each phase**
   - Compute and display coverage % immediately after each extraction phase
   - Let team decide whether to proceed with gap-filling or accept coverage level

5. **Formalized fallback chains**
   - DBpedia SPARQL → DBpedia WebFetch → WebSearch → mark uncrawlable
   - Document in SOP with specific commands for each fallback

### Tool Improvements (prioritized)

| Priority | Improvement | Effort |
|----------|------------|--------|
| P0 | Add retry logic (3 retries with backoff) | 30 min |
| P0 | Distinguish empty-from-query vs never-queried in cache | 20 min |
| P1 | Add `--refresh` CLI flag for single-article re-fetch | 15 min |
| P1 | Add progress reporting to batch operations | 15 min |
| P1 | Add WebSearch fallback for DBpedia gaps | 1 hour |
| P2 | Add article existence check (`ASK` query) | 20 min |
| P2 | Add cache TTL (re-fetch after N days) | 30 min |
| P2 | Add DBpedia Lookup API for article summaries | 45 min |
| P3 | Add SPARQL response validation | 15 min |
| P3 | Harden URL decompression ordering | 10 min |

## Lessons Learned

1. **Always test connectivity before building tools.** A 30-second probe saves hours of dead-end agent work.
2. **Share failure knowledge across teams.** A blocked-domains registry prevents redundant discovery.
3. **Batch SPARQL is transformatively fast.** 234 articles in 9 seconds vs minutes per article with individual queries.
4. **Cache empty results differently from absent results.** Silent data poisoning is the worst kind of bug.
5. **Token efficiency pays compound returns.** 31% savings on every agent prompt adds up across hundreds of operations.
6. **Probe-then-parallelize beats parallel-probe.** One agent testing 12 methods is faster than 4 agents each testing 3.

# First Market Research Sprint: Methodology and Findings

## Context
TEAM-0035 executed the first market research sprint to produce actionable stock picks. Previous teams had focused on infrastructure (coordination systems, knowledge base, SOPs) without generating domain output. This session applied the SOP-022 team sizing (5 agents), SOP-023 anti-recursion (80% domain ratio, 0% infrastructure), and the TT-3 quality framework to break the zero-output streak.

## Method
### 4-Phase Research Pipeline
1. **Phase 1 — Intelligence (parallel):** Two research agents gathered macro backdrop and sector screening data simultaneously.
2. **Phase 2 — Research (parallel):** Fundamental analyst and sentiment analyst evaluated 12 candidates across 4 sectors in parallel.
3. **Phase 3 — Scoring:** Composite scoring using weighted formula: Fundamental (50%) + Sentiment (30%) + Macro Fit (20%).
4. **Phase 4 — Output:** Pick files written using TEMPLATE.md, index updated, KB entry created.

### Macro Environment (March 12, 2026)
- S&P 500 at ~6,740 (erased 2026 gains, 3-month low)
- VIX at 25.74 (elevated fear)
- Fed funds rate at 3.50-3.75% (on hold)
- Q4 2025 GDP at 1.4% annualized (below forecast)
- CPI at 2.4% YoY (stable but oil shock risk)
- Dominant theme: US-Iran conflict, oil above $100/bbl, stagflation risk

### Sectors Selected
1. Healthcare — multi-decade low valuations, policy clarity, demographic tailwinds
2. Industrials — AI capex super-cycle ($660-690B), data center buildout
3. Energy — geopolitical oil spike, value rotation, nat gas/data center pivot
4. Materials — 5-year breakout, copper supply deficit, infrastructure boom

### Candidate Screening
12 stocks screened: MRK, NVO, VEEV (Healthcare), ETN, VRT, EME (Industrials), XOM, AR, FTI (Energy), RIO, NUE, FCX (Materials).

## Lessons Learned
1. **Parallel research phases dramatically improve speed.** Running macro + sector screening simultaneously, then fundamental + sentiment analysis simultaneously, was highly efficient.
2. **Insider selling is pervasive.** Every single candidate showed net insider selling. This cross-cutting signal should be weighed more heavily in future screens — it may indicate broad market overvaluation.
3. **Contrarian value picks (NVO) require higher conviction thresholds.** Deep value in healthcare is compelling on paper but sentiment headwinds can persist longer than expected.
4. **WebSearch provides adequate financial data.** No MCP financial data servers were needed for this initial sprint — analyst targets, P/E ratios, insider activity, and news are all accessible via web search.
5. **The composite scoring formula works well.** Fund 50% / Sent 30% / Macro 20% produced a ranking that aligned with qualitative judgment.

## Recommendations
1. **Session 2 should validate these picks with live financial data** via MCP servers (Yahoo Finance, Alpha Vantage, etc.) and update entry prices.
2. **Add a technical analysis overlay** — none of these picks incorporated chart patterns or technical indicators.
3. **Monitor insider selling closely** — if FTI or EME see additional C-suite sales, consider tightening stops.
4. **Track the Iran conflict resolution timeline** — this is the dominant macro variable affecting Energy picks (FTI, AR) and overall market direction.
5. **Consider short/hedge picks in future sessions** — all 5 picks are long. In an elevated-VIX environment with stagflation risk, having short exposure would improve portfolio balance.
