# Embedding Models & Vector Search Systems for Semantic Search over Knowledge Graphs (RTX 4070 Super / 12GB VRAM)

## Context
Deep research crawl on building a semantic search layer over a knowledge graph with millions of nodes, constrained to an RTX 4070 Super (12GB VRAM). Covers embedding models, vector databases, quantization, search techniques, and practical GPU memory planning. All data current as of March 2026.

### 1.2 Key Findings Per Model

**nomic-embed-text v1.5 (137M params)**
- Long-context BERT architecture, multi-stage training pipeline
- Matryoshka at 768/512/256/128/64 dimensions
- Outperforms OpenAI Ada-002 and text-embedding-3-small
- Open weights, training code, and data under Apache 2.0
- Requires task prefixes: search_query, search_document, clustering, classification
- Aligned vision model (nomic-embed-vision-v1.5) for multimodal

**nomic-embed-text v2 (475M/305M active)**
- First MoE embedding model: 8 experts, top-2 routing, alternating MoE layers
- Only 305M of 475M params active per inference
- Trained on 1.6B contrastive pairs across ~100 languages
- Outperforms models in same parameter class on mono+multilingual benchmarks
- Competitive with models 2x its size
- All code/data open-sourced at github.com/nomic-ai/contrastors

**BGE-M3 (568M params) -- UNIQUELY IMPORTANT FOR KNOWLEDGE GRAPHS**
- Triple retrieval: dense + sparse + multi-vector in ONE forward pass
- 100+ languages, up to 8192 tokens
- Dense embeddings alone rival E5-Mistral-7B (7B params) on English
- Combined dense+sparse+multi-vector gives best results per BAAI benchmarks
- MIRACL nDCG@10 = 70.0 (all modes), outperforming all baselines
- Self-knowledge distillation training enhances adaptability
- Ideal for knowledge graphs: entity name matching (sparse) + semantic (dense) + fine-grained (multi-vector)

**E5-large-v2 (335M params)**
- Solid baseline, 1024d, 512 token limit
- BEIR score 50.6
- No instruction prefix needed (simpler integration)
- Outclassed by newer models but still widely deployed

**E5-mistral-7b-instruct (7.1B params)**
- Highest MTEB at release, 4096d embeddings, 4096 token context
- Instruction-following embedding model
- TOO LARGE for 12GB VRAM alongside an index (~14GB fp16)
- Best for English; multilingual is suboptimal

**GTE-multilingual-base (~110M params)**
- Encoder-only, small and fast, dense + sparse vector generation
- 10x faster inference than decoder-only variants
- 768d, 8192 tokens, supports RoPE

**GTE-Qwen2-7B-instruct (7.6B params)**
- #1 on MTEB English+Chinese (as of June 2024): score 70.24
- 3584d embeddings, 32K context
- TOO LARGE for 12GB VRAM use case

**Cohere embed-v4 (API-only)**
- Multimodal (text + images, interleaved), 128K context
- Matryoshka (256-1536d), float/int8/uint8/binary/ubinary output
- Best commercial option if you want to avoid self-hosting

**Jina embeddings v3 (570M params)**
- Task-specific LoRA adapters for retrieval, clustering, classification, matching
- 1024d default, truncatable to 32d with 92% retention at 64d
- 89 languages, 8192 tokens via RoPE
- CC-BY-NC-4.0 license RESTRICTS commercial self-hosting

**Snowflake arctic-embed v2 (113M / 303M)**
- Quantization-aware embedding training: 128-byte vectors via MRL + 4-bit quantization
- arctic-embed-m v2: 113M params, extremely fast, >100 docs/sec on A10
- arctic-embed-l v2: built on BGE-M3-retromae, drop-in replacement
- MRL dimension: 256, with <3% quality degradation from full dimensions

### 1.3 Recommendations for 12GB VRAM

**BEST OVERALL: BGE-M3 (~2.2GB)** -- Triple retrieval eliminates need for separate sparse model. 8K context handles most KG node descriptions.

**BEST FOR SPEED: nomic-embed-text v1.5 (~550MB) or Snowflake arctic-embed-m v2 (~450MB)** -- Tiny models, maximize remaining VRAM for index. MRL support. 3000-5000+ sentences/sec.

**BEST BALANCE: nomic-embed-text v2 (~1.9GB)** -- MoE gives quality beyond its active parameter count. Multilingual. MRL 256-768d.

**TOO LARGE (won't fit alongside index):** E5-mistral-7b (~14GB), GTE-Qwen2-7B (~15GB), Qwen3-Embedding-8B (~16GB). Use via API or on separate hardware.

### 1.4 Speed vs Quality Tiers

| Tier | Models | Est. Throughput (RTX 4070S) |
|---|---|---|
| Ultra-fast (batch indexing) | nomic v1.5, arctic-embed-m v2, GTE-multilingual-base | 3000-6000 sent/s |

### 2.2 FAISS Deep Dive

**Index Types:**

| Index | Memory/Vec (768d) | GPU? | Recall | Notes |
|---|---|---|---|---|
| Flat (fp32) | 3072B | Yes | 100% | Brute force, no training |
| Flat (fp16) | 1536B | Yes | ~100% | Negligible quality loss |
| IVFFlat | 3072B + overhead | Yes | 95-99% | nprobe tunes speed/recall |
| IVFPQ (m=64) | ~64B | Yes | 80-95% | Best compression, tunable |
| IVFSQ8 | 768B | Yes | ~99% | 4x compression, high recall |
| HNSW | 3072B + graph | CPU only | 98-99.5% | Best CPU recall |
| CAGRA (cuVS v1.10+) | graph-based | GPU native | 98-99% | 12x faster build than CPU HNSW |

**FAISS + cuVS Performance Gains (v1.10+):**
- IVF build: up to 4.7x faster than classic GPU
- IVF search: up to 8.1x lower latency at 95% recall
- CAGRA build: up to 12.3x faster than CPU HNSW
- CAGRA search: up to 4.7x faster (Deep100M)
- CAGRA offline throughput: 18x higher (images), 8x (text embeddings)
- CAGRA converts to HNSW for CPU serving (build GPU, serve CPU)

**12GB VRAM Capacity (~9.5GB after model+overhead):**

| Index Type | 768d | 384d | 256d MRL | 128d MRL |
|---|---|---|---|---|
| Flat fp32 | 3.2M | 6.4M | 9.5M | 19M |
| Flat fp16 | 6.4M | 12.8M | 19M | 38M |
| IVFSQ8 | 12.8M | 25.6M | 38M | 76M |
| IVFPQ (m=64) | 30M+ | 50M+ | 75M+ | 150M+ |
| Binary | 88M | 176M | 265M | 530M |

### 2.3 Qdrant
- Rust, 18,200 QPS on SIFT1M (23% faster than Milvus)
- Payload-based filtering integrated into search (not post-processing)
- Binary, scalar, product quantization built-in
- Memory-mapped storage for datasets > RAM
- ACID transactions, horizontal sharding
- No native GPU but fast enough on CPU for <100M

### 2.4 Milvus / Zilliz
- Designed for billions of vectors
- GPU-accelerated indexing (IVF, HNSW)
- Complex to self-host (etcd + MinIO/S3 + message queues)
- IVF_SQ8: ~99% recall rate
- Best when >100M vectors with data engineering team

### 2.5 ChromaDB
- 2025 Rust rewrite: 4x faster writes/queries
- Ceiling: ~500K vectors, 3,200 QPS
- Prototyping only, teams migrate for production

### 2.6 LanceDB
- Embedded (like SQLite), no separate server
- Lance columnar format, Apache Arrow, memory-mapped disk access
- <20ms latency on 1M vectors, ~3ms at 0.90 recall with IVF-PQ
- GPU-accelerated index building (CUDA, Apple MPS)
- Ingest: 3M 512-dim vectors/minute (GPU builder)
- Scales to billions on disk + S3
- Zero-copy: PyArrow, Polars, Pandas, DuckDB
- Best for disk-based KG search, edge deployment

### 2.7 Weaviate
- HNSW with cuVS/CAGRA GPU acceleration
- 4.7x faster build, 2.6x faster query at 1M vectors
- Built-in ML modules, native hybrid search
- ~79 QPS/node (lower raw throughput than Qdrant/Milvus)

### 2.8 Scale Recommendations

| Vector Count | Primary | Alternative |
|---|---|---|
| <500K | FAISS Flat on GPU | ChromaDB for prototyping |
| 500K-5M | FAISS IVFSQ8 GPU | Qdrant, LanceDB |
| 5-10M | FAISS IVFPQ GPU | LanceDB disk, Qdrant mmap |
| 10-50M | LanceDB NVMe SSD | Qdrant with quantization |
| 50-100M | Qdrant binary quant | LanceDB + S3 |
| >100M | Milvus distributed | LanceDB + S3 |

## 3. QUANTIZATION FOR EMBEDDINGS

### 3.1 Methods Compared

| Method | Bytes/Dim | Compression | Recall Loss | Speed Multiplier |
|---|---|---|---|---|
| float32 | 4 | 1x | 0% | 1x |
| float16/bfloat16 | 2 | 2x | ~0% | ~1.5x GPU |
| int8 (SQ8) | 1 | 4x | <1% (rescore) | ~3.66x |
| int4 (SQ4) | 0.5 | 8x | 2-5% | ~5x |
| PQ (m=64) | ~0.083 | 48x | 5-40% tunable | ~10-20x |
| Binary (1-bit) | 0.125 | 32x | 5-15% | ~24.76x |

### 3.2 Memory at Scale (768d, raw vectors)

| Vectors | fp32 | fp16 | int8 | PQ (m=64) | Binary |
|---|---|---|---|---|---|
| 1M | 3.07 GB | 1.54 GB | 0.77 GB | 64 MB | 96 MB |
| 10M | 30.7 GB | 15.4 GB | 7.7 GB | 640 MB | 960 MB |
| 100M | 307 GB | 154 GB | 77 GB | 6.4 GB | 9.6 GB |

### 3.3 Matryoshka Representation Learning (MRL)

Trains embeddings so first N dimensions are most important. Orthogonal to precision quantization -- they stack.

| Dim Reduction | Storage Factor | Quality Retained |
|---|---|---|
| 768 -> 512 | 0.67x | ~99% |
| 768 -> 256 | 0.33x | ~97% |
| 768 -> 128 | 0.17x | ~94% |
| 768 -> 64 | 0.08x | ~90% |

**Combined MRL + Quantization:**
- 768d fp32 -> 256d int8 = 12x compression, ~96% quality
- 768d fp32 -> 256d binary = 96x compression, ~88% quality
- 768d fp32 -> 128d int8 + rescore = 24x compression, ~98% quality with rescore
- 1024d fp32 -> 256d 4-bit (Snowflake v2) = 32x compression, ~97% quality

### 3.4 Binary Quantization Tolerance by Model

| Model | Binary Quality Retention |
|---|---|
| GTE ModernBERT (Alibaba) | ~98% |
| nomic-embed-text v1.5/v2 | ~95% |
| BGE-M3 | ~94% |
| E5-base-v2 | ~92% |
| E5-small-v2 | ~87% |

Models with MRL + quantization-aware training tolerate quantization far better.

### 3.5 PQ Recall Tradeoffs (2025 Research)

- Heavy PQ (m=32, k=16/256) on 100K embeddings: top-10 overlap <10% with exact
- HNSW + SQ8: ~87% recall, high memory
- IVF-PQ: ~61% recall, 7.2x less memory
- Always pair PQ with a rescore stage for acceptable recall

### 3.6 Recommended Quantization Pipeline (12GB VRAM)

**3-stage retrieval for maximum scale:**
1. Binary/PQ search over MRL-truncated vectors (stage 1, GPU)
2. int8 rescore with full dimensions (stage 2, SSD/RAM)
3. Cross-encoder rerank (stage 3, GPU)

**Hot/Cold for 100M vectors (768d):**
- Hot (GPU): PQ codes ~6.4GB + IVF clusters ~300MB + IDs ~800MB = ~7.5GB
- Cold (NVMe SSD): Full int8 vectors for rescoring = 77GB

## 4. SEMANTIC SEARCH TECHNIQUES

### 4.1 Hybrid Search (Dense + Sparse/BM25)

**Performance:**
- Dense alone: ~0.78 recall
- BM25 alone: ~0.72 recall
- Hybrid (dense + BM25): ~0.91 recall, ~0.87 precision
- Three-way (dense + SPLADE + BM25): optimal per IBM research

**For knowledge graphs:**
- Entity names need exact matching (sparse/BM25 strength)
- Relationships need semantic understanding (dense strength)
- BGE-M3 produces both in one forward pass

**Fusion:**
- Reciprocal Rank Fusion (RRF): robust default, no training, rank-based
- Adaptive per-query weighting (2025): +2-7.5pp Precision@1 and MRR@20
- Dynamic Weighted RRF: query specificity informs weights, reduces hallucination

**Implementation:**
- BGE-M3: dense + sparse + multi-vector in one model
- Qdrant/Weaviate/Milvus: native hybrid search
- Separate BM25 (Elasticsearch/tantivy) + FAISS/LanceDB

### 4.2 Cross-Encoder Reranking

**Impact:** 20-35% accuracy improvement, 200-500ms latency

**Best models for 12GB VRAM:**

| Model | Params | Size | BEIR nDCG@10 | Best For |
|---|---|---|---|---|
| ms-marco-MiniLM-L-6-v2 | 22M | ~90MB | ~49 | Fast prototyping |
| ms-marco-MiniLM-L-12-v2 | 33M | ~130MB | ~51 | Best lightweight |
| bge-reranker-v2-m3 | 278M | ~1.1GB | ~51.8 | Best balanced, 100+ langs |
| bge-reranker-large | 560M | ~2.2GB | ~53.5 | Max self-hosted quality |

**Practical:** Rerank 10-30 candidates. Below 10 misses relevant; above 50 latency grows linearly.

### 4.3 Late Interaction / ColBERT v2

- Per-token embeddings + MaxSim for fine-grained matching
- ColBERTv2: 6-10x compression vs v1, PLAID engine 7x faster GPU / 45x faster CPU
- Jina-ColBERT-v2: +6.5% over ColBERTv2, 128d (96/64 via MRL), 89 languages
- For KGs: excels when entity attributes need token-level matching
- Storage: N vectors per document (N = tokens). Short entities (~20-50 tokens) manageable.
- Best as reranking stage, not primary index

### 4.4 Multi-Vector Representations

- BGE-M3: dense + sparse + multi-vector in one forward pass
- For KGs: entity name embedding + description embedding + relationship-context embedding
- Combined retrieval (all three modes) gives best results per BAAI benchmarks

### 4.5 Matryoshka in Practice

- Supported: nomic v1.5/v2, Jina v3/v4, Cohere v4, Snowflake arctic v2, GTE-multilingual-base
- Multi-resolution search: 256d for fast initial, full dim for rescore
- Key optimization for VRAM-constrained setups

## 5. PRACTICAL ARCHITECTURE FOR RTX 4070 SUPER (12GB VRAM)

### 5.1 VRAM Budget

```
Total VRAM:                      12,288 MB
CUDA overhead + scratch:         ~2,000 MB

Option A (speed focus):
  Embedding: nomic v1.5            550 MB
  Reranker: MiniLM-L-12            130 MB
  FAISS GPU index:               9,608 MB  --> ~12M int8 768d vectors

Option B (quality focus):
  Embedding: BGE-M3              2,200 MB
  Reranker: bge-reranker-v2-m3   1,100 MB
  FAISS GPU index:               6,988 MB  --> ~9M int8 768d vectors

Option C (max index):
  Embedding: nomic v1.5            550 MB
  No reranker on GPU                 0 MB
  FAISS GPU index:               9,738 MB  --> ~150M+ PQ vectors
```

### 5.2 Architecture 1: Small Graph (1-5M nodes)
```
Embedding:  nomic-embed-text v1.5 (137M, 550MB, Apache 2.0)
Dimensions: 768d or 256d MRL
Index:      FAISS GpuIndexIVFSQ8 (fits ~5M vectors easily)
Hybrid:     BM25 via tantivy for entity name search
Fusion:     Reciprocal Rank Fusion
Reranker:   ms-marco-MiniLM-L-12-v2 on same GPU (130MB)
Latency:    <10ms search + ~150ms reranking
```

### 5.3 Architecture 2: Medium Graph (5-50M nodes)
```
Embedding:  BGE-M3 (568M, 2.2GB) -- dense + sparse + multi-vector
Index:      FAISS CAGRA (GPU build) -> HNSW (CPU serve)
            OR LanceDB on NVMe SSD with IVF-PQ (GPU build)
Storage:    256d MRL + int8 = 256 bytes/vec = 12.8GB for 50M (SSD)
Hot set:    FAISS IVFPQ on GPU for frequent clusters
Reranker:   bge-reranker-v2-m3 (1.1GB, load to GPU for batch)
Latency:    ~5-20ms search + ~300ms reranking
```

### 5.4 Architecture 3: Large Graph (50M+ nodes)
```
Embedding:  BGE-M3 (batch process, model swap for serving)
Index:      LanceDB on NVMe SSD with IVF-PQ
            OR Qdrant with binary quantization + mmap
Storage:    Binary (256d MRL) = 32 bytes/vec
            100M vectors = 3.2GB binary + 76.8GB int8 on disk
Pipeline:   3-stage:
  1. Binary vector search (sub-ms, 100M+ vectors)
  2. int8 rescore from SSD (top-100, <5ms)
  3. Cross-encoder rerank (top-20, ~200ms)
Total:      ~206ms per query
```

### 5.5 Batch Embedding Throughput

| Model | Params | Est. Throughput | Time for 1M nodes |
|---|---|---|---|
| nomic v1.5 | 137M | 3000-5000 sent/s | 3-6 min |
| arctic-embed-m v2 | 113M | 4000-6000 sent/s | 3-4 min |
| GTE-multilingual-base | 110M | 4000-6000 sent/s | 3-4 min |
| nomic v2 (MoE) | 305M active | 1000-3000 sent/s | 6-17 min |
| BGE-M3 | 568M | 500-1500 sent/s | 11-33 min |

**Optimization tips:**
- fp16/bf16 inference (2x speedup, no quality loss)
- Sort by length before batching (minimize padding)
- batch_size=64-128, convert_to_tensor=True
- HuggingFace TEI server for production
- Pre-tokenize separately (Snowflake research: 16x throughput gain)

### 5.6 CPU Fallback Strategies

1. **Build GPU, serve CPU:** FAISS CAGRA builds 12x faster on GPU, converts to HNSW for CPU
2. **Memory-mapped indexes:** LanceDB/Qdrant serve from SSD, ~10-20ms on NVMe
3. **Tiered hot/cold:** Frequent clusters in GPU, rest in CPU RAM or SSD
4. **Model swapping:** Load embedding model for indexing, unload, load index for serving

### 5.7 Recommended Software Stack

```
Embedding model:    nomic-embed-text v1.5 (speed) or BGE-M3 (quality + hybrid)
Inference server:   HuggingFace TEI or sentence-transformers
Vector index:       FAISS + cuVS/CAGRA (GPU, <10M) or LanceDB (disk, >10M)
Sparse search:      BGE-M3 sparse output OR BM25 via tantivy/OpenSearch
Reranker:           bge-reranker-v2-m3 or ms-marco-MiniLM-L-12-v2
Fusion:             Reciprocal Rank Fusion (RRF)
Quantization:       MRL (256d) + int8 storage, fp16 GPU inference
```

## Lessons Learned

1. **MRL is the single most impactful optimization** for VRAM-constrained setups. 768d -> 256d = 3x storage reduction with ~3% quality loss. Stacks with precision quantization.

2. **BGE-M3 is uniquely powerful for knowledge graphs** -- dense + sparse + multi-vector in one forward pass eliminates need for separate models.

3. **FAISS + cuVS (CAGRA)** is the best GPU-accelerated search option. Build on GPU, serve on CPU is ideal for 12GB VRAM.

4. **LanceDB is the dark horse** -- disk-based with mmap gives <20ms on millions of vectors, minimal RAM, GPU-accelerated builds.

5. **Binary quantization quality varies dramatically by model.** GTE ModernBERT: 98%, E5-small: 87%. Always validate.

6. **7B+ embedding models** won't fit alongside index on 12GB. Use via API or separate GPU.

7. **3-stage retrieval** (binary/PQ -> int8 rescore -> cross-encoder rerank) is the gold standard for constrained hardware.

8. **Hybrid search is not optional for KGs.** Dense-only misses exact keywords and proper nouns. RRF is the robust default fusion.

9. **PQ recall is worse than commonly claimed.** 2025 research: IVF-PQ tops at ~61% recall vs HNSW+SQ8 at ~87%. Always pair PQ with rescore.

10. **nomic v1.5 at 137M params** is the efficiency champion -- tiny footprint leaves maximum VRAM for index.

## Recommendations

1. **Start with nomic-embed-text v1.5** at 256d MRL + int8 for ~38M vectors in GPU memory with room for model + reranker.

2. **Add BM25 hybrid search** for entity names via tantivy or BGE-M3 sparse mode.

3. **Use FAISS CAGRA** for GPU graph index, convert to HNSW for CPU if needed.

4. **For >10M nodes**, use LanceDB on NVMe SSD with GPU-built IVF-PQ. <20ms latency.

5. **Always include a reranker.** ms-marco-MiniLM-L-12-v2 (33M, 130MB) is best lightweight option.

6. **For best quality**, use BGE-M3 for embeddings and bge-reranker-v2-m3 for reranking.

7. **For 100M+ nodes**, implement 3-stage pipeline: binary -> int8 rescore -> cross-encoder. Binary in GPU, int8 on NVMe.
