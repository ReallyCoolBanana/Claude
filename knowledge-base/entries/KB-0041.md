# Distributed Agent Coordination Protocols

## Context
Our multi-agent coordination system has matured through several iterations (SQLite WAL shared state, JSONL message bus, work-stealing, help protocol). We surveyed the broader landscape of distributed coordination protocols to identify where our system fits architecturally, what we can adopt, and how to scale beyond single-machine deployment.

## Method
Compared our implemented coordination patterns against established distributed systems protocols (blackboard systems, Contract Net Protocol, NATS, Ray), emerging AI agent standards (Google A2A, Anthropic MCP), and recent academic work on LLM agent consensus. Mapped our architecture to known patterns and identified scaling paths.

## Result

### Our System in Context
- Our **SQLite WAL system** is architecturally a **blackboard system** — a well-established AI coordination pattern (Erman et al., 1980). Agents read/write shared state, with the coordinator monitoring for convergence. This validates our design as theoretically sound, not ad-hoc.
- Our **work-stealing implementation** operates at **O(1) per steal** (dequeue from victim's tail) vs the **Contract Net Protocol at O(n)** (broadcast task announcement, collect bids, award). For our use case (homogeneous agents, frequent rebalancing), work-stealing is the superior choice.

### Scaling Beyond Single Machine

#### NATS as Bus Replacement
- **NATS** is the best message bus replacement for multi-machine scaling: single Go binary, microsecond publish latency, built-in Raft consensus via JetStream.
- Supports subject-based routing (maps cleanly to our team/channel structure), request-reply (maps to help protocol), and queue groups (maps to work-stealing).
- Can run embedded in Go or as sidecar — no JVM, no Zookeeper, no complex deployment.

#### Ray Actors for Distributed State
- **Ray Actors** provide distributed agent state management proven at scale: 2000+ node clusters at Ant Financial.
- Each agent becomes a Ray Actor with method-based communication — natural fit for our agent model.
- Ray's placement groups could replace our coordinator hub for resource-aware scheduling.

### Industry Standards Convergence
- **Google A2A (Agent-to-Agent)** + **Anthropic MCP (Model Context Protocol)** are now under the **Linux Foundation AAIF** (AI Agent Interoperability Forum), with OpenAI, Anthropic, Google, Microsoft, and AWS as members.
- A2A handles agent discovery and task delegation; MCP handles tool/resource access. Together they define a standard agent communication layer.
- Our system predates these standards but aligns well — our help protocol maps to A2A task delegation, our tool definitions map to MCP resources.

### LLM Agent Consensus
- The **Aegean protocol** (recent research) demonstrates that LLM agents need **stochastic consensus**, not deterministic Raft/Paxos. LLM outputs are inherently non-deterministic, so consensus must handle disagreement differently — through debate rounds and confidence-weighted voting rather than log replication.
- This validates our think-tank approach (convergence through discussion) over trying to force deterministic agreement between agents.

## Lessons Learned
- Our architecture is more theoretically grounded than we realized — blackboard systems and work-stealing are decades-old patterns with deep research behind them.
- The single-machine constraint is actually an advantage: SQLite WAL gives us ACID guarantees and sub-millisecond latency that no distributed system can match.
- A2A/MCP standardization means our agents could eventually interoperate with external agent ecosystems, but the standards are still early (2025-2026).
- Stochastic consensus is a fundamentally different problem from distributed systems consensus — applying Raft to LLM agents would be architecturally wrong.

## Recommendations
- **Keep SQLite WAL for single-machine coordination** — it is optimal for this use case and adding distributed consensus would only add latency and complexity.
- **Adopt NATS for bus scaling** when multi-machine deployment is needed. Migration path: replace JSONL file bus with NATS subjects, keep SQLite WAL for local state per machine, use NATS JetStream for cross-machine state sync.
- **Adopt A2A for agent discovery** when interoperating with external agent systems. Our help protocol is already close to A2A's task delegation model.
- **Do not adopt Raft/Paxos** for agent agreement — use our think-tank convergence model, which naturally handles the stochastic nature of LLM reasoning.
- Evaluate Ray Actors if we need 100+ agent scaling — overkill for current 6-18 agent deployments.

# TOCTOU Bug Fixes in Coordination System

## Context
KB-0035 identified rate limiter TOCTOU as one of top 3 weak links. A comprehensive audit (Archiver 3) found 22 TOCTOU/concurrency bugs across the coordination system — 2 Critical, 5 High, 9 Medium, 6 Low. This session fixed the 2 Critical and 2 highest High-severity bugs.

## Method
Applied two fix patterns based on Researcher 3's analysis:
1. **Single-statement UPDATE...WHERE** — eliminates TOCTOU entirely by combining check and action in one SQL statement. Used `cursor.rowcount` to detect precondition failure.
2. **BEGIN IMMEDIATE transaction** — acquires write lock immediately, serializing the read-modify-write cycle across processes. Added ROLLBACK in except blocks.

## Result
4 bugs fixed:

| Bug | Severity | File | Fix Pattern |
|-----|----------|------|-------------|
| TOCTOU-WS-001 | Critical | `work_stealing.py:complete_work` | Single-statement UPDATE...WHERE claimed_by=? |
| TOCTOU-HP-001 | Critical | `help_protocol.py:fulfill_help` | BEGIN IMMEDIATE wrapping SELECT + 2 UPDATEs |
| TOCTOU-DC-001 | High | `direct_channels.py:join_channel` | BEGIN IMMEDIATE for JSON participants RMW |
| TOCTOU-DC-002 | High | `direct_channels.py:leave_channel` | BEGIN IMMEDIATE for JSON participants RMW |

Stress tests written (`tests/test_toctou_fixes.py`) using threading.Barrier for maximum contention, 5 rounds each, separate DB connections per thread.

## Lessons Learned
1. **Single-statement UPDATE...WHERE is superior** to BEGIN IMMEDIATE when feasible — eliminates the race entirely vs serializing it
2. **threading.Lock + BEGIN IMMEDIATE serve different purposes**: Lock protects the Python connection object within a process; BEGIN IMMEDIATE protects across processes
3. **In WAL mode, BEGIN IMMEDIATE and BEGIN EXCLUSIVE behave identically** — use IMMEDIATE for convention consistency
4. The existing `@_retry_on_busy` decorator already handles SQLITE_BUSY from BEGIN IMMEDIATE contention
5. **18 bugs remain** (3 High, 9 Medium, 6 Low) — documented in `archiver_toctou_catalog.json`

## Recommendations
1. Next priority fixes: TOCTOU-WS-002 (start_stage), TOCTOU-HP-002 (request_help), TOCTOU-MTR-004 (double stop)
2. Use single-statement UPDATE...WHERE pattern wherever possible — it's the simplest and safest
3. Run `python -m pytest storage/coordination/tests/test_toctou_fixes.py` to verify fixes hold
4. Consider adding these stress tests to CI pipeline
