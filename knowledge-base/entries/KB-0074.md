# Hybrid Adaptive Architecture: Complete Technical Deep-Dive

Deep breakdown of Structure 8 (Hybrid Adaptive) from KB-0073, covering all four major subsystems: Hub Brain Dual-Role, Migration Protocol, Metrics & Triggers, and Evolution Path & VRAM Management.

## 1. Hub Brain Dual-Role Subsystem

The hub brain (Qwen3-4B) serves two roles simultaneously — this is the central architectural tension.

### 1.1 Role A: Query Router (Real-Time)

**The <100ms constraint is impossible with LLM inference alone.** At 75 tok/s on RTX 4070 Super, even a 5-token JSON response takes ~65ms + prefill overhead. Solution: two routing tiers.

**Tier 1 — Embedding Classifier (primary, <15ms):**
Embed the query with nomic-embed-text-v1.5 (384-dim Matryoshka), cosine similarity against pre-computed domain centroids (one per core). FAISS IndexFlatIP on 20 centroids = <0.1ms search. Total: ~10-15ms.

```python
class EmbeddingRouter:
    def __init__(self, model_path, centroid_path):
        self.embed_model = SentenceTransformer(model_path)
        self.centroids = np.load(centroid_path)  # (n_cores, 384)
        self.index = faiss.IndexFlatIP(384)
        self.index.add(self.centroids)

    def route(self, query, top_k=2):
        vec = self.embed_model.encode(
            [f"search_query: {query}"], normalize_embeddings=True
        )[:, :384]
        vec = vec / np.linalg.norm(vec, axis=1, keepdims=True)
        scores, indices = self.index.search(vec, top_k)
        return {
            "primary_core": self.core_names[indices[0][0]],
            "confidence": float(scores[0][0]),
        }
```

Escalation to Tier 2 when: `primary_score < 0.65` OR `primary_score - secondary_score < 0.10`.

**Tier 2 — LLM Constrained Routing (fallback, ~300-600ms):**
Qwen3-4B with GBNF grammar constraint forces JSON-only output (no preamble). llama.cpp `cache_prompt: true` caches the system prompt KV tensors — only the variable query portion needs prefill. Context: 512 tokens total (200 system + 280 query + 60 output).

```bnf
# routing-plan.gbnf
root ::= "{" ws '"cores"' ws ":" ws "[" ws core-id ("," ws core-id)* "]" ws
  "," ws '"intent"' ws ":" ws intent ws
  "," ws '"strategy"' ws ":" ws strategy ws
  "," ws '"confidence"' ws ":" ws number ws "}"
core-id ::= '"encyclopedic"' | '"procedural"' | '"research"' | '"personal"' | '"synthesis"'
intent ::= '"lookup"' | '"analysis"' | '"traversal"' | '"synthesis"'
strategy ::= '"sequential"' | '"parallel"' | '"single"' | '"cascade"'
```

**Expected distribution:** ~70-80% Tier 1 (<15ms), ~15-25% Tier 2 (~300-600ms), ~5% cross-domain synthesis.

**Routing Plan JSON output:**
```json
{
  "cores": ["encyclopedic", "research"],
  "intent": "analysis",
  "strategy": "parallel",
  "confidence": 0.82
}
```

### 1.2 Role B: Meta-Architect (Background, Async)

Runs as a separate async background task on the same GPU. Evaluates restructuring every 15 minutes.

**Decision logic is hybrid: rules first, LLM for refinement.**

Rule engine fires on deterministic conditions (overloaded core >45%, dead core <2%, etc.). If rules trigger, the LLM receives the metrics summary + triggered rules and generates a structured restructuring proposal JSON. If no rules trigger, the LLM is not called.

**Restructuring Proposal JSON schema:**
```json
{
  "action": "split_core",
  "confidence": 0.82,
  "risk_level": "medium",
  "rationale": "Encyclopedic core handles 52% of queries...",
  "target_core": "encyclopedic",
  "new_core_spec": {
    "name": "encyclopedic-wikipedia",
    "domain_description": "Wikipedia articles, broad world knowledge",
    "vram_budget_gb": 0.5
  },
  "expected_improvement": {
    "metric": "load_balance_gini",
    "current_value": 0.42,
    "projected_value": 0.25
  },
  "human_review_required": true
}
```

**Human-review gate (auto-escalation when):**
- `risk_level` is "high" or "critical"
- `confidence` < 0.85
- Action is "remove_core" or "merge_cores"
- Same action was proposed and rejected in last 7 days
- System has been stable < 48h since last restructuring

### 1.3 Thread/Process Separation

**Recommended: Single llama-server with `--parallel 2` + async priority queue.**

```python
class Priority(IntEnum):
    ROUTER = 10      # highest
    SYNTHESIS = 5    # mid
    META_ARCH = 1    # lowest — never blocks routing

class PriorityInferenceQueue:
    async def submit(self, request, priority):
        future = asyncio.get_event_loop().create_future()
        await self.queue.put((-priority.value, request, future))
        return future
```

Router requests always jump ahead of meta-architect requests. Collision probability is low (meta-architect runs once per 15 minutes). When collision occurs, the meta-architect request waits for the current token stream to complete (~100-2000ms).

**Alternative (if interference measured):** Two llama-server instances on same GPU. Cost: 2×2.7GB = 5.4GB for hub models alone. Only worth it if router latency degrades >50ms from meta-architect interference.

### 1.4 Failure Modes

**Bad restructuring decision:** Detected by 48-hour reward signal comparing pre/post metrics (latency, load balance, error rate, cache hit rate, VRAM headroom). Automated rollback if error_rate increases >15% or latency >200% above pre-restructuring baseline. Config snapshots kept for last 3 versions.

**Prompt injection via knowledge graph:** Mitigated by structural isolation — the meta-architect's metrics summary contains only routing event statistics (query hashes, latencies, counts), never document content. Additional layers: injection pattern scanning on ingest, schema validation on all LLM outputs, action whitelist per confidence band.

## 2. Migration Protocol

### 2.1 Core Registry and Routing Table (SQLite)

```sql
CREATE TABLE core_registry (
    core_id       TEXT PRIMARY KEY,
    core_type     TEXT NOT NULL,
    status        TEXT NOT NULL DEFAULT 'active',  -- active|shadow|draining|decommissioned
    vram_mb       INTEGER NOT NULL,
    node_count    INTEGER NOT NULL DEFAULT 0,
    edge_count    INTEGER NOT NULL DEFAULT 0,
    db_path       TEXT NOT NULL,
    partition_key TEXT,         -- JSON: {"type":"label","values":["code","api"]}
    parent_core_id TEXT,
    created_at    REAL NOT NULL
);

CREATE TABLE routing_table (
    route_id     INTEGER PRIMARY KEY AUTOINCREMENT,
    pattern      TEXT NOT NULL,
    pattern_type TEXT NOT NULL,  -- label_match|prefix|cluster_id|catchall
    core_id      TEXT NOT NULL,
    priority     INTEGER NOT NULL DEFAULT 100,
    is_fallback  INTEGER NOT NULL DEFAULT 0,
    valid_from   REAL NOT NULL,
    valid_until   REAL,
    created_by_txn TEXT
);

CREATE TABLE transitions_in_progress (
    transition_id    TEXT PRIMARY KEY,
    operation        TEXT NOT NULL,  -- SPLIT|MERGE|ADD|REMOVE
    state            TEXT NOT NULL DEFAULT 'allocated',
    source_cores     TEXT NOT NULL,  -- JSON array
    target_cores     TEXT NOT NULL,  -- JSON array
    timeout_at       REAL NOT NULL,  -- hard deadline (1 hour default)
    lock_holder      TEXT NOT NULL
);

-- Only one active transition at a time
CREATE UNIQUE INDEX idx_one_active_transition
    ON transitions_in_progress (operation)
    WHERE state NOT IN ('completed', 'failed', 'rolled_back');
```

### 2.2 State Machine

```
SPLIT / MERGE:
  [ALLOCATED] → [DUAL_WRITE] → [CONSISTENCY_CHECK] → [DRAINING] → [PROMOTING] → [DECOMMISSIONING] → [COMPLETED]
       ↓              ↓                ↓
  [ROLLED_BACK]  [ROLLED_BACK]  [ROLLED_BACK]

ADD (trivial):
  [ALLOCATED] → [REGISTERING] → [COMPLETED]

REMOVE:
  [DRAINING] → [REROUTING] → [DECOMMISSIONING] → [COMPLETED]
```

### 2.3 SPLIT Operation Step-by-Step

**Phase 1 — Shadow Allocation (~5 min):**
1. Acquire global migration lock (UNIQUE INDEX enforces one-at-a-time)
2. Compute partition plan. **Strategy A (recommended): Label-based** — each node has labels, assign labels to partitions by mapping. No VRAM cost, deterministic. **Strategy B: Embedding cluster** — mini-batch k-means (k=2) on 10K-node sample, assign all nodes by nearest centroid. More semantic but requires ~30MB RAM for sample.
3. Create shadow core SQLite databases (WAL mode, `synchronous=NORMAL`)
4. Bulk copy nodes in 5K batches. 150K nodes = 30 batches, ~1.5-3 seconds total
5. Build HNSW indexes for shadows: ~8-15 seconds for 150K vectors at dim=768
6. Handle cross-partition edges: edges spanning B1↔B2 go into `cross_core_edges` table in hub DB. Expect 15-25% of edges to be cross-partition.

**Phase 2 — Dual Write (~10-30 min):**
- Routing table updated: shadow routes added at higher priority, old core becomes fallback
- New writes go to BOTH old core AND appropriate shadow
- Reads continue hitting old core (shadows are write-only during this phase)
- Dual-write log (sampled at 10%) for audit trail
- Nodes with labels spanning both partitions: majority-vote assignment, forwarding stub in the other partition

**Phase 3 — Consistency Check:**
Six verification passes:
1. Node count: source == B1 + B2
2. Node ID completeness: no orphans (union of B1∪B2 == source)
3. Edge integrity: source edges == B1 edges + B2 edges + cross_core_edges
4. Dual-write completeness: all writes during Phase 2 reflected in shadows
5. HNSW index health: spot-check 100 random nodes, verify self-nearest-neighbor
6. Checksum sampling: hash-based statistical integrity on 1K-node sample

**Phase 4 — Drain and Decommission:**
- Old core set to read-only, poll `inflight_queries` table every 100ms
- 30-second drain timeout. If exceeded: soft abort (mark stuck queries as expired)
- Atomic routing table swap: expire old routes, promote shadow routes
- VRAM reclamation: move tensors to CPU, close connections, archive old DB (keep 7 days)

### 2.4 MERGE Operation

Reverse of SPLIT. Key differences:
- Three write destinations (both sources + merge target) during dual-write = highest risk
- HNSW indices cannot merge in-place — rebuild from scratch (~8-15s for 150K nodes)
- Deduplication on merge: `ON CONFLICT DO UPDATE SET data = CASE WHEN excluded.updated_at > nodes.updated_at...`
- Hub brain requires higher confidence (0.85 vs 0.75) before initiating

### 2.5 ADD (Functional Core)

Trivial: allocate VRAM, create empty DB, register in core_registry, add routing rules. No data migration. VRAM budget check: verify `allocated + required <= available` before proceeding.

### 2.6 Edge Cases

**OOM during shadow allocation:** Safe — routing table is NOT modified until Phase 2. Cleanup: deregister shadow cores, delete partial DBs, free HNSW indices. Core-B continues unmodified.

**Dual-write divergence:** DualWriteWatchdog runs every 30s, compares node counts (B1_recent + B2_recent should == source_recent). Recovery: replay missing writes from source.

**Drain timeout with in-flight queries:** Force-drain marks stuck queries as abandoned. Callers wrapped in `safe_query()` retry against promoted shadow core on `SQLITE_INTERRUPT`.

**VRAM insufficient for transition:** Offload LRU core to CPU first. If still insufficient, defer migration. Shadow HNSW indices are built on CPU/RAM, not VRAM.

### 2.7 Performance Impact

**Naive synchronous dual-write: 20-40% degradation.** Sources: dual SQLite commits per write, hub coordination DB lock contention (WAL checkpoint stalls), HNSW index maintenance.

**With async shadow writes (100ms buffer): ~5-8% degradation.** Shadow writes queued in ring buffer, flushed every 100ms. Reads still fall back to old core. Inconsistency window: max 100ms.

## 3. Metrics Ledger and Self-Restructuring Triggers

### 3.1 Metrics Collection

**Per core, per 60-second interval:**
- Query count (atomic counter, ~0 cost)
- p50/p95/p99 latency in microseconds (reservoir sample, sort 1K samples in <1ms)
- VRAM used/free (pynvml, ~0.1ms per call — NOT nvidia-smi subprocess)
- Cache hits/misses (intercepted at dispatch layer)
- Cross-core join count + top-10 join pairs (JSON blob, bounded)
- Error/timeout counts
- Poor result count (hub scores relevance < threshold)
- Semantic drift (centroid cosine distance, updated on ingest)

**SQLite schema (STRICT mode, WAL, separate DB from coordination):**
```sql
CREATE TABLE metrics_ledger (
    id            INTEGER PRIMARY KEY,
    ts            INTEGER NOT NULL,        -- Unix epoch seconds
    core_id       TEXT    NOT NULL,
    query_count   INTEGER NOT NULL DEFAULT 0,
    p50_us        INTEGER NOT NULL DEFAULT 0,  -- microseconds as INTEGER
    p95_us        INTEGER NOT NULL DEFAULT 0,
    p99_us        INTEGER NOT NULL DEFAULT 0,
    vram_used_mb  INTEGER NOT NULL DEFAULT 0,
    vram_free_mb  INTEGER NOT NULL DEFAULT 0,
    cache_hits    INTEGER NOT NULL DEFAULT 0,
    cache_misses  INTEGER NOT NULL DEFAULT 0,
    join_count    INTEGER NOT NULL DEFAULT 0,
    join_pairs    TEXT    NOT NULL DEFAULT '{}',  -- JSON top-10
    error_count   INTEGER NOT NULL DEFAULT 0,
    poor_result_count INTEGER NOT NULL DEFAULT 0,
    total_scored  INTEGER NOT NULL DEFAULT 0,
    centroid_cos_dist REAL NOT NULL DEFAULT 0.0
) STRICT;
```

**Overhead:** <10ms CPU/min, <5MB RAM, 5 SQLite writes/min. Negligible.

**Retention:** Raw 60s data: 30 days (~216K rows, ~43MB). Hourly rollups: 1 year (~44K rows, ~4MB). Nightly purge + VACUUM at 03:00.

### 3.2 The Seven Triggers

| # | Trigger | Threshold | Window | Priority | Response |
|---|---------|-----------|--------|----------|----------|
| 1 | **Load Imbalance** | >45% queries to one core | 30 min | HIGH | Split candidate |
| 2 | **Latency Degradation** | p95 > 3× baseline | 10 min | HIGH | Split or offload |
| 3 | **Cross-Core Join Freq** | >30% queries join same pair | 2 hours | MEDIUM | Merge or bridge core |
| 4 | **Dead Core** | <2% queries | 7 days | LOW | Hibernate or merge |
| 5 | **VRAM Pressure** | <1.5GB free | 5 min | CRITICAL | Emergency eviction |
| 6 | **Semantic Drift** | New content >0.4 cosine from centroid | Per ingest | MEDIUM | Reclassify or new core |
| 7 | **Query Pattern Novelty** | >15% poor results | 7 days | MEDIUM | Add functional core |

**Threshold calibration rationale:**

- **45% load imbalance:** In a 5-core system, fair share is 20%. At 45%, one core handles 2.25× fair share. Below 35% is often transient (query burst). Must exceed minimum 30 queries in window.
- **3× latency baseline:** Baseline is 7-day rolling average of median-hour p95. 2× could be a slow query distribution shift; 3× is rarely benign (usually VRAM pressure or index fragmentation). Cold start: use absolute 5-second threshold until 7 days of data accumulate.
- **30% cross-core joins:** Below 15% is normal cross-domain activity. At 30% for a specific pair, the boundary is structurally wrong — join coordination overhead (200-800ms) compounds.
- **<2% dead core, 7 days:** Weekend-aware: computes weekday vs weekend share separately. Minimum 100 total system queries to avoid noise.
- **<1.5GB VRAM free:** Minimum for loading a new core (~1.1GB model + overhead). Polled every 5 seconds (separate from 60s metrics cycle). Account for display compositor (~200MB).
- **0.4 cosine drift:** In nomic-embed space, 0.3-0.5 = adjacent domains. 0.4 catches genuinely misplaced content without flagging related-but-slightly-off-topic material. Online centroid updated via Welford's algorithm (~1.5KB RAM per core).
- **15% poor results:** Well-tuned system produces 5-8% from genuinely novel queries. Above 15% is systematic. Minimum 20 scored queries to prevent false alarm from small samples.

### 3.3 Trigger Conflict Resolution

When multiple triggers fire simultaneously, priority ordering resolves conflicts:

| Conflict | Resolution |
|----------|-----------|
| Load Imbalance + VRAM Pressure | VRAM wins. Evict LRU core first. Defer split until VRAM stable. |
| Latency Degradation + VRAM Pressure | Causally linked. Fix VRAM first; latency self-resolves. |
| Dead Core + Cross-Core Join (same core) | Paradox: rarely queried directly but frequently joined. Convert to functional/reference core, not merge. |
| Semantic Drift + Load Imbalance (same core) | Reinforcing signals. Elevate to HIGH. Split using drift-batch centroid as boundary. |
| Query Novelty + Semantic Drift (same core) | Correlated. Investigate: is routing misclassifying, or does coverage need expansion? |

### 3.4 Observation Mode (First 90 Days)

All metrics collected, all triggers detected, but NO automatic actions taken. Instead, logs what it *would* have done to `restructuring_log` with `action_taken = 'observation_only'`.

**Graduation requirements:**
1. Baselines for all cores with ≥720 hourly data points (30 days)
2. No routing logic bugs found in decision log
3. At least one complete weekly cycle captured per core
4. Operator explicitly enables `allow_auto_restructuring = true`

**Graduated caution:** First 3 restructuring events are "supervised active mode" — proposed, not auto-executed. After 3 successful events with positive reward signals, system moves to fully autonomous.

### 3.5 The 48-Hour Reward Signal

Reward = weighted sum of improvements:

```
latency_improvement   × 0.35  (lower p95 = better)
load_balance_gini     × 0.25  (lower Gini = more balanced)
error_rate_delta      × 0.20  (fewer errors = better)
cache_hit_improvement × 0.10  (higher hit rate = better)
vram_headroom_delta   × 0.10  (more free VRAM = better)
```

Score range: -1.0 (bad) to +1.0 (good). Automated rollback if score indicates severe degradation (error_rate +15% or latency +200%).

**In-context learning:** The hub brain's restructuring prompt includes the last 5 restructuring outcomes and their reward scores. This provides crude but effective few-shot learning without fine-tuning. Over 10-20 events, the hub develops calibrated intuition for which actions produce positive outcomes.

## 4. Evolution Path and VRAM Management

### 4.1 Static VRAM Budget (All Phases)

| Component | VRAM |
|-----------|------|
| Hub Brain (Qwen3-4B Q8_0, 4K ctx) | 2.80 GB |
| Shared Embedding (nomic-embed-text-v1.5 384-dim) | 0.32 GB |
| FAISS scratch + CUDA overhead | 0.33 GB |
| **Static total** | **3.45 GB** |
| **Dynamic pool** | **8.55 GB** |
| **Restructuring headroom (reserved)** | **2.00 GB** |
| **Usable for cores** | **6.55 GB** |

### 4.2 Phase 1: 100K Edges (Day 1 — ~3 months)

**Critical design decision: Sub-AI cores are embedding + retrieval only.** No per-core generative models. All NL generation through the hub brain. Only exception: Synthesis core runs Qwen3-0.6B Q8_0 (~0.75GB) for cross-domain merging.

| Core | Domain | VRAM | Index Type |
|------|--------|------|-----------|
| Encyclopedic | Wikipedia, papers | 0.22 GB | FAISS FlatIP (40K×384) |
| Procedural | SOPs, scripts | 0.08 GB | FAISS FlatIP (10K×384) |
| Research | Market, citations | 0.06 GB | FAISS FlatIP (8K×384) |
| Personal | Notes, bookmarks | 0.04 GB | FAISS FlatIP + SQLite FTS5 |
| Synthesis | Cross-domain joins | 0.80 GB | Qwen3-0.6B Q8_0 (2K ctx) |

**Total Phase 1: 4.65 GB** (7.35 GB free headroom — very comfortable).

**Shared embedding model:** Always resident (0.32GB), all cores call it through an async queue with 10ms batch accumulation window. Throughput: ~2,000-5,000 sentences/sec at batch_size=64. The bottleneck is hub brain generation (~70-80 tok/s), not embedding.

**Graph store:** Msgpack binary adjacency dict in RAM. 100K edges × ~500 bytes = ~50MB. Trivial. Not in VRAM.

**Why FAISS FlatIP, not IVF-PQ?** At <200K vectors, flat GPU search is sub-millisecond. IVF-PQ only earns its complexity above ~500K vectors.

### 4.3 Phase 2: 500K Edges (6-12 months)

**First splits occur.** The system decides WHERE to split based on:
1. **Load imbalance** — Encyclopedic gets >45% of queries for 30+ minutes
2. **Intra-core semantic variance** — k-means k=2 on core embeddings produces two clusters with cosine distance >0.5 between centroids
3. **Cross-core join frequency** — same two cores consistently joined in >30% of queries

**Typical split:** Encyclopedic → Wikipedia (exploratory queries) + KB-Structured (lookup-precise queries). Different query patterns, different semantic clusters.

**Tiered embedding strategy begins:**
- Hot (VRAM): FAISS indexes for all cores, ~200-300MB total
- Warm (RAM): Full adjacency dict (~250MB at 500K edges), recently-accessed node metadata in LRU cache
- Cold (NVMe): Raw node files, full text, SQLite per-core databases
- Cache miss penalty: ~40ms (FAISS hit 1ms + SQLite 3ms + NVMe read 10ms + context construction 10ms + reranking 15ms)

**Temporal Reasoner core appears:** CPU-only analytics core (zero VRAM). Monitors access velocity, promotion/demotion flux, seasonal cycles. Produces temporal summaries for the hub. Triggered when >6 months of timestamped data and temporal queries show consistently poor results.

### 4.4 Phase 3: 1M Edges (12-24 months)

**9-10 active cores, per-core VRAM drops to ~0.87GB average.** In practice, heterogeneous:

| Core | VRAM | Contents |
|------|------|----------|
| Wikipedia | 0.50 GB | FAISS IVF-PQ (~200K vectors) |
| KB-Structured | 0.35 GB | FAISS FlatIP |
| Procedural | 0.25 GB | FAISS FlatIP |
| Research | 0.40 GB | FAISS IVF-PQ |
| Market | 0.30 GB | FAISS FlatIP + time-series |
| Personal | 0.20 GB | FAISS FlatIP |
| Synthesis | 0.80 GB | Qwen3-0.6B Q8_0 |
| Temporal Reasoner | 0.00 GB | CPU-only |
| Code/Scripts | 0.25 GB | FAISS FlatIP |
| **Total cores** | **3.05 GB** | |
| **Grand total** | **6.50 GB** | 5.50 GB free |

**LRU subgraph caching:** Cache unit = 2-hop neighborhood from seed node. `cachetools.LRUCache(maxsize=2000)` keyed by `(node_id, depth, min_weight)`. ~10MB RAM total. Expected hit rate: 60-75% for session-based usage. Cache invalidation: reverse index `node_id → cache_keys`, invalidate on write.

**N-gram query prediction:** Bigram/trigram table over query→query transitions (using top-3 FAISS result node IDs as stable identifiers). Hit rate: 30-50% for session-based usage, 10-20% for random access. Prefetches predicted neighborhoods into subgraph cache. Reduces latency from ~15ms to ~1ms for predicted queries.

**FAISS upgrade:** Large cores (>200K vectors) migrate from FlatIP to `OPQ32,IVF2048,PQ16` with nprobe=32: ~90-95% recall at 1-3ms latency.

### 4.5 Phase 4: 10M Edges (24+ months)

**Hibernation model:** Only 4-5 cores active in VRAM at any time.

**Cold start time breakdown:**
- Retrieval-only cores (no LLM): ~200ms (NVMe read 30ms + GPU transfer 50ms + index init)
- Cores with Qwen3-0.6B: 2-5 seconds (model load dominates)
- Cores with larger models: 10-30 seconds

**Minimizing cold start:**
1. `mlock()` on FAISS index files — OS keeps them in RAM buffer cache
2. GGUF files in tmpfs (RAM disk) for near-instant model load
3. Stagger evictions: delay 30 seconds before hibernating to catch follow-up queries

**Speculative loading:** Co-occurrence matrix (15×15, trivially small) tracks which cores activate together in sessions. When Core-A activates and co-occurrence predicts Core-C with >0.4 probability, begin background loading. Expected accuracy: 60-75% for consistent workflows.

**Tiered memory hierarchy:**
- Hot (VRAM): Active FAISS indexes (4-5 cores) ~8-10GB
- Warm (RAM): Active adjacency dicts, metadata LRU, subgraph cache ~3-5GB
- Cold (NVMe): All edge files, all node JSON, hibernated FAISS indexes ~15-25GB

**32GB RAM feasibility at 10M edges:** Yes. Key: partition adjacency dict by core, only active cores' edges in RAM. 4 active cores × 2.5M edges × 80 bytes = ~800MB RAM for active adjacency. Total RAM: ~9-12GB used, 20-23GB free.

### 4.6 VRAM Monitoring

**Primary: pynvml (nvidia-ml-py)** — 100-500× faster than nvidia-smi subprocess (~0.1-0.5ms vs 50-200ms). Initialize once at startup.

```python
class VRAMGuard:
    WARN_FREE_MB = 2000    # warning threshold
    CRITICAL_FREE_MB = 512  # shed load immediately

    def _loop(self):
        while True:
            free = get_vram_free_mb()
            if free < self.CRITICAL_FREE_MB:
                self._shed_load()  # unload LRU core, reduce KV cache
            time.sleep(2.0)  # 2-second poll
```

**Burst handling (11.5GB/12GB):**
1. KV cache quantization (`--cache-type-k q8_0 --cache-type-v q8_0`) — preemptive, cuts KV by ~50%
2. Dynamic context window reduction (8K → 4K) when VRAM warning threshold hit
3. Evict Synthesis core (~0.80GB freed) — hub handles synthesis at reduced quality
4. Request queuing with 10-second timeout — wait for in-flight query KV cache to free
5. `torch.cuda.empty_cache()` to release PyTorch's caching allocator

| 4 | 4-5 | Meta-architect loop: rule engine → LLM refinement → proposal validation | Background intelligence |
| 5 | 5-6 | Config snapshots, rollback, post-restructuring health monitor | Safety net |
| 6 | 6-7 | Injection scanner, proposal sanity checks, systemd hardening | Security |

**The single most important early decision:** Build the centroid routing index FIRST. Test with 200 sample queries, plot with UMAP colored by domain. If domain clusters exist in embedding space (they will), the two-tier architecture is sound. If not, rethink core taxonomy before building anything else.

## 6. Key Design Principles

1. **All NL generation through hub brain.** Sub-cores are retrieval pipelines. Only Synthesis core runs a (tiny) generative model.
2. **Embedder is shared infrastructure.** One model, one GPU process, async queue. Never duplicate.
3. **FAISS flat until you measure slowness.** IVF-PQ only above 200K vectors per core.
4. **2GB free VRAM before any restructuring.** Budget for dual-write shadow cores explicitly.
5. **No restructuring without 90 days of baseline.** Every split/merge cites specific metrics.
6. **Hibernation over vertical scaling.** You're rarely querying all domains simultaneously.
7. **The routing table is the control plane.** Data layer changes asynchronously and independently.
8. **Conflict resolution by priority, not timestamp.** Fix stability first, then optimize structure.
