## Context
Deep research crawl covering all major aspects of training GNNs on consumer hardware (RTX 4070 Super, 12GB VRAM) for knowledge graph applications. Covers frameworks, architectures, embedding models, scaling strategies, and continual learning. Research conducted March 2026.

## 1. PyTorch Geometric (PyG)

### Latest Version
- **PyG 2.7** (latest stable), compatible with PyTorch 2.8
- 53 contributors, 282+ commits since 2.6

### Key Features by Version
| Version | Key Features |
|---------|-------------|
| **2.7** | Full PyTorch 2.8 compatibility |
| **2.6** | `torch_geometric.nn.nlp` sub-package, SentenceTransformer integration, GRetriever (LLAMA2 + GAT for KG QA), new `Index` class |
| **2.5** | First in-house distributed training via `torch_geometric.distributed`, METIS graph partitioning, DDP + RPC |
| **2.4** | Full `torch.compile` support with `dynamic=True` for varying graph sizes |

### NeighborLoader (Mini-Batch Training)
- **Purpose**: Enables mini-batch training on graphs too large for full-batch (solves OOM)
- **Key parameters**:
  - `num_neighbors`: list controlling samples per hop (e.g., `[25, 10]` for 2-layer)
  - `subgraph_type`: `"directional"`, `"bidirectional"`, or `"induced"`
  - `time_attr`: temporal sampling (neighbors must have earlier timestamps)
  - `weight_attr`: weighted/biased sampling
  - `disjoint`: each seed gets its own subgraph
- **Heterogeneous support**: Works with both `Data` and `HeteroData`; samples up to `num_neighbors` per edge type
- **LinkNeighborLoader**: Extension for link prediction tasks with negative sampling
- **HGAM** (Hierarchical Graph Adjacency Matrix): Eliminates redundant computation for nodes that don't contribute at later hops via `trim_to_layer()`
- **Performance**: Supports multi-process loading (`num_workers`), CSC format caching, `filter_per_worker` control

### HeteroConv for Heterogeneous Graphs
- Generic wrapper for per-edge-type convolution operators
- Unlike `to_hetero()` (same operator for all edge types), HeteroConv allows **different operators per edge type**
- Example: GCNConv for paper-cites-paper, SAGEConv for author-writes-paper, GATConv for paper-written_by-author
- Aggregation strategies: `"sum"`, `"mean"`, `"max"` for multi-relation destinations
- Supports edge attributes via `edge_attr_dict`

### 12GB VRAM Feasibility
**Highly feasible.** PyG's NeighborLoader and mini-batch training are specifically designed for memory-constrained environments. A 100K-node, 1M-edge knowledge graph can be trained comfortably on 12GB with proper sampling.

### Practical Recommendations
- Use NeighborLoader with `num_neighbors=[15, 10]` as a starting point
- Enable `torch.compile(dynamic=True)` for speed (PyG 2.4+)
- Use HeteroConv for heterogeneous KGs with different relation semantics
- Use HGAM/`trim_to_layer()` to reduce wasted computation
- Consider cuGraph-PyG for GPU-accelerated sampling (2-8x speedup)

**Sources**: [PyG Releases](https://github.com/pyg-team/pytorch_geometric/releases), [PyG Docs](https://pytorch-geometric.readthedocs.io/), [NeighborLoader Tutorial](https://pytorch-geometric.readthedocs.io/en/2.5.2/tutorial/neighbor_loader.html), [HeteroConv Docs](https://pytorch-geometric.readthedocs.io/en/latest/generated/torch_geometric.nn.conv.HeteroConv.html), [NVIDIA PyG Release Notes](https://docs.nvidia.com/deeplearning/frameworks/pyg-release-notes/overview.html)

## 3. GraphSAGE

### Architecture
- Inductive learning: learns aggregation functions (not fixed embeddings), generalizes to unseen nodes
- Sampling-based: fixed-size neighborhood sampling per hop
- Aggregators: mean, max-pool, LSTM (mean recommended as default)

### Neighborhood Sampling Best Practices
| Parameter | Recommended | Notes |
|-----------|-------------|-------|
| **Num layers** | 2-3 | More causes neighborhood explosion |
| **Hop 1 samples** | 15-25 | Higher = better accuracy, more memory |
| **Hop 2 samples** | 10 | Diminishing returns beyond this |
| **Keep hops = layers** | Always | Sampling more hops than layers is wasteful |

### Sampling Strategies
- **Uniform** (default): Simple, effective baseline
- **Importance-based**: Weight neighbors by visit count or edge weight
- **Layer-wise** (FastGCN, ASGCN): Address neighborhood expansion
- **Graph-wise** (Cluster-GCN, GraphSAINT): Better scalability

### For 100K+ Nodes, 1M+ Edges on 12GB VRAM
**Easily feasible.** GraphSAGE with NeighborLoader was designed for exactly this scale.
- 2-layer model with `[25, 10]` sampling, batch_size=256-512
- Estimated VRAM usage: 2-4GB for model + sampled subgraphs
- Plenty of room for larger models or additional features

### Practical Recommendations
- Start with mean aggregator, 2 layers, `[15, 10]` sampling
- Profile bottlenecks: neighbor lookup vs. GPU utilization
- Cache embeddings for inference; update incrementally as graph changes
- Use hybrid pipeline: GraphSAGE embeddings + task-specific heads

**Sources**: [GraphSAGE Paper](https://arxiv.org/abs/1706.02216), [GraphSAGE Guide 2025](https://www.shadecoder.com/topics/graphsage-a-comprehensive-guide-for-2025), [Sampling Methods Survey](https://arxiv.org/pdf/2103.05872)

## 4. Graph Attention Networks (GAT/GATv2)

### GATv2 vs. GAT
- Original GAT has "static" attention: ranking of scores is unconditioned on query node
- **GATv2** (ICLR 2022) fixes this with dynamic attention: strictly more expressive
- GATv2 achieves higher MRR than GAT across all tested datasets

### GATv2 vs. GraphSAGE
| Factor | GATv2 | GraphSAGE |
|--------|-------|-----------|
| **Accuracy** | Higher (0.802 F1) | Competitive (0.788 F1) |
| **Training speed** | Slower (attention overhead) | Faster (0.062s) |
| **Scalability** | Challenging on large graphs | Designed for scale |
| **Noise robustness** | Better | Moderate |
| **Real-time deployment** | Less suitable | More suitable |
| **Heterogeneous relations** | Better (dynamic attention) | Simpler aggregation |

### When to Use GATv2
- When relationship importance varies and needs to be learned
- When noise robustness matters
- When you can afford the computational overhead
- For heterogeneous graphs where edge semantics vary significantly

### When to Use GraphSAGE
- For very large graphs (100K+ nodes) where speed matters
- For real-time/production deployment
- When scalability is the primary concern
- As a strong baseline before trying more complex architectures

### 12GB VRAM Feasibility
**Feasible with care.** Multi-head attention increases memory usage. For 100K nodes:
- Use 4-8 attention heads (not 16+)
- Hidden dim 64-128 per head
- Mini-batch training essential at scale

### Practical Recommendation
**Start with GraphSAGE** for baseline, then try GATv2 if accuracy needs improvement. The attention overhead may not be worth it for all tasks -- the original GATv2 paper found GraphSAGE sometimes outperforms attention-based GNNs.

**Sources**: [GATv2 Paper (ICLR 2022)](https://arxiv.org/pdf/2105.14491), [GCN vs GraphSAGE vs GAT Comparison](https://apxml.com/courses/introduction-to-graph-neural-networks/chapter-3-foundational-gnn-architectures/comparing-gcn-graphsage-gat)

## 5. Heterogeneous Graph Transformers (HGT)

### Architecture
- Type-dependent attention via **meta-relation triplets**: `<source_type, edge_type, target_type>`
- Separate representation spaces per node/edge type
- Implicit meta-path learning: automatically discovers important multi-hop patterns
- No manual meta-path design needed

### Performance
- Outperforms SOTA GNN baselines by **9-21%** on Open Academic Graph (179M nodes, 2B edges)
- Both HGT and HAN outperform GAT on heterogeneous graphs
- HGT has particular advantage on complex, large-scale heterogeneous graphs

### Scalability: HGSampling
- Node-type specific budgets maintain separate quotas per type
- Guarantees type diversity in each batch
- Tested on 179M node / 2B edge graphs

### 2025 Developments
| Model | Innovation | Status |
|-------|-----------|--------|
| **EHG** (Feb 2025) | Linear key-value interaction, reduced complexity | Published |
| **HMT** (Dec 2025) | Graph memory modules for long-range context | Published |
| **HGT-Scheduler** (Mar 2025) | RL + HGT for job scheduling | Published |
| **ProtHGT** (2025) | Protein function prediction via HGT | Published |

### 12GB VRAM Feasibility
**Feasible for medium-scale heterogeneous KGs.** HGT is more memory-intensive than GraphSAGE due to type-specific parameters, but:
- 100K nodes / 1M edges: comfortably fits with mini-batch training
- Use HGSampling with type-specific budgets
- Consider EHG variant if memory is tight (linear complexity)

### Practical Recommendations
- Use HGT when you have multiple meaningful node/edge types (e.g., `Person`, `Organization`, `Topic` with `works_at`, `studies`, `mentions` edges)
- PyG provides `HGTConv` natively
- If types are minimal (2-3), HeteroConv with simpler operators may suffice
- For very large graphs, EHG's linear complexity is attractive

**Sources**: [HGT Paper](https://arxiv.org/abs/2003.01332), [EHG Paper](https://advancesincontinuousanddiscretemodels.springeropen.com/articles/10.1186/s13662-025-03885-0), [HGT EmergentMind](https://www.emergentmind.com/papers/2003.01332)

## 7. Link Prediction Methods

### State of the Art (2025-2026)

#### Negative-Sample-Free Methods (Emerging Trend)
| Model | Key Innovation | Performance |
|-------|---------------|-------------|
| **MuCo-KGC** (Mar 2025) | Multi-context BERT, cross-entropy loss | +6.88% Hit@1 on WN18RR, +25.23% on CoDEx-M |
| **CAB-KGC** | Context-aware BERT, no entity descriptions needed | +6.88-17.13% Hit@1 across datasets |

#### Path-Based Methods
| Model | Key Innovation | Performance |
|-------|---------------|-------------|
| **BioPathNet** (Jan 2026) | NBFNet-based path reasoning for biomedical KGs | +4% MRR with type-constrained negatives |

### Negative Sampling Strategies
| Strategy | Impact |
|----------|--------|
| **Random** | Baseline, cheap, potentially noisy |
| **Type-constrained** | +10% MRR on standard benchmarks, +150% on ontology-backed |
| **Semantic similarity** | More deceptive negatives, higher quality |
| **Self-adversarial** (RotatE) | Weights hard negatives higher, +3-4% MRR |
| **Cross-entropy (no negatives)** | Emerging approach, avoids sampling bias entirely |

### Evaluation Metrics
- **MRR** (Mean Reciprocal Rank): Primary metric, harmonic mean of ranks
- **Hits@K** (K=1,3,10): Proportion of correct entities in top K
- **MR** (Mean Rank): Average rank of correct entity
- **Caveat**: Under Open World Assumption, "negative" triples may actually be positive (KG incompleteness). Even models with 0.8 MRR and 100% Hits@10 can show lower accuracy on absolute metrics.

### 12GB VRAM Feasibility
**Highly feasible.** Link prediction models are generally lightweight:
- Embedding models (TransE, RotatE): very memory-efficient
- BERT-based (MuCo-KGC): may need gradient checkpointing for large KGs
- GNN-based (BioPathNet): standard mini-batch training

### Practical Recommendations
- For traditional KG completion: use RotatE with self-adversarial negative sampling
- For highest accuracy: consider MuCo-KGC or CAB-KGC (negative-sample-free)
- Always use type-constrained negatives if you have type information
- Evaluate with both MRR and Hits@1,3,10; be cautious interpreting absolute values

**Sources**: [MuCo-KGC](https://arxiv.org/html/2503.03091v1), [BioPathNet](https://www.nature.com/articles/s41551-025-01598-z), [Negative Sampling Analysis](https://arxiv.org/pdf/1708.06816)

## 8. Node2Vec and Graph Embeddings

### Architecture
- Self-supervised/unsupervised: no labels needed
- Biased random walks + Skip-Gram optimization
- Parameters `p` (return) and `q` (in-out) control walk behavior:
  - Low `q`: depth-first (captures structural roles)
  - High `q`: breadth-first (captures local neighborhoods)

### PyG Implementation
```python
from torch_geometric.nn import Node2Vec
model = Node2Vec(edge_index, embedding_dim=128, walk_length=20,
                 context_size=10, walks_per_node=10, p=1.0, q=1.0,
                 num_negative_samples=1, sparse=True)
```

### Key Parameters
| Parameter | Typical Value | Purpose |
|-----------|--------------|---------|
| `embedding_dim` | 64-256 | Output dimension |
| `walk_length` | 10-80 | Steps per random walk |
| `context_size` | 5-10 | Skip-gram window |
| `walks_per_node` | 5-20 | Walks starting from each node |
| `p` | 0.5-2.0 | Return parameter |
| `q` | 0.5-2.0 | In-out parameter |

### Limitations
- **Transductive only**: Cannot generate embeddings for new nodes without retraining
- For dynamic/growing graphs, use **GraphSAGE** instead (inductive)
- For heterogeneous graphs, use **MetaPath2Vec** (type-aware random walks)

### Use Cases for KG Pre-Training
1. Pre-compute node embeddings as initial features for GNN training
2. Warm-start GNN training with Node2Vec embeddings
3. Use as baseline comparison for GNN methods
4. Cluster analysis and visualization of graph structure

### 12GB VRAM Feasibility
**Trivially feasible.** Node2Vec is very lightweight:
- 100K nodes x 128 dims = ~50MB for embeddings
- Random walks run on CPU; only Skip-Gram training on GPU
- Can handle millions of nodes on 12GB easily

### Practical Recommendations
- Use Node2Vec for quick structural analysis and as pre-training
- For production KG systems, prefer GraphSAGE (handles new nodes)
- For heterogeneous KGs, use MetaPath2Vec with domain-specific metapaths
- Set `sparse=True` for large graphs to reduce memory

**Sources**: [PyG Node2Vec Docs](https://pytorch-geometric.readthedocs.io/en/latest/generated/torch_geometric.nn.models.Node2Vec.html), [PyG Shallow Embeddings Tutorial](https://pytorch-geometric.readthedocs.io/en/latest/tutorial/shallow_node_embeddings.html)

## 9. Elastic Weight Consolidation (EWC) for Continual Learning on Graphs

### Key Paper (NeurIPS 2025 Workshop)
**"Elastic Weight Consolidation for Knowledge Graph Continual Learning: An Empirical Evaluation"** (Jhajj and Lin, NORA'25 Workshop at NeurIPS 2025)

### How EWC Works
- Adds quadratic penalty based on **Fisher Information Matrix** (FIM)
- Protects parameters important to previous tasks
- Penalty: `L_ewc = L_new + (lambda/2) * sum(F_i * (theta_i - theta_i_old)^2)`

### Key Results on KG Link Prediction (TransE + FB15k-237)
| Method | Forgetting Rate | Notes |
|--------|----------------|-------|
| Naive sequential | 12.62% | Baseline |
| **EWC (best)** | **6.85%** | **45.7% reduction** in forgetting |
| EWC + Replay (500 examples) | Moderate | Replay alone less effective |
| Replay only | Higher than EWC | Buffer size limiting |

### Key Findings
- **Task partitioning matters**: Semantically coherent tasks show 9.8 pp higher forgetting than random partitions (12.62% vs 2.81%)
- **Stronger regularization is not always better**: lambda=10 increased forgetting on random partitions (5.08% vs 2.81% naive)
- **EWC > replay** for limited memory budgets
- Experiments ran on **RTX 3070 Ti (8GB)**, 20 hours for 80 experiments

### Practical EWC Settings
| Parameter | Recommended Range | Notes |
|-----------|------------------|-------|
| `lambda` | 0.1 - 1.0 | Start with 1.0; higher can hurt |
| FIM approximation | Diagonal | Block-diagonal for better protection |
| Replay buffer | 500-1000 per task | Combine with EWC for best results |

### 12GB VRAM Feasibility
**Excellent.** The original experiments ran on 8GB VRAM (RTX 3070 Ti). With 12GB:
- More room for larger models or embedding dimensions
- Can afford larger replay buffers
- Fisher Information Matrix computation is the main overhead (one pass over data)

### Practical Recommendations
- Use EWC with lambda=1.0 as starting point for continual KG learning
- Combine with small replay buffer (500-1000 examples per task) for best results
- Use random task partitioning in evaluation to avoid inflated forgetting metrics
- Consider diagonal FIM approximation first; upgrade to block-diagonal if needed
- For production: retrain periodically with EWC protection between updates

**Sources**: [EWC for KG Paper](https://arxiv.org/abs/2512.01890), [NeurIPS 2025 Workshop](https://neurips.cc/virtual/2025/129842), [EWC Deep Dive](https://towardsdatascience.com/continual-learning-a-deep-dive-into-elastic-weight-consolidation-loss-7cda4a2d058c/)

## 10. Knowledge Graph Embedding Models

### Model Comparison

| Model | Space | Scoring Function | Symmetry | Asymmetry | Inversion | Composition |
|-------|-------|-----------------|----------|-----------|-----------|-------------|
| **TransE** | Real | `\|h + r - t\|` | No | Yes | Yes | Yes |
| **DistMult** | Real | `<h, r, t>` (diagonal bilinear) | Yes | No | No | No |
| **ComplEx** | Complex | `Re(<h, r, conj(t)>)` | Yes | Yes | Yes | No |
| **RotatE** | Complex | `\|h * r - t\|` (rotation) | Yes | Yes | Yes | Yes |

### Performance on Standard Benchmarks

#### FB15k-237 (14,541 entities, 237 relations)
| Model | MRR | Hits@10 |
|-------|-----|---------|
| TransE | ~0.294 | ~0.465 |
| DistMult | ~0.241 | ~0.419 |
| ComplEx | ~0.247 | ~0.428 |
| **RotatE** | **~0.338** | **~0.533** |

#### WN18RR (40,493 entities, 11 relations)
| Model | MRR | Hits@10 |
|-------|-----|---------|
| TransE | ~0.226 | ~0.501 |
| DistMult | ~0.430 | ~0.490 |
| ComplEx | ~0.440 | ~0.510 |
| **RotatE** | **~0.476** | **~0.571** |

### Which to Use for Heterogeneous Knowledge Graphs

**RotatE is the best general choice** because:
1. Only model that handles all four relation patterns (symmetry, asymmetry, inversion, composition)
2. Consistently outperforms others on FB15k-237 and WN18RR
3. Self-adversarial negative sampling adds +3-4% MRR
4. Active 2025 research building on it (Ne_AnKGE, TP-RotatE)

**ComplEx** is a solid second choice when:
- Composition patterns are rare in your KG
- You need a simpler model (fewer hyperparameters)
- Symmetry/asymmetry are the dominant patterns

**TransE** remains useful for:
- Very large KGs (simplest, fastest to train)
- KGs dominated by hierarchical/compositional relations
- Quick baselines

**DistMult** is generally not recommended for heterogeneous KGs due to inability to model asymmetric relations.

### 2025 Enhancements
| Model | Innovation |
|-------|-----------|
| **Ne_AnKGE** (2025) | Negative analogical reasoning, combines TransE + RotatE |
| **TP-RotatE** (2025) | Path info + rules for complex relational patterns |
| **SparseTransX** (2025) | Sparse matrix ops, 5.3x CPU / 4.2x GPU speedup |

### 12GB VRAM Feasibility
**Trivially feasible.** KG embedding models are extremely lightweight:
- 100K entities x 256 dims x 4 bytes = ~100MB
- All four models train easily on 12GB with millions of entities
- SparseTransX further reduces memory via sparse operations

### Practical Recommendations
- **Default choice**: RotatE with self-adversarial negative sampling
- **Embedding dim**: 200-500 (higher for complex KGs)
- **Negative samples**: 256-1024 per positive triple
- **Learning rate**: 0.0001-0.001 with Adam
- Use type-constrained negative sampling if type info available
- Consider Ne_AnKGE for best 2025 performance

**Sources**: [RotatE Paper](https://arxiv.org/abs/1902.10197), [KGE GitHub](https://github.com/DeepGraphLearning/KnowledgeGraphEmbedding), [Ne_AnKGE](https://www.nature.com/articles/s41598-025-98550-7), [KGE Wikipedia](https://en.wikipedia.org/wiki/Knowledge_graph_embedding)

## 11. Scaling GNN Training on 12GB VRAM

### RTX 4070 Super Specifications
- **12GB GDDR6X** VRAM
- **836 TFLOPS FP8** / 233 TFLOPS FP16
- PCIe 4.0 x16
- "Go-to recommendation for budget-conscious ML practitioners in 2025"

### Memory Budget Breakdown (12GB)
| Component | Estimated Usage | Notes |
|-----------|----------------|-------|
| PyTorch/CUDA overhead | 1-2 GB | Framework and kernel caches |
| Model parameters | 0.1-1 GB | Depends on architecture |
| Sampled subgraph | 1-3 GB | Depends on batch size and sampling |
| Activations/gradients | 2-4 GB | Main bottleneck |
| **Available for features** | **3-7 GB** | Depends on above |

### Key Strategies
1. **Mini-batch with NeighborLoader**: Essential. Full-batch impossible for large graphs.
2. **CPU-GPU hybrid** (WholeGraph): Store graph/features in CPU RAM, stream minibatches to GPU.
3. **Graph partitioning** (METIS): Minimize cross-partition edges for efficient subgraph extraction.
4. **Gradient checkpointing**: Trade compute for memory on deep models.
5. **Mixed precision** (FP16/BF16): 2x memory savings on activations.
6. **Quantization** (INT8/INT4): For embeddings and less critical computations.
7. **Feature compression**: Reduce input feature dimensions via PCA or hashing.

### Scale Limits on 12GB
| Graph Size | Feasibility | Strategy |
|------------|-------------|----------|
| 100K nodes, 1M edges | Easy | Standard mini-batch |
| 1M nodes, 10M edges | Feasible | Mini-batch + CPU offload |
| 10M nodes, 100M edges | Possible | CPU offload + partitioning + sampling |
| 100M+ nodes | Requires multi-GPU | WholeGraph distributed |

### Mini-Batch vs. Full-Batch Tradeoffs (VLDB 2025)

| Aspect | Mini-Batch | Full-Batch |
|--------|-----------|------------|
| **Convergence speed** | **1-15.2x faster** | Slower |
| **Final accuracy** | Comparable or higher (with tuning) | Sometimes better on small graphs |
| **Memory** | O(batch_size * k^L) | O(full graph) |
| **Gradient quality** | Higher variance (graph sampling noise) | Lower variance |
| **Hyperparameters** | Need separate tuning | Different optimal settings |

**Critical finding** (Jan 2026, arXiv:2601.22678): Full-graph training does NOT always yield better performance. Well-tuned mini-batch with appropriate fan-out can match or exceed full-graph. Fan-out size and batch size have non-isotropic effects on convergence.

### Practical Recommendations
- **Always use mini-batch** for graphs > 10K nodes on 12GB
- Start with batch_size=256, `num_neighbors=[15, 10]`
- Enable mixed precision: `torch.cuda.amp.autocast()`
- Monitor VRAM with `torch.cuda.memory_summary()`
- Tune hyperparameters separately for mini-batch (don't reuse full-batch settings)
- Use `pin_memory=True` and `num_workers=4` for data loading

**Sources**: [GNN Training Systems Comparison (VLDB)](https://arxiv.org/html/2406.00552v3), [Full vs Mini-Batch Analysis](https://arxiv.org/abs/2601.22678), [WholeGraph Part 1](https://developer.nvidia.com/blog/optimizing-memory-and-retrieval-for-graph-neural-networks-with-wholegraph-part-1/)

## 12. GNN Hyperparameter Tuning

### Key Hyperparameters and Ranges
| Hyperparameter | Range | Default/Start | Impact |
|---------------|-------|--------------|--------|
| **Learning rate** | 1e-4 to 1e-2 | 5e-4 | High |
| **Hidden dimensions** | 32-512 | 64-256 | High |
| **Number of GNN layers** | 1-6 | 2-3 | High (over-smoothing risk) |
| **Batch size** | 32-256 | 128 | Medium |
| **Dropout** | 0.0-0.5 | 0.1-0.3 | Medium |
| **Activation** | ReLU, ELU, GELU | ReLU | Low |
| **Weight decay** | 1e-5 to 1e-3 | 5e-4 | Medium |
| **Fan-out (sampling)** | [5-25] per hop | [15, 10] | High |
| **Attention heads** (GAT) | 1-8 | 4 | Medium |
| **Embedding dim** (KGE) | 100-500 | 200 | High |

### Best Practices
1. **Simple architectures can win**: Under comprehensive tuning, GCN can outperform complex architectures
2. **Use Bayesian optimization** (TPE/FANOVA) over grid search
3. **Low-fidelity first**: Run short experiments to identify important hyperparameters, then tune those
4. **GNN-Diff** (ICLR 2025): Diffusion-based framework that generates high-performing GNN configurations from coarse search checkpoints
5. **Separate tuning per training method**: Mini-batch and full-batch optima differ significantly
6. **Watch for over-smoothing**: Adding layers beyond 3 often hurts performance

### Tuning Protocol
1. Fix architecture, tune learning rate and weight decay first
2. Tune hidden dimensions and number of layers
3. Tune sampling parameters (fan-out, batch size)
4. Fine-tune dropout and regularization
5. Optionally: architecture search (aggregation function, attention heads)

**Sources**: [GNN HPO Survey](https://arxiv.org/pdf/2104.06046), [GNN-Diff (ICLR 2025)](https://openreview.net/forum?id=D756s2YQ6b), [Iterative GNN Tuning Guide](https://machinelearningmastery.com/guide-to-iteratively-tuning-gnns/)

## 13. Feature Hashing for Large/Growing Vocabularies

### The Problem
Knowledge graphs grow over time. New entity types, relation types, and attribute values appear. One-hot encodings become impractical (memory explosion) and cannot handle unseen values.

### Solutions

#### PosHashEmb (Position-based Hash Embeddings)
- **Key paper**: "Position-based Hash Embeddings For Scaling Graph Neural Networks" (Kalantzi et al.)
- Combines position-specific component (graph structure) + node-specific component (features)
- **97% memory savings** (35x fewer parameters) vs full embeddings
- Performance does not vary significantly as memory is reduced
- Best results on ogbn-products dataset

#### Feature Hashing (The Hashing Trick)
- Maps arbitrary features to fixed-size vector via hash function
- Handles unbounded vocabularies naturally
- No retraining needed for new features
- Collisions introduce noise but are manageable with sufficient dimensionality

#### Practical Implementation for KGs
```python
import torch
from torch.nn import EmbeddingBag

class HashEmbedding(torch.nn.Module):
    def __init__(self, num_buckets, embedding_dim):
        super().__init__()
        self.num_buckets = num_buckets
        self.embedding = EmbeddingBag(num_buckets, embedding_dim, mode='sum')

    def forward(self, features):
        indices = torch.tensor([hash(f) % self.num_buckets for f in features])
        return self.embedding(indices)
```

### 12GB VRAM Feasibility
**Feature hashing specifically helps with VRAM constraints** by replacing O(vocabulary_size) embeddings with O(num_buckets) where num_buckets << vocabulary_size.

### Practical Recommendations
- Use PosHashEmb when node features are weak or absent
- Use feature hashing when vocabulary is large (>100K unique values) or growing
- Set num_buckets to 2-10x the expected feature count for manageable collisions
- Combine with learned embeddings: hash for rare features, learned for frequent ones
- For KGs: hash entity attributes, learn embeddings for entity/relation types

**Sources**: [PosHashEmb Paper](https://arxiv.org/pdf/2109.00101), [Feature Hashing Wikipedia](https://en.wikipedia.org/wiki/Feature_hashing), [HashGNN for Recommender Systems](https://arxiv.org/pdf/2003.01917)

## 14. Continual Learning for Knowledge Graphs (2025-2026 Papers)

### Latest Research

| Paper | Venue | Key Contribution |
|-------|-------|-----------------|
| **DMSG** | ICLR 2025 | Superior buffer selection and replay for growing graphs |
| **Online Continual Graph Learning** | ICLR 2025 | General formulation for online CL on graphs, bounded memory |
| **IMCGNN** | Neurocomputing Jan 2025 | Information-theoretic node selection for replay |
| **EWC for KG** | NeurIPS 2025 Workshop | 45.7% forgetting reduction on KG link prediction |
| **ARTD** | ADC 2025 | Adaptive replay + topology distillation for multimodal KGs |
| **EL-GNN** | Electronics Jul 2025 | Elastic GNN for intrusion detection (task-incremental) |
| **ReFNet** | Information Sciences 2025 | Framelet-based GNN with coverage-based diversity replay |

### Core Challenges Unique to Graph CL
1. **Topological dependencies**: Nodes are not independent samples; replay requires neighborhood context
2. **Memory replay on graphs**: Cannot just store individual samples; must aggregate multi-hop neighbors
3. **Growing graph structure**: New nodes/edges change existing node representations
4. **Type diversity**: Heterogeneous graphs need type-balanced replay buffers

### Approaches Taxonomy
| Approach | Method | Pros | Cons |
|----------|--------|------|------|
| **Regularization** (EWC) | Penalize changes to important params | Memory-efficient | May be too restrictive |
| **Replay** (DMSG, IMCGNN) | Store/replay representative subgraphs | Preserves topology | Memory overhead |
| **Distillation** (ARTD) | Transfer knowledge from old to new model | Preserves representations | Compute overhead |
| **Architecture** (EL-GNN) | Expandable network components | No forgetting limit | Growing model size |
| **Hybrid** (EWC + Replay) | Combine regularization + replay | Best of both worlds | More hyperparameters |

### 12GB VRAM Feasibility
**Feasible.** All methods work within consumer GPU constraints:
- EWC: Minimal overhead (FIM storage ~ model size)
- Replay: Buffer size configurable (500-2000 subgraphs typical)
- Distillation: Requires old model in memory (2x model size briefly)

### Practical Recommendations for KG Continual Learning
1. **Start with EWC** (simplest, proven on KGs): lambda=1.0, diagonal FIM
2. **Add replay buffer** (500-1000 subgraphs per task) for better topology preservation
3. Use **type-balanced sampling** for heterogeneous KGs
4. Evaluate on both **new task performance** and **old task forgetting**
5. Consider ARTD for multimodal KGs (text + structure)
6. Monitor the [awesome-graph-incremental-learning](https://github.com/jwsu825/awesome-graph-incremental-learning) GitHub repo for new papers

**Sources**: [DMSG (ICLR 2025)](https://proceedings.iclr.cc/paper_files/paper/2025/file/b5e5a6c0ab7078e5c21e7c9e46360480-Paper-Conference.pdf), [Online CGL (ICLR 2025)](https://openreview.net/forum?id=4sJJixGIZX), [IMCGNN](https://www.sciencedirect.com/science/article/abs/pii/S0925231225000347), [ARTD](https://link.springer.com/chapter/10.1007/978-981-95-6196-4_21), [CL on Graphs Survey](https://arxiv.org/html/2402.11565v1)

## Lessons Learned
- PyG is the clear winner over DGL for new projects (NVIDIA backing, better performance, more active development)
- Mini-batch training is not a compromise -- it often matches or exceeds full-batch accuracy with proper tuning
- RotatE is the best general-purpose KG embedding model for heterogeneous graphs
- EWC provides meaningful catastrophic forgetting reduction (45.7%) with minimal overhead
- cuGraph analytics (PageRank, centrality) as GNN features is an underutilized pattern
- Feature hashing enables handling growing KG vocabularies without retraining embedding layers
- 12GB VRAM is sufficient for graphs up to ~10M nodes with proper mini-batch strategies

## Recommendations
1. Build on PyG 2.7 with cuGraph integration for maximum performance
2. Use GraphSAGE as baseline, upgrade to HGT/GATv2 only if accuracy demands it
3. Implement EWC + small replay buffer for continual KG updates
4. Pre-compute cuGraph features (PageRank, Louvain communities) as node features
5. Use RotatE for KG completion tasks with self-adversarial negative sampling
6. Always use mini-batch training with NeighborLoader on consumer GPUs
7. Tune hyperparameters separately for your specific training method (mini-batch settings differ from full-batch)
