# Multi-Agent Team Patterns: Empirical Analysis Across 22 Operations

## Summary
Analysis of 22 team sessions (TEAM-0001 through TEAM-0026), 37 knowledge base entries, coordination system runtime data, and 96+ stress tests to identify what actually works in multi-agent delegation.

## Key Finding: The Parallel Research → Direct Action Pattern Dominates

Across all successful operations, one pattern consistently outperforms: **delegate research/analysis to parallel agents, then act on results directly.**

Every high-performing session follows this structure:
1. Fan out research/analysis agents in parallel
2. Collect and synthesize their findings
3. Execute fixes/implementations directly (not via agents)

Sessions that violated this (e.g., delegating sequential edits to agents) showed worse outcomes.

## Empirical Data: Team Configurations Tested

### Team Sizing (from TEAM-0007 controlled experiment)
| Config | Structure | Result |
|--------|-----------|--------|
| Config 1 | 1 solo agent | Works for narrow scope |
| Config 2 | 2 leads + 1 sub each (4 total) | Decent coverage |
| Config 3 | 3 leads + 2 subs each (9 total) | **Optimal for research** |
| Config 4 | 4 leads + 2 subs each (12 total) | Diminishing returns |

**Verdict:** 3 leads + 2 subs (9 agents) is the sweet spot for research tasks. Beyond that, coordination overhead exceeds parallelism gains.

### Scaling Efficiency Formula (from KB-0026/KB-0027)
```
E ≈ 2.0 × N^(-1.0)
```
Where N = number of agents, E = per-agent efficiency. At 10 agents, each operates at ~20% individual efficiency — but total output is still 2x a solo agent.

## Pattern 1: Successful Delegation (When Agents Help)

### Parallel Research with Cross-Referencing
**Best example:** TEAM-0022 — Alpha-1 found Proto A had 79% throughput collapse. Alpha-2 found live tests showed 0 denials. Cross-referencing revealed the benchmark rate limiter was misconfigured, not broken. **This insight was only possible because two independent agents analyzed different data sets.**

### Think Tank Bug Analysis
**Best example:** TEAM-0025 — 3 bug analysis agents found 14 bugs in help_protocol.py (3 critical, 5 high, 5 medium, 1 low), plus bugs in direct_channels.py and work_stealing.py. Analysis agents worked in parallel; coding teams fixed bugs in parallel.

### Independent Workstream Fan-Out
**Best example:** TEAM-0009 — 3 programming teams built completely independent tools simultaneously (Python archive tools, pipeline fixes, Go compiled tools). 3 archive teams verified in parallel. Zero coordination conflicts because workstreams had no file overlap.

## Pattern 2: Failed Delegation (When Agents Hurt)

### Sequential Waves (Anti-Pattern)
**Example:** TEAM-0025 coordinator initially planned sequential batch execution. User had to correct: "all teams within each batch run simultaneously." The anti-sequential rules (ASR-001 through ASR-010 in SOP-011) were created specifically because this mistake kept recurring.

**Root causes identified (from think tank analysis):**
- SEQ-001: Risk aversion without visibility
- SEQ-002: Assuming causal dependency where none exists
- SEQ-003: Simpler mental model (linear is easier to plan)
- SEQ-004: Fear of merge conflicts from past experience
- SEQ-005: "Completion dependency illusion" — waiting for results you don't actually need
- SEQ-006: Not consuming partial results

### Over-Decomposition
**Observation:** No team session explicitly failed from over-decomposition, but KB-0027 documents that single-item work stealing (the current default) is the "worst possible strategy" — hierarchical lead with pre-partitioned batches is 10.4x better.

### Duplicate Work
**Observation:** TEAM-0022 Beta-1 and Beta-2 had overlapping scope (both indexing repository contents). The separation worked because Beta-1 focused on KB/logs and Beta-2 on code/tools — clear partition. Without partition, they would have duplicated effort.

## Pattern 3: Coordination System Resilience

### Stress Test Results (96+ tests, all passing)
- **35 concurrent message senders** on same channel: all unique IDs, ordering preserved
- **20 threads competing for 5 items** (thundering herd): exactly 5 winners, 15 losers, zero duplicates
- **25 teams offering help on same request**: exactly 1 winner, 24 rejections
- **50-stage linear pipeline**: executes correctly under concurrency
- **1MB JSON values**: stored and retrieved correctly
- **SQL injection attempts**: blocked by parameterized queries

### Key Infrastructure Finding
SQLite WAL mode with `BEGIN IMMEDIATE` transactions eliminates deadlocks. All 4 coordination modules (help_protocol, direct_channels, work_stealing, coordinator_hub) follow this pattern successfully.

## Actionable Recommendations

### For Commanders (SOP-022 Calibration)
1. **Research tasks**: Always delegate. 3 leads + 2 subs optimal.
2. **Code edits**: Almost never delegate. Direct execution is faster for targeted fixes.
3. **Bug analysis → fix pipeline**: Delegate analysis (produces large output), fix directly (tight feedback loop).
4. **Cross-referencing**: Requires 2+ agents analyzing different data — impossible solo.
5. **Default to parallel**: The Hard Dependency Test (SOP-011) should be the only gate for sequential execution.

### For Team Design
1. **Partition by file/module**, not by task type. Prevents merge conflicts.
2. **Give coordinator read-only access** to all team outputs (TEAM-0009 pattern).
3. **Reassign completed teams** to help stragglers (TEAM-0025 user directive).
4. **Never exceed 12 agents** for a single research topic. Diminishing returns are steep.
5. **Use hierarchical lead distribution** (KB-0027) instead of single-item work stealing.

### For Infrastructure
1. **SQLite WAL + BEGIN IMMEDIATE** is production-proven under 50-thread concurrency.
2. **Bus notifications should be fire-and-forget** — never crash callers after DB commit.
3. **Pre-partition work** before distributing — 10.4x better than runtime stealing.
4. **Monitor with hub-and-spoke** — enables parallel execution by giving visibility.
