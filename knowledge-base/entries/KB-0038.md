# Multi-Agent Team Patterns: Empirical Analysis Across 22 Operations

## Summary
Analysis of 22 team sessions (TEAM-0001 through TEAM-0026), 37 knowledge base entries, coordination system runtime data, and 96+ stress tests to identify what actually works in multi-agent delegation.

## Key Finding: The Parallel Research → Direct Action Pattern Dominates

Across all successful operations, one pattern consistently outperforms: **delegate research/analysis to parallel agents, then act on results directly.**

Every high-performing session follows this structure:
1. Fan out research/analysis agents in parallel
2. Collect and synthesize their findings
3. Execute fixes/implementations directly (not via agents)

Sessions that violated this (e.g., delegating sequential edits to agents) showed worse outcomes.

## Empirical Data: Team Configurations Tested

### Team Sizing (from TEAM-0007 controlled experiment)
| Config | Structure | Result |
|--------|-----------|--------|
| Config 1 | 1 solo agent | Works for narrow scope |
| Config 2 | 2 leads + 1 sub each (4 total) | Decent coverage |
| Config 3 | 3 leads + 2 subs each (9 total) | **Optimal for research** |
| Config 4 | 4 leads + 2 subs each (12 total) | Diminishing returns |

**Verdict:** 3 leads + 2 subs (9 agents) is the sweet spot for research tasks. Beyond that, coordination overhead exceeds parallelism gains.

### Scaling Efficiency Formula (from KB-0026/KB-0027)
```
E ≈ 2.0 × N^(-1.0)
```
Where N = number of agents, E = per-agent efficiency. At 10 agents, each operates at ~20% individual efficiency — but total output is still 2x a solo agent.

### Operation Scale History
| Operation | Agents | Teams | Output | Outcome |
|-----------|--------|-------|--------|---------|
| TEAM-0003 | 5 | 3 | First multi-team research | Good — established patterns |
| TEAM-0004 | ~17 | 3+coordinator | Data gathering loop | Good — 2 iterations, +400% methods |
| TEAM-0007 | 8+subs | 4 research + 2 coding + 1 archive | Config testing | Good — found optimal sizing |
| TEAM-0009 | 12+8subs | 8 teams | Operation 3 full build | Good — Go tools + Python tools + verification |
| TEAM-0022 | 18 | 6 | Production deployment | Excellent — found critical cross-team insight |
| TEAM-0025 | 15 | 15 parallel | Bug fixes + SOPs + hub | Good after correction — user had to fix sequential plan |

## Pattern 1: Successful Delegation (When Agents Help)

### Parallel Research with Cross-Referencing
**Best example:** TEAM-0022 — Alpha-1 found Proto A had 79% throughput collapse. Alpha-2 found live tests showed 0 denials. Cross-referencing revealed the benchmark rate limiter was misconfigured, not broken. **This insight was only possible because two independent agents analyzed different data sets.**

### Think Tank Bug Analysis
**Best example:** TEAM-0025 — 3 bug analysis agents found 14 bugs in help_protocol.py (3 critical, 5 high, 5 medium, 1 low), plus bugs in direct_channels.py and work_stealing.py. Analysis agents worked in parallel; coding teams fixed bugs in parallel.

### Independent Workstream Fan-Out
**Best example:** TEAM-0009 — 3 programming teams built completely independent tools simultaneously (Python archive tools, pipeline fixes, Go compiled tools). 3 archive teams verified in parallel. Zero coordination conflicts because workstreams had no file overlap.

## Pattern 2: Failed Delegation (When Agents Hurt)

### Sequential Waves (Anti-Pattern)
**Example:** TEAM-0025 coordinator initially planned sequential batch execution. User had to correct: "all teams within each batch run simultaneously." The anti-sequential rules (ASR-001 through ASR-010 in SOP-011) were created specifically because this mistake kept recurring.

**Root causes identified (from think tank analysis):**
- SEQ-001: Risk aversion without visibility
- SEQ-002: Assuming causal dependency where none exists
- SEQ-003: Simpler mental model (linear is easier to plan)
- SEQ-004: Fear of merge conflicts from past experience
- SEQ-005: "Completion dependency illusion" — waiting for results you don't actually need
- SEQ-006: Not consuming partial results

### Over-Decomposition
**Observation:** No team session explicitly failed from over-decomposition, but KB-0027 documents that single-item work stealing (the current default) is the "worst possible strategy" — hierarchical lead with pre-partitioned batches is 10.4x better.

### Duplicate Work
**Observation:** TEAM-0022 Beta-1 and Beta-2 had overlapping scope (both indexing repository contents). The separation worked because Beta-1 focused on KB/logs and Beta-2 on code/tools — clear partition. Without partition, they would have duplicated effort.

## Pattern 3: Coordination System Resilience

### Stress Test Results (96+ tests, all passing)
- **35 concurrent message senders** on same channel: all unique IDs, ordering preserved
- **20 threads competing for 5 items** (thundering herd): exactly 5 winners, 15 losers, zero duplicates
- **25 teams offering help on same request**: exactly 1 winner, 24 rejections
- **50-stage linear pipeline**: executes correctly under concurrency
- **1MB JSON values**: stored and retrieved correctly
- **SQL injection attempts**: blocked by parameterized queries

### Key Infrastructure Finding
SQLite WAL mode with `BEGIN IMMEDIATE` transactions eliminates deadlocks. All 4 coordination modules (help_protocol, direct_channels, work_stealing, coordinator_hub) follow this pattern successfully.

## Pattern 4: Knowledge Accumulation

### Dependency Graph Structure
37 entries across 4 domains:
1. **Storage/Infrastructure** (KB-0001→KB-0009): Foundation layer, most fan-out
2. **Communication System** (KB-0015→KB-0025): Linear evolution from design to production
3. **Coordination Optimization** (KB-0026→KB-0035): Research-heavy, benchmark-driven
4. **Vulkan Graphics** (KB-0029→KB-0037): Independent domain, parallel development

### Most Referenced Entries
- **KB-0001** (Storage System): 15+ transitive dependents — every system builds on it
- **KB-0009** (Operation 3): 7 direct dependents — bridge to communication domain
- **KB-0018/0019** (Communication Prototypes): Basis for all production coordination

### Knowledge Reuse Pattern
Teams that read prior KB entries before starting produced higher-quality output. TEAM-0022 (which built on 7 prior KB entries) made the most significant cross-domain discovery.

## Actionable Recommendations

### For Commanders (SOP-022 Calibration)
1. **Research tasks**: Always delegate. 3 leads + 2 subs optimal.
2. **Code edits**: Almost never delegate. Direct execution is faster for targeted fixes.
3. **Bug analysis → fix pipeline**: Delegate analysis (produces large output), fix directly (tight feedback loop).
4. **Cross-referencing**: Requires 2+ agents analyzing different data — impossible solo.
5. **Default to parallel**: The Hard Dependency Test (SOP-011) should be the only gate for sequential execution.

### For Team Design
1. **Partition by file/module**, not by task type. Prevents merge conflicts.
2. **Give coordinator read-only access** to all team outputs (TEAM-0009 pattern).
3. **Reassign completed teams** to help stragglers (TEAM-0025 user directive).
4. **Never exceed 12 agents** for a single research topic. Diminishing returns are steep.
5. **Use hierarchical lead distribution** (KB-0027) instead of single-item work stealing.

### For Infrastructure
1. **SQLite WAL + BEGIN IMMEDIATE** is production-proven under 50-thread concurrency.
2. **Bus notifications should be fire-and-forget** — never crash callers after DB commit.
3. **Pre-partition work** before distributing — 10.4x better than runtime stealing.
4. **Monitor with hub-and-spoke** — enables parallel execution by giving visibility.

# New Free APIs & Data Sources: 20 Additions Across 8 Categories

## Context
Our catalog had 44 data sources across Academic, News, Economic/Financial, Developer, AI/ML, Weather, Crypto, and Utility categories. Major gaps existed in Health/Science, Legal/Regulatory, Geopolitical, and Knowledge Graph categories. Research Beta searched for new free APIs released or verified in 2025-2026.

## Method
Systematic web search for free/freemium APIs across underrepresented categories. Each API verified for: free access, base URL, rate limits, data types, and relevance. Cross-referenced against existing 44 sources to avoid duplicates.

## Result

### 20 New APIs Discovered

**Health/Science (4 new):**
1. **PubMed/NCBI E-utilities** — 36M+ biomedical citations, 10 req/s with free key
2. **ClinicalTrials.gov API v2** — World's largest clinical trials registry, no auth required
3. **openFDA** — Drug adverse events, recalls, device data; 240 req/min, no auth for basic
4. **WHO GHO OData API** — Global health statistics for 194 countries, no auth

**Legal/Regulatory (3 new — was zero):**
5. **CourtListener REST API** — Federal/state case law, PACER via RECAP, no auth
6. **Federal Register API** — All federal regulations 1994-present, no auth
7. **Regulations.gov API** — Federal rulemaking + public comments, free key

**Geopolitical (1 new):**
8. **ACLED API** — Real-time conflict events worldwide, ~200K events/year, free key

**AI/ML (2 new):**
9. **Groq Cloud API** — Fastest free LLM inference (~300 tok/s), OpenAI-compatible, no credit card
10. **OpenAI Realtime API** — WebSocket speech-to-speech, frontier real-time AI pattern

**Financial/Trading (2 new):**
11. **Alpaca Markets API** — Commission-free trading + data, WebSocket streaming, 10K calls/min free
12. **Polygon.io** — Tick-level stock/options/forex/crypto data, WebSocket streaming

**Knowledge Graph (2 new):**
13. **Google Knowledge Graph Search** — Structured entity data, schema.org, free key
14. **YAGO Knowledge Base** — 2B type-consistent triples, 64M entities, free SPARQL

**Developer (1 new):**
15. **Libraries.io API** — 9.96M packages across 37+ managers, dependency graphs, 60 req/min

**Security (1 new):**
16. **OSV.dev** — Google's vulnerability DB, no rate limits, covers all major ecosystems

**Science/Space (2 new):**
17. **NASA Open APIs** — APOD, Mars Rover, Earth imagery, NEO data; 1K req/hr free
18. **NASA GIBS/Earthdata** — Near-real-time satellite imagery, standard WMTS/WMS

**Education/Books (1 new):**
19. **Open Library API** — Book metadata for millions of books, no auth

**Search/Utility (1 new):**
20. **DuckDuckGo Instant Answer API** — Zero-auth factual lookups, no rate limits

### 5 Companion Tools Identified
- OSV-Scanner (vulnerability scanning CLI)
- Juriscraper (court website scraping)
- pytrials (ClinicalTrials.gov Python wrapper)
- Graphiti (knowledge graph framework)
- Alpaca MCP Server (AI-native trading access)

### Key Cross-Team Notes
- Groq API: fastest free LLM inference, OpenAI-compatible format, drop-in replacement
- OSV.dev: no rate limits — ideal for bulk vulnerability scanning
- ACLED + GDELT together: comprehensive geopolitical monitoring
- CourtListener + Federal Register + Regulations.gov: full U.S. legal/regulatory coverage
- CoinCap WebSocket: easiest zero-auth real-time streaming for testing
- LLM API prices dropped ~80% from 2025 to 2026

### Remaining Gaps
- Education APIs (Khan Academy deprecated public API)
- Real-time non-financial streaming (IoT, social media mostly paywalled)
- Geospatial/mapping (OpenStreetMap APIs could fill this)
- Geospatial/routing (OSRM, Overpass API candidates)
- Social media analytics (Twitter/X API priced out, Reddit restrictive)

## Lessons Learned
1. Health/Science and Legal/Regulatory had the largest category gaps — now filled
2. Zero-auth APIs are increasingly common for government/public data
3. WebSocket streaming APIs are emerging as a distinct pattern worth cataloging separately
4. MCP servers are appearing alongside REST APIs (Alpaca, Sourcegraph) — future integration pattern
5. Package intelligence (Libraries.io) covers 37+ ecosystems in one API vs our per-ecosystem approach

## Recommendations
1. Register all 20 new sources in storage/sources/ with proper SRC IDs
2. Build data gathering methods for the highest-value new APIs (PubMed, CourtListener, ACLED)
3. Add a "streaming" category for WebSocket-based APIs
4. Evaluate OpenStreetMap APIs (Nominatim, OSRM, Overpass) for geospatial gap
5. Create MCP servers for commonly used APIs following the Alpaca MCP pattern
