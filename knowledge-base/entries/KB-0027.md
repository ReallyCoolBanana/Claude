# Large-Team Efficiency Experiment: 8 Strategies Compared (10x Improvement Found)

## Context
KB-0026 benchmarks revealed the current single-item work stealing approach degrades sharply at 4+ agents: steal overhead exceeds work time (ratio 2.77:1), work distribution becomes very uneven (CV=0.54), and per-agent throughput drops proportionally to team size (exponent -0.99). This experiment tested 7 alternative coordination strategies to find improvements.

## Method
8 communicating teams (via Proto A bus + scratchpad), each testing a different work distribution strategy with identical workloads (500 items, 10 workers, 1ms simulated work per item):

| # | Strategy | Description |
|---|----------|-------------|
| 1 | **Baseline** | Current single-item `steal_work()` via `BEGIN IMMEDIATE` |
| 2 | **Batch Steal (10)** | Steal 10 items per transaction |
| 3 | **Pre-Partition** | Round-robin assignment, no stealing |
| 4 | **Hierarchical** | Team lead steals batches, distributes via thread-safe queue |
| 5 | **Sharded Queues** | 3 separate DBs, workers prefer their shard |
| 6 | **Adaptive Batch** | Start at 2, grow batch size when contention detected |
| 7 | **Hybrid 80/20** | Pre-assign 80%, put 20% in steal queue |
| 8 | **Batch Steal (5)** | Steal 5 items per transaction (batch size comparison) |

## Result

## Lessons Learned

1. **The current baseline is the worst possible strategy for large teams.** Single-item stealing with `BEGIN IMMEDIATE` spends 2.77x more time on steal transactions than on actual work. The coordination system is doing 1,010 SQLite transactions for 500 work items.

2. **Pre-partition is the theoretical optimum** (10.8x faster, perfect distribution, zero overhead) but requires knowing all work upfront and assumes uniform work item cost. It cannot handle dynamic work or stragglers.

3. **Hierarchical is the practical winner** (10.4x faster, near-perfect distribution, 0.048 overhead ratio). It decouples the DB-contention problem from workers: only 1 thread (the lead) touches SQLite, workers pull from an in-memory queue. It handles 500 items in just 26 transactions.

4. **Batch stealing helps but doesn't fix distribution.** Batch steal (10) gets 4.7x throughput improvement but makes distribution WORSE (CV 0.65 vs 0.54 baseline) because some workers grab large batches while others get nothing. Batch sizes of 5 and 10 perform identically on throughput.

5. **Sharded queues disappoint.** Only 1.5x improvement despite 3 separate databases, because workers still contend within their preferred shard and the cross-shard fallback logic adds overhead.

6. **Adaptive batch is the best pure-steal approach** (5.5x, CV 0.45). Starting small and growing batch size based on contention signals naturally balances distribution vs throughput.

7. **Hybrid 80/20 is surprisingly mediocre** (2.7x). The 20% steal pool creates enough contention to drag performance below batch approaches, and the pre-assigned 80% doesn't fully remove coordination ops since workers still need to check the steal queue afterward.

## Recommendations

### Immediate Improvements (no architecture changes)

1. **Add `steal_batch(n)` method to `WorkStealing`**: Claim N items in a single `BEGIN IMMEDIATE` transaction. Default to `n=10` for large teams. Implementation: change `LIMIT 1` to `LIMIT ?` in `steal_work()` and loop the UPDATE inside the same transaction. This alone gives **4.7x throughput**.

2. **Add adaptive batch size option**: Start with batch_size=2, increase by 2 when full batches are returned, decrease by 1 when partial. This gives **5.5x throughput** with better distribution than fixed batch.

### Structural Improvements

3. **Implement hierarchical team lead pattern**: Add a `TeamLeadDistributor` class that wraps `WorkStealing` with a thread-safe `queue.Queue`. The lead thread batch-steals from SQLite, workers pull from the in-memory queue. This gives **10.4x throughput** with near-perfect distribution (CV=0.009).

4. **For known-upfront workloads, use pre-partition**: When all work items are known at dispatch time (e.g., processing a list of files), skip the steal queue entirely and round-robin assign. This is the `enqueue_and_partition(items, num_workers)` pattern.

### What NOT to Do

5. **Don't shard the database** for coordination. The overhead of cross-shard fallback logic negates the benefit of reduced per-shard contention. SQLite WAL mode with batch stealing already handles the serialization point well enough.

6. **Don't use hybrid pre-assign + steal** unless the steal pool is very small (<10%). The context-switching between "process my pre-assigned work" and "go steal from the queue" creates awkward phase transitions.

# SDK Launcher System: Multi-Agent Subprocess Management for Claude Code

## Context
The coordination system (JSONL bus + SQLite shared state + coordinator hub) needed a way to actually spawn and manage Claude Code CLI agents as real operating system processes. Prior work (multi_team_runner.py, coordinator_hub.py, help_protocol.py, direct_channels.py, work_stealing.py) provided the communication and coordination infrastructure, but launching, monitoring, and controlling agent lifecycles was manual. The SDK launcher system fills this gap with four modules that together provide a complete agent lifecycle management layer.

## Method
Four Python modules were built on top of the existing coordination infrastructure:

### 1. `sdk_launcher.py` -- Process Lifecycle Manager (core)

The central module that spawns Claude Code CLI agents as managed async subprocesses. Key components:

- **`AgentProcess`**: Wraps a single `claude --print` subprocess. Handles start, stop (SIGTERM then SIGKILL), restart with exponential backoff, and health checking via process polling. Each agent gets its own log file under `coordination/logs/`. On start, the agent receives a system prompt injected with its identity (`agent_id`, `team`, `role`), the bus directory path, and the database path so it can participate in coordination.

- **`SDKLauncher`**: Orchestrates multiple teams of `AgentProcess` instances. Launches all teams, runs background health-check and heartbeat loops, auto-restarts crashed agents (up to `max_restarts` per agent with configurable backoff), and handles graceful shutdown on SIGTERM/SIGINT. Writes launcher state to the `runner_state` SQLite table and agent state to the `sdk_agents` table. Also registers agents in the older `agents` table for backward compatibility with multi_team_runner.py.

- **`TeamConfig`**: Frozen dataclass defining a team -- name, number of agents, system prompt, allowed tools, work queue, working directory. Agent IDs are deterministic: `{team}-lead` for index 0, `{team}-worker-{i}` for the rest.

- **Bus integration**: Every lifecycle event (start, stop, crash, restart, restart-exhausted) is written to the `global` JSONL bus channel, making all events visible to other agents and monitoring tools.

- **CLI modes**: `--config teams.json` (file-based), `--team X --agents N --prompt "..."` (quick launch), `--status` (read from DB), `--shutdown` (send SIGTERM to running launcher via stored PID).

### 2. `sdk_config.py` -- Configuration & Presets

Typed configuration system with validation. Key components:

- **`AgentRole` enum**: leader, worker, researcher, reviewer, think_tank.
- **`TeamDefinition`**: Per-team config including agent count, role, system prompt, allowed tools, work directory, environment variables. Generates agent IDs matching the multi_team_runner convention (`{name}-lead`, `{name}-worker-{i}`).
- **`LaunchConfig`**: Top-level config aggregating teams plus infrastructure settings (bus_path, db_path, log_dir, max_restarts, health_check_interval, heartbeat_interval, dead_agent_timeout, cleanup_interval). Defaults paths relative to the coordination directory.
- **`validate_config()`**: Checks for duplicate team names, positive agent counts, existing work directories, positive intervals. Returns a list of error strings.
- **`load_config()` / `load_named_config()`**: Load from YAML (with PyYAML) or JSON. Supports files with multiple named configurations under a `configurations` key.
- **Built-in presets**: `standard_dev_team` (coding/testing/review, 7 agents), `research_team` (research/synthesis, 5 agents), `review_team` (audit/reporting, 4 agents), `full_production_team` (all roles, 12 agents). Accessible via `PRESETS` dict or `get_preset()`.

### 3. `sdk_cli.py` -- Command-Line Interface

Full CLI with six subcommands for operating the multi-agent system:

| Subcommand | Purpose |
|------------|---------|
| `launch` | Start teams from config file or inline args. Delegates to multi_team_runner.py. Checks for already-running instance. Supports `--dry-run`. |
| `status` | Color-coded agent health display with heartbeat age. Groups by team, shows OK/WARN/DEAD badges. Optional `--json` output. |
| `stop` | Sends SIGTERM to runner. Can stop individual teams by updating DB status. `--wait` polls for process exit. |
| `restart` | Resets dead/stale agents to alive status in DB. Can target specific agent or team. |
| `logs` | View runner log file or bus messages. Supports `--source runner|bus`, `--channel`, `--team` filter, `--tail N`. Color-codes log levels and message types. |
| `config` | Validate config files, generate configs (`--generate TEAMS AGENTS`), or show current stored config. |

The CLI reads state from the shared SQLite database and JSONL bus files -- it does not need to be colocated with the running launcher process. ANSI color output auto-detects terminal capability (respects `NO_COLOR` and `FORCE_COLOR` environment variables).

### 4. `sdk_dashboard.py` -- Real-Time Monitoring Dashboard

Enhanced terminal dashboard with six rendering sections:

- **Team Grid**: Compact overview with color-coded health bars (`#`=ok, `~`=stale, `X`=dead, `.`=done).
- **Agent Detail**: Per-agent status with role, PID, heartbeat age, and health badge.
- **Message Bus**: Recent messages per channel with type-colored output.
- **Phase Signals**: History of phase transitions from the phase_signals table.
- **Lifecycle Events**: Restart, start, stop, and dead-agent events from the global bus channel.
- **Findings Summary**: Aggregate counts by team and priority.

Modes: `--watch` for auto-refresh (configurable interval), `--section X` to show specific sections only, `--compact` for single-line agent view, `--json` for machine-readable output. All data collected via read-only SQLite queries and bus file reads.

## Result
The four modules form a complete lifecycle management layer:

```
sdk_config.py  -->  sdk_launcher.py  -->  Claude Code CLI subprocesses
                         |                        |
                    writes to:               participate in:
                    - SQLite (sdk_agents,     - JSONL bus messaging
                      runner_state)           - SQLite shared state
                    - JSONL bus (events)      - coordinator hub
                         |
                    monitored by:
                    sdk_dashboard.py / sdk_cli.py status
```

**How the pieces connect to existing infrastructure:**
- The launcher writes to the same SQLite WAL database used by coordinator_hub.py and multi_team_runner.py. It creates its own `sdk_agents` table but also writes to the existing `agents` table for compatibility.
- All lifecycle events go through the JSONL bus (`global` channel), making them visible to bus_cli.py, dashboard.py, and any agent reading the bus.
- The `TeamConfig` / `TeamDefinition` classes generate agent IDs following the same `{team}-lead` / `{team}-worker-{N}` convention used throughout the system.
- The CLI and dashboard read state from the same DB and bus files, so they work whether the launcher is running or not.

## Lessons Learned

1. **Subprocess management needs both process polling and heartbeats.** Process polling catches crashes immediately, but heartbeats detect hangs where the process is alive but unresponsive.

2. **Backward compatibility tables matter.** The SDK launcher writes to both `sdk_agents` (new) and `agents` (legacy) tables, so existing monitoring tools (dashboard.py, bus_cli.py) continue to work without modification.

3. **Exponential backoff on restart is essential.** Without it, a flapping agent can consume resources indefinitely. The `max_restarts` cap with `restart_backoff * restart_count` prevents runaway restart loops.

4. **Deterministic agent IDs enable predictable addressing.** Using `{team}-lead` and `{team}-worker-{i}` means any agent can address any other agent by constructing the ID from the team name and index.

5. **Configuration presets reduce launch friction.** Having `standard_dev_team()`, `research_team()`, etc. as one-liner factory functions means teams can be spun up without writing config files.

## Recommendations

1. **Use `sdk_cli.py` as the primary operator interface.** It wraps all common operations (launch, status, stop, restart, logs, config) with color output and sensible defaults.

2. **For custom deployments, use JSON config files** loaded via `sdk_launcher.py --config`. For quick experimentation, use `sdk_launcher.py --team X --agents N --prompt "..."`.

3. **Monitor with `sdk_dashboard.py --watch`** during multi-agent runs. The auto-refresh mode gives continuous visibility into agent health, bus activity, and phase transitions.

4. **Use `sdk_config.py` presets programmatically** when building higher-level orchestration. The `validate_config()` function should be called before any launch to catch misconfiguration early.

5. **Check `sdk_cli.py logs --source bus --channel global`** after runs to review the full lifecycle event history (starts, crashes, restarts, stops) for post-mortem analysis.

6. **If extending the system**, keep the pattern of writing lifecycle events to the JSONL bus. This makes all new components automatically visible to the dashboard and CLI without additional integration work.
