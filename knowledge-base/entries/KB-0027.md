# Large-Team Efficiency Experiment: 8 Strategies Compared (10x Improvement Found)

## Context
KB-0026 benchmarks revealed the current single-item work stealing approach degrades sharply at 4+ agents: steal overhead exceeds work time (ratio 2.77:1), work distribution becomes very uneven (CV=0.54), and per-agent throughput drops proportionally to team size (exponent -0.99). This experiment tested 7 alternative coordination strategies to find improvements.

## Method
8 communicating teams (via Proto A bus + scratchpad), each testing a different work distribution strategy with identical workloads (500 items, 10 workers, 1ms simulated work per item):

| # | Strategy | Description |
|---|----------|-------------|
| 1 | **Baseline** | Current single-item `steal_work()` via `BEGIN IMMEDIATE` |
| 2 | **Batch Steal (10)** | Steal 10 items per transaction |
| 3 | **Pre-Partition** | Round-robin assignment, no stealing |
| 4 | **Hierarchical** | Team lead steals batches, distributes via thread-safe queue |
| 5 | **Sharded Queues** | 3 separate DBs, workers prefer their shard |
| 6 | **Adaptive Batch** | Start at 2, grow batch size when contention detected |
| 7 | **Hybrid 80/20** | Pre-assign 80%, put 20% in steal queue |
| 8 | **Batch Steal (5)** | Steal 5 items per transaction (batch size comparison) |

## Lessons Learned

1. **The current baseline is the worst possible strategy for large teams.** Single-item stealing with `BEGIN IMMEDIATE` spends 2.77x more time on steal transactions than on actual work. The coordination system is doing 1,010 SQLite transactions for 500 work items.

2. **Pre-partition is the theoretical optimum** (10.8x faster, perfect distribution, zero overhead) but requires knowing all work upfront and assumes uniform work item cost. It cannot handle dynamic work or stragglers.

3. **Hierarchical is the practical winner** (10.4x faster, near-perfect distribution, 0.048 overhead ratio). It decouples the DB-contention problem from workers: only 1 thread (the lead) touches SQLite, workers pull from an in-memory queue. It handles 500 items in just 26 transactions.

4. **Batch stealing helps but doesn't fix distribution.** Batch steal (10) gets 4.7x throughput improvement but makes distribution WORSE (CV 0.65 vs 0.54 baseline) because some workers grab large batches while others get nothing. Batch sizes of 5 and 10 perform identically on throughput.

5. **Sharded queues disappoint.** Only 1.5x improvement despite 3 separate databases, because workers still contend within their preferred shard and the cross-shard fallback logic adds overhead.

6. **Adaptive batch is the best pure-steal approach** (5.5x, CV 0.45). Starting small and growing batch size based on contention signals naturally balances distribution vs throughput.

7. **Hybrid 80/20 is surprisingly mediocre** (2.7x). The 20% steal pool creates enough contention to drag performance below batch approaches, and the pre-assigned 80% doesn't fully remove coordination ops since workers still need to check the steal queue afterward.

## Recommendations

### Immediate Improvements (no architecture changes)

1. **Add `steal_batch(n)` method to `WorkStealing`**: Claim N items in a single `BEGIN IMMEDIATE` transaction. Default to `n=10` for large teams. Implementation: change `LIMIT 1` to `LIMIT ?` in `steal_work()` and loop the UPDATE inside the same transaction. This alone gives **4.7x throughput**.

2. **Add adaptive batch size option**: Start with batch_size=2, increase by 2 when full batches are returned, decrease by 1 when partial. This gives **5.5x throughput** with better distribution than fixed batch.

### Structural Improvements

3. **Implement hierarchical team lead pattern**: Add a `TeamLeadDistributor` class that wraps `WorkStealing` with a thread-safe `queue.Queue`. The lead thread batch-steals from SQLite, workers pull from the in-memory queue. This gives **10.4x throughput** with near-perfect distribution (CV=0.009).

4. **For known-upfront workloads, use pre-partition**: When all work items are known at dispatch time (e.g., processing a list of files), skip the steal queue entirely and round-robin assign. This is the `enqueue_and_partition(items, num_workers)` pattern.

### What NOT to Do

5. **Don't shard the database** for coordination. The overhead of cross-shard fallback logic negates the benefit of reduced per-shard contention. SQLite WAL mode with batch stealing already handles the serialization point well enough.

6. **Don't use hybrid pre-assign + steal** unless the steal pool is very small (<10%). The context-switching between "process my pre-assigned work" and "go steal from the queue" creates awkward phase transitions.
