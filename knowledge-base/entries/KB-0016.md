# SQLite WAL Shared State: Technical Reference for Inter-Agent Coordination

## Executive Summary

SQLite in WAL (Write-Ahead Logging) mode provides a robust, zero-infrastructure solution for inter-agent shared state, supporting concurrent readers with a single writer and sub-millisecond read latency. This entry documents the complete technical details needed to implement a shared coordination database for multiple AI agent processes: WAL internals, Python API patterns, schema designs for rate-limit tracking / heartbeats / phase signals / pub-sub messaging, concurrency handling, performance characteristics, and reliability edge cases. All processes must reside on the same local filesystem — network filesystems are explicitly unsupported.

## 1. SQLite WAL Mode Deep Dive

### 1.1 How Write-Ahead Logging Works

In the default rollback journal mode, SQLite copies original page content to a separate journal file before modifying the database, enabling rollback by restoring those pages. WAL inverts this: **the original database file is left untouched, and new versions of modified pages are appended to a separate WAL file**.

The sequence for a write transaction:

1. Writer appends new page versions to the end of the WAL file.
2. On COMMIT, a commit record is written to the WAL.
3. The original database file remains unmodified until a **checkpoint** transfers WAL content back.

For readers:

1. When a read transaction starts, the reader records the last valid commit point in the WAL (the "end mark").
2. For each page read, the reader checks the WAL (using the wal-index) for the most recent version at or before the end mark.
3. If no WAL version exists, the page is read from the original database file.

This gives **snapshot isolation**: each reader sees a consistent snapshot as of its transaction start, unaffected by concurrent writes.

### 1.2 Concurrency Model: Multiple Readers + Single Writer

| Operation | Concurrent with Readers? | Concurrent with Writers? |
|-----------|-------------------------|-------------------------|
| Read      | Yes                     | Yes                     |
| Write     | Yes                     | **No** — serialized     |
| Checkpoint| Partially (PASSIVE)     | No                      |

Key properties:
- **Readers never block writers.** A writer can append to the WAL while any number of readers are active.
- **Writers never block readers.** Readers see their snapshot regardless of ongoing writes.
- **Only one writer at a time.** A second writer attempting to acquire the write lock receives `SQLITE_BUSY`.
- Writers merely append to the WAL file — they never modify content that readers might be accessing.

### 1.3 The WAL-Index (Shared Memory File)

The `-shm` file is a shared-memory region (memory-mapped) that acts as a hash table index into the WAL file. It allows readers to locate pages in the WAL with minimal I/O — typically a single hash lookup rather than scanning the entire WAL.

Properties:
- Usually exactly 32 KiB in size.
- Memory-mapped, requiring all accessing processes to be on the **same machine with a shared local filesystem**.
- This is the fundamental reason WAL mode cannot work over NFS or network filesystems.

### 1.4 SQLITE_BUSY: What Happens When Two Processes Write Simultaneously

When process B attempts to write while process A holds the write lock:

1. If `busy_timeout` is set, SQLite retries internally with a backoff schedule (hardcoded sleep intervals: 1, 2, 5, 10, 15, 20, 25, 25, 25, 50, 50, 100 ms, repeating).
2. If the lock is released within the timeout, process B proceeds.
3. If the timeout expires, `SQLITE_BUSY` is raised (Python: `sqlite3.OperationalError: database is locked`).
4. There is **no FIFO guarantee** — lock acquisition among competing processes follows a geometric distribution (essentially random).

**Critical distinction with DEFERRED transactions**: If a DEFERRED transaction attempts to upgrade from a read lock to a write lock and another writer already holds it, `SQLITE_BUSY` is returned **immediately** — the `busy_timeout` is **not respected** in this case. This is because the read snapshot may already be stale. Use `BEGIN IMMEDIATE` to avoid this.

### 1.5 WAL Checkpointing

Checkpointing transfers committed content from the WAL file back into the main database file. Without checkpointing, the WAL file grows indefinitely, degrading read performance.

**Automatic checkpointing**: By default, a checkpoint runs automatically when the WAL reaches **1000 pages** (~4 MB with default page size). This uses PASSIVE mode. Configure with:

```sql
PRAGMA wal_autocheckpoint = 1000;  -- default; set to 0 to disable
```

**Manual checkpoint modes** (via `PRAGMA wal_checkpoint(MODE)`):

| Mode     | Behavior | Blocks Writers? | Blocks Readers? |
|----------|----------|----------------|----------------|
| PASSIVE  | Checkpoints as much as possible without blocking | No | No |
| FULL     | Waits for readers to finish, then checkpoints completely | Waits | Waits |
| RESTART  | Like FULL, then resets WAL to beginning | Waits | Waits |
| TRUNCATE | Like RESTART, then truncates WAL file to zero bytes | Waits | Waits |

For agent coordination, PASSIVE auto-checkpoints are sufficient. Run `PRAGMA wal_checkpoint(TRUNCATE)` periodically (e.g., from the coordinator) to reclaim disk space.

### 1.6 Enabling WAL Mode

```sql
PRAGMA journal_mode=WAL;
```

This is **persistent** — it is stored in the database file header and survives connection close/reopen. You only need to set it once. Verify with:

```sql
PRAGMA journal_mode;  -- returns 'wal' if active
```

The database file format version numbers at offsets 18 and 19 are changed from 1 to 2, which means SQLite versions older than 3.7.0 (2010) will refuse to open WAL-mode databases.

## 2. Python sqlite3 Standard Library

### 2.1 Thread Safety

Python's `sqlite3.threadsafety` attribute indicates the DB-API 2.0 thread safety level:

| Value | Meaning |
|-------|---------|
| 1     | Threads may share the module, but not connections |
| 2     | Threads may share the module and connections, but not cursors |
| 3     | Fully thread-safe (serialized mode) |

As of Python 3.11+, this attribute reflects the actual compile-time threading mode of the underlying SQLite library (previously hardcoded to 1). Most platforms compile SQLite in **serialized mode** (threadsafety=3).

### 2.2 check_same_thread Parameter

```python
conn = sqlite3.connect("coordination.db", check_same_thread=False)
```

- Default is `True`: raises `ProgrammingError` if a connection is used from a different thread than the one that created it.
- Setting to `False` disables the Python-level check but does **not** make the connection thread-safe by itself.
- **For multi-process agent coordination**: Each process should create its own connection. `check_same_thread` is irrelevant unless a single process uses multiple threads to access the same connection.

### 2.3 The timeout Parameter

```python
conn = sqlite3.connect("coordination.db", timeout=30.0)
```

- Specifies how many **seconds** to wait when the database is locked before raising `OperationalError`.
- Default is **5.0 seconds**.
- Maps to SQLite's `busy_timeout` handler internally.
- **For agent coordination**: Set to at least 10-30 seconds. With many agents, increase to 60+ seconds.
- The timeout applies at the `BEGIN IMMEDIATE` or write statement level, **not** at read time (reads never block in WAL mode).

### 2.4 Connection Handling Pattern for Multi-Process Access

**Recommended pattern**: Each process creates its own connection. Do not share connections between processes.

```python
import sqlite3
from contextlib import contextmanager

DB_PATH = "/path/to/coordination.db"

@contextmanager
def get_db():
    """Get a database connection with optimal settings for coordination."""
    conn = sqlite3.connect(DB_PATH, timeout=30.0)
    conn.execute("PRAGMA journal_mode=WAL")       # Persistent, but harmless to repeat
    conn.execute("PRAGMA synchronous=NORMAL")      # Safe in WAL mode, much faster
    conn.execute("PRAGMA busy_timeout=30000")       # 30s in milliseconds (alternative to timeout param)
    conn.execute("PRAGMA wal_autocheckpoint=1000")  # Default, explicit for clarity
    conn.row_factory = sqlite3.Row                  # Dict-like access to rows
    try:
        yield conn
    finally:
        conn.close()
```

### 2.5 Transaction Handling

Python's `sqlite3` module has an `isolation_level` parameter that controls automatic transaction management:

```python
# Option A: Let Python manage transactions (default)
conn = sqlite3.connect("coordination.db")
# Python automatically issues BEGIN before DML statements
# Use conn.commit() / conn.rollback() explicitly

# Option B: Manual transaction control (recommended for coordination)
conn = sqlite3.connect("coordination.db", isolation_level=None)  # autocommit mode
conn.execute("BEGIN IMMEDIATE")
conn.execute("INSERT INTO messages ...")
conn.execute("COMMIT")
```

**For write operations in agent coordination, always use explicit `BEGIN IMMEDIATE`:**

```python
def write_with_retry(conn, sql, params=(), max_retries=3):
    """Execute a write operation with explicit IMMEDIATE transaction."""
    for attempt in range(max_retries):
        try:
            conn.execute("BEGIN IMMEDIATE")
            conn.execute(sql, params)
            conn.execute("COMMIT")
            return True
        except sqlite3.OperationalError as e:
            if "database is locked" in str(e):
                conn.execute("ROLLBACK")
                if attempt < max_retries - 1:
                    time.sleep(0.1 * (2 ** attempt))  # Exponential backoff
                    continue
            raise
    return False
```

## 3. Multi-Process Concurrency Patterns

### 3.1 Connection-Per-Process Model

Each agent process maintains its own `sqlite3.Connection`:

```
Agent-A (Process 1) ──conn_a──┐
Agent-B (Process 2) ──conn_b──┼──▶ coordination.db (WAL mode)
Agent-C (Process 3) ──conn_c──┘
```

- All connections can read simultaneously (WAL snapshot isolation).
- Write transactions are serialized by SQLite's internal locking.
- No connection pooling needed — one connection per process is sufficient.

### 3.2 BEGIN IMMEDIATE vs BEGIN DEFERRED

| Aspect | BEGIN DEFERRED (default) | BEGIN IMMEDIATE |
|--------|------------------------|----------------|
| Lock acquired at | First database access | BEGIN statement |
| Concurrent readers during txn | Yes | Yes |
| Concurrent writers | Attempted, may deadlock | Serialized from start |
| `busy_timeout` respected | **No** (on upgrade failure) | **Yes** |
| Risk of mid-transaction failure | High with multiple writers | Low |

**Rule: Always use `BEGIN IMMEDIATE` for any transaction that will write.** Use plain `BEGIN` (DEFERRED) only for read-only transactions.

Why DEFERRED is dangerous for writes:
1. Transaction starts with a read lock.
2. A SELECT executes (read lock held).
3. An INSERT is attempted — SQLite tries to upgrade to a write lock.
4. If another process holds the write lock, `SQLITE_BUSY` is returned **immediately** (no retry, no timeout).
5. The entire transaction must be rolled back and retried from scratch.

With `BEGIN IMMEDIATE`, the write lock is acquired at the BEGIN statement, where `busy_timeout` is respected and retries happen automatically.

### 3.3 Retry Strategy for Write Contention

```python
import sqlite3
import time
import random

def execute_write(db_path, sql, params=(), timeout=30.0):
    """Execute a write with application-level retry and jitter."""
    deadline = time.monotonic() + timeout
    attempt = 0

    while True:
        try:
            with sqlite3.connect(db_path, timeout=timeout) as conn:
                conn.execute("PRAGMA journal_mode=WAL")
                conn.execute("PRAGMA busy_timeout=5000")
                conn.execute("BEGIN IMMEDIATE")
                conn.execute(sql, params)
                conn.commit()
                return True
        except sqlite3.OperationalError as e:
            if "database is locked" not in str(e):
                raise
            if time.monotonic() >= deadline:
                raise
            # Exponential backoff with jitter
            delay = min(0.1 * (2 ** attempt), 2.0) + random.uniform(0, 0.1)
            time.sleep(delay)
            attempt += 1
```

Key principles:
- **Jitter**: Add randomness to backoff to prevent thundering herd when multiple agents retry simultaneously.
- **Deadline-based timeout**: Use `time.monotonic()` for a hard deadline rather than counting retries.
- **Short write transactions**: Keep the time between `BEGIN IMMEDIATE` and `COMMIT` as short as possible. Do all computation before starting the transaction.

### 3.4 Performance Under Contention

With WAL mode and well-designed short transactions:
- **2-5 concurrent writers**: Contention is minimal; most writes succeed on first attempt.
- **10-20 concurrent writers**: Occasional retries; set `busy_timeout` to 10-30 seconds.
- **50+ concurrent writers**: Consider serializing writes through a coordinator process or using a write queue.

For our use case (5-15 agent teams with infrequent writes), direct multi-process access with `BEGIN IMMEDIATE` and a 30-second timeout is well within SQLite's comfort zone.

## 4. Schema Design for Agent Coordination

### 4.1 Complete Schema

```sql
-- Enable WAL mode (persistent, only needs to be set once)
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;

-- ============================================================
-- Agent Registry & Heartbeats
-- ============================================================
CREATE TABLE IF NOT EXISTS agents (
    agent_id       TEXT PRIMARY KEY,              -- e.g., "TEAM-0016"
    agent_type     TEXT NOT NULL,                  -- "coordinator", "researcher", "programmer"
    worktree_path  TEXT,                           -- git worktree path
    pid            INTEGER,                        -- OS process ID
    started_at     TEXT NOT NULL DEFAULT (datetime('now')),
    last_heartbeat TEXT NOT NULL DEFAULT (datetime('now')),
    status         TEXT NOT NULL DEFAULT 'active', -- active, idle, blocked, terminated
    current_task   TEXT,                           -- free-text description of current work
    metadata       TEXT                            -- JSON blob for extensible data
);

CREATE INDEX IF NOT EXISTS idx_agents_status ON agents(status);
CREATE INDEX IF NOT EXISTS idx_agents_heartbeat ON agents(last_heartbeat);

-- ============================================================
-- Messages (Pub/Sub)
-- ============================================================
CREATE TABLE IF NOT EXISTS messages (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at  TEXT NOT NULL DEFAULT (datetime('now')),
    sender_id   TEXT NOT NULL,                     -- agent_id of sender
    channel     TEXT NOT NULL,                     -- topic/channel name
    msg_type    TEXT NOT NULL,                     -- "info", "warning", "blocker", "request", "response"
    payload     TEXT NOT NULL,                     -- JSON message body
    expires_at  TEXT,                              -- optional TTL
    FOREIGN KEY (sender_id) REFERENCES agents(agent_id)
);

CREATE INDEX IF NOT EXISTS idx_messages_channel ON messages(channel, id);
CREATE INDEX IF NOT EXISTS idx_messages_created ON messages(created_at);

-- ============================================================
-- Rate Limit Tracking
-- ============================================================
CREATE TABLE IF NOT EXISTS rate_limits (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    api_endpoint TEXT NOT NULL,                    -- e.g., "api.example.com/v1/search"
    agent_id     TEXT NOT NULL,                    -- who made the call
    called_at    TEXT NOT NULL DEFAULT (datetime('now')),
    response_code INTEGER,                         -- HTTP status code
    FOREIGN KEY (agent_id) REFERENCES agents(agent_id)
);

CREATE INDEX IF NOT EXISTS idx_rate_limits_endpoint ON rate_limits(api_endpoint, called_at);

-- Rate limit configuration (shared across all agents)
CREATE TABLE IF NOT EXISTS rate_limit_config (
    api_endpoint    TEXT PRIMARY KEY,
    max_calls       INTEGER NOT NULL,             -- max calls allowed
    window_seconds  INTEGER NOT NULL,             -- time window in seconds
    cooldown_until  TEXT                           -- if rate-limited, when to resume
);

-- ============================================================
-- Phase Signals
-- ============================================================
CREATE TABLE IF NOT EXISTS phase_signals (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    phase_name  TEXT NOT NULL,                     -- e.g., "research", "implementation", "review"
    agent_id    TEXT NOT NULL,                     -- who signaled
    signal_type TEXT NOT NULL,                     -- "started", "completed", "blocked", "skipped"
    details     TEXT,                              -- JSON with details/blockers
    created_at  TEXT NOT NULL DEFAULT (datetime('now')),
    FOREIGN KEY (agent_id) REFERENCES agents(agent_id)
);

CREATE INDEX IF NOT EXISTS idx_phase_signals_phase ON phase_signals(phase_name, created_at);
CREATE INDEX IF NOT EXISTS idx_phase_signals_agent ON phase_signals(agent_id);

-- ============================================================
-- Blockers / Dependency Tracking
-- ============================================================
CREATE TABLE IF NOT EXISTS blockers (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    reported_by     TEXT NOT NULL,
    blocked_agent   TEXT,                          -- NULL means system-wide
    blocker_type    TEXT NOT NULL,                 -- "rate_limit", "dependency", "resource", "error"
    description     TEXT NOT NULL,
    resolved        INTEGER NOT NULL DEFAULT 0,
    reported_at     TEXT NOT NULL DEFAULT (datetime('now')),
    resolved_at     TEXT,
    resolved_by     TEXT,
    FOREIGN KEY (reported_by) REFERENCES agents(agent_id)
);

CREATE INDEX IF NOT EXISTS idx_blockers_active ON blockers(resolved, reported_at);
```

### 4.2 Index Design Rationale

Each index is designed for the polling queries agents will run most frequently:

- **`idx_agents_heartbeat`**: Efficiently find stale agents (`WHERE last_heartbeat < datetime('now', '-60 seconds')`).
- **`idx_messages_channel`**: Composite index on `(channel, id)` supports the primary polling query: `WHERE channel = ? AND id > ?` — this is the most critical index for pub/sub performance.
- **`idx_rate_limits_endpoint`**: Composite index on `(api_endpoint, called_at)` for counting calls within a time window.
- **`idx_blockers_active`**: Find unresolved blockers efficiently.

### 4.3 Data Retention

Add a periodic cleanup job (run by the coordinator) to prevent unbounded growth:

```sql
-- Delete messages older than 1 hour
DELETE FROM messages WHERE created_at < datetime('now', '-1 hour');

-- Delete rate limit records older than the max window
DELETE FROM rate_limits WHERE called_at < datetime('now', '-1 hour');

-- Archive completed phase signals older than 24 hours
DELETE FROM phase_signals WHERE created_at < datetime('now', '-24 hours');
```

## 5. Performance Characteristics

### 5.1 Read Throughput

- SQLite in WAL mode can sustain **100,000+ SELECT queries per second** on a single connection with a well-indexed database.
- Multiple readers can operate concurrently with no lock contention.
- Read performance degrades as the WAL file grows — each read must check the WAL index. Keep auto-checkpointing enabled to bound WAL size.
- With `mmap_size` set, reads use memory-mapped I/O, further reducing syscall overhead.

### 5.2 Write Throughput

- Individual INSERT operations: **~80,000 inserts/second** when wrapped in a single transaction with `synchronous=NORMAL`.
- One-statement-per-transaction (autocommit): **~1,000-5,000 writes/second** depending on `synchronous` setting and disk speed.
- For agent coordination, write frequency is low (heartbeats every 30s, rate limit checks per API call, phase signals per phase) — well within capacity.

### 5.3 Latency

| Operation | Typical Latency |
|-----------|----------------|
| Single SELECT by primary key | < 0.1 ms |
| Single SELECT with index scan | 0.1 - 1 ms |
| Single INSERT (autocommit, WAL, synchronous=NORMAL) | 0.5 - 2 ms |
| Single INSERT (within transaction batch) | < 0.05 ms |
| Checkpoint (PASSIVE, small WAL) | 5 - 50 ms |

### 5.4 Optimal PRAGMA Configuration

```sql
PRAGMA journal_mode = WAL;            -- Concurrent reads + writes
PRAGMA synchronous = NORMAL;          -- Safe in WAL; only checkpoints sync to disk
PRAGMA temp_store = memory;           -- Temp tables in RAM
PRAGMA mmap_size = 268435456;         -- 256 MB memory-mapped I/O
PRAGMA cache_size = -64000;           -- 64 MB page cache (negative = KiB)
PRAGMA wal_autocheckpoint = 1000;     -- Checkpoint every 1000 pages (~4 MB)
PRAGMA optimize;                      -- Run before closing long-lived connections
```

### 5.5 Comparison with Alternatives

| Approach | Read Latency | Write Latency | Concurrency | Infrastructure |
|----------|-------------|---------------|-------------|----------------|
| SQLite WAL | < 1 ms | 1-2 ms | Readers unlimited, 1 writer | Zero (single file) |
| JSON files | 1-50 ms | 10-100 ms | Manual locking needed | Zero |
| Redis | < 1 ms | < 1 ms | Unlimited | Separate server |
| PostgreSQL | 1-5 ms | 1-5 ms | Unlimited | Separate server |
| Named pipes | < 0.1 ms | < 0.1 ms | Complex routing | OS-level setup |

SQLite WAL is the sweet spot for our use case: near-Redis read performance with zero infrastructure, ACID guarantees, and structured query support.

## 6. Reliability & Edge Cases

### 6.1 Crash Recovery

SQLite is **highly resilient** to crashes:

- If a process crashes mid-transaction, the incomplete WAL entries are simply ignored on next access. The WAL contains checksums; any partially-written frames are detected and discarded.
- The next process to open the database automatically performs **WAL recovery** — it replays valid committed transactions from the WAL into the main database.
- No manual intervention is required. The database self-heals on next open.

### 6.2 synchronous=NORMAL Durability Trade-off

With `synchronous=NORMAL` in WAL mode:
- Committed transactions **may be lost** after a power failure or OS crash (not application crash).
- The database will **not be corrupted** — you simply lose the most recent commits that were in the WAL but not yet checkpointed.
- For agent coordination data (heartbeats, rate limits, messages), this trade-off is acceptable — the data is ephemeral and will be regenerated.
- For maximum durability, use `synchronous=FULL` (at a performance cost).

### 6.3 WAL File Corruption Scenarios

The WAL can become problematic in these cases:

1. **Separated files**: Never copy the `.db` file without its `.db-wal` and `.db-shm` files. Missing WAL = lost committed transactions. Missing SHM = recoverable (rebuilt automatically).
2. **Broken fsync**: If the filesystem lies about flushing to disk, corruption is possible after power loss. This is a filesystem/hardware issue, not SQLite's fault.
3. **Partial checkpoint + WAL deletion**: If you manually delete the WAL file after an incomplete checkpoint, the database will be corrupted.
4. **Multiple hard/soft links**: If two processes open the same database via different filesystem paths, they use separate locking namespaces and can corrupt the database.

### 6.4 Network Filesystems: DO NOT USE

**SQLite on NFS/CIFS/SMB is unsupported and will corrupt your data.** The reasons:

- The WAL-index (`-shm` file) requires shared memory via `mmap()`. NFS cannot reliably provide this.
- `fcntl()` file locking is broken on many NFS implementations. NFS may report a lock as acquired when it was not.
- Even NFSv4 with proper locking support has implementation bugs across platforms.
- Real-world reports: databases become "malformed" within 15 minutes of multi-process access over NFS.

**Solution**: All agent processes must access the database on a **local filesystem**. If agents run on different machines, use a client-server database (PostgreSQL) instead.

```sql
-- Returns "ok" if healthy, or a list of problems

-- Quick check (faster, less thorough)

```

### 6.6 Live Backup

Use the SQLite backup API or `VACUUM INTO` rather than copying files:

```python
import sqlite3

def backup_coordination_db(src_path, backup_path):
    """Safely backup a live SQLite database."""
    src = sqlite3.connect(src_path)
    dst = sqlite3.connect(backup_path)
    src.backup(dst)  # Uses SQLite's online backup API
    dst.close()
    src.close()
```

Alternatively:

```sql
VACUUM INTO '/path/to/backup.db';
```

Both methods are safe to run while other processes are reading/writing the database.

### 7.2 Agent Registration and Heartbeats

```python
import sqlite3
import os
import json
import time

class AgentCoordinator:
    def __init__(self, db_path, agent_id, agent_type="worker"):
        self.db_path = db_path
        self.agent_id = agent_id
        self.agent_type = agent_type
        self._conn = None

    def _get_conn(self):
        if self._conn is None:
            self._conn = sqlite3.connect(self.db_path, timeout=30.0)
            self._conn.execute("PRAGMA journal_mode=WAL")
            self._conn.execute("PRAGMA synchronous=NORMAL")
            self._conn.execute("PRAGMA busy_timeout=30000")
            self._conn.row_factory = sqlite3.Row
        return self._conn

    def register(self, worktree_path=None):
        """Register this agent in the coordination database."""
        conn = self._get_conn()
        conn.execute("""
            INSERT OR REPLACE INTO agents (agent_id, agent_type, worktree_path, pid, started_at, last_heartbeat, status)
            VALUES (?, ?, ?, ?, datetime('now'), datetime('now'), 'active')
        """, (self.agent_id, self.agent_type, worktree_path, os.getpid()))
        conn.commit()

    def heartbeat(self, current_task=None):
        """Update heartbeat timestamp and optional task description."""
        conn = self._get_conn()
        conn.execute("""
            UPDATE agents SET last_heartbeat = datetime('now'), current_task = ?, status = 'active'
            WHERE agent_id = ?
        """, (current_task, self.agent_id))
        conn.commit()

    def set_status(self, status, current_task=None):
        """Update agent status: active, idle, blocked, terminated."""
        conn = self._get_conn()
        conn.execute("""
            UPDATE agents SET status = ?, current_task = ?, last_heartbeat = datetime('now')
            WHERE agent_id = ?
        """, (status, current_task, self.agent_id))
        conn.commit()

    def close(self):
        """Mark agent as terminated and close connection."""
        if self._conn:
            try:
                self._conn.execute("""
                    UPDATE agents SET status = 'terminated', last_heartbeat = datetime('now')
                    WHERE agent_id = ?
                """, (self.agent_id,))
                self._conn.commit()
            finally:
                self._conn.close()
                self._conn = None
```

### 7.3 Rate Limit Checking

```python
    def check_rate_limit(self, api_endpoint):
        """Check if an API call is allowed under rate limits. Returns True if allowed."""
        conn = self._get_conn()

        # Get rate limit config
        config = conn.execute("""
            SELECT max_calls, window_seconds, cooldown_until
            FROM rate_limit_config WHERE api_endpoint = ?
        """, (api_endpoint,)).fetchone()

        if config is None:
            return True  # No rate limit configured

        # Check cooldown
        if config["cooldown_until"]:
            cooldown = conn.execute(
                "SELECT datetime('now') < ? AS in_cooldown",
                (config["cooldown_until"],)
            ).fetchone()
            if cooldown["in_cooldown"]:
                return False

        # Count calls in window (read — no lock needed)
        count = conn.execute("""
            SELECT COUNT(*) as cnt FROM rate_limits
            WHERE api_endpoint = ?
              AND called_at > datetime('now', ? || ' seconds')
        """, (api_endpoint, -config["window_seconds"])).fetchone()["cnt"]

        return count < config["max_calls"]

    def record_api_call(self, api_endpoint, response_code=200):
        """Record an API call for rate limiting."""
        conn = self._get_conn()
        conn.execute("""
            INSERT INTO rate_limits (api_endpoint, agent_id, called_at, response_code)
            VALUES (?, ?, datetime('now'), ?)
        """, (api_endpoint, self.agent_id, response_code))
        conn.commit()

        # If we got rate-limited (429), set a cooldown
        if response_code == 429:
            conn.execute("""
                UPDATE rate_limit_config
                SET cooldown_until = datetime('now', '+60 seconds')
                WHERE api_endpoint = ?
            """, (api_endpoint,))
            conn.commit()
```

### 7.5 Pub/Sub Messaging with Polling

```python
    def publish(self, channel, msg_type, payload, ttl_seconds=3600):
        """Publish a message to a channel."""
        conn = self._get_conn()
        expires = f"+{ttl_seconds} seconds" if ttl_seconds else None
        conn.execute("""
            INSERT INTO messages (sender_id, channel, msg_type, payload, expires_at)
            VALUES (?, ?, ?, ?, CASE WHEN ? IS NOT NULL THEN datetime('now', ?) END)
        """, (self.agent_id, channel, msg_type,
              json.dumps(payload) if isinstance(payload, dict) else payload,
              expires, expires))
        conn.commit()

    def poll_messages(self, channel, since_id=0, limit=50):
        """Poll for new messages on a channel since a given message ID."""
        conn = self._get_conn()
        rows = conn.execute("""
            SELECT id, created_at, sender_id, msg_type, payload
            FROM messages
            WHERE channel = ? AND id > ?
              AND (expires_at IS NULL OR expires_at > datetime('now'))
            ORDER BY id ASC
            LIMIT ?
        """, (channel, since_id, limit)).fetchall()
        return rows

    def poll_all_channels(self, since_ids=None, limit=50):
        """Poll multiple channels. since_ids is a dict of {channel: last_seen_id}."""
        if since_ids is None:
            since_ids = {}
        conn = self._get_conn()
        results = {}
        for channel, last_id in since_ids.items():
            results[channel] = self.poll_messages(channel, last_id, limit)
        return results
```

### 7.6 Coordinator System-Wide Status Query

```python
    def get_system_status(self):
        """Get a complete system status snapshot (for coordinator use)."""
        conn = self._get_conn()

        status = {}

        # Active agents
        status["agents"] = conn.execute("""
            SELECT agent_id, agent_type, status, current_task, last_heartbeat,
                   ROUND((julianday('now') - julianday(last_heartbeat)) * 86400) as seconds_since_heartbeat
            FROM agents
            WHERE status != 'terminated'
            ORDER BY last_heartbeat DESC
        """).fetchall()

        # Stale agents (no heartbeat in 120 seconds)
        status["stale_agents"] = conn.execute("""
            SELECT agent_id, last_heartbeat
            FROM agents
            WHERE status = 'active'
              AND last_heartbeat < datetime('now', '-120 seconds')
        """).fetchall()

        # Active blockers
        status["blockers"] = conn.execute("""
            SELECT id, reported_by, blocked_agent, blocker_type, description, reported_at
            FROM blockers
            WHERE resolved = 0
            ORDER BY reported_at DESC
        """).fetchall()

        # Rate limit status
        status["rate_limits"] = conn.execute("""
            SELECT rc.api_endpoint, rc.max_calls, rc.window_seconds, rc.cooldown_until,
                   COUNT(rl.id) as calls_in_window
            FROM rate_limit_config rc
            LEFT JOIN rate_limits rl ON rc.api_endpoint = rl.api_endpoint
                AND rl.called_at > datetime('now', '-' || rc.window_seconds || ' seconds')
            GROUP BY rc.api_endpoint
        """).fetchall()

        # Recent messages
        status["recent_messages"] = conn.execute("""
            SELECT id, created_at, sender_id, channel, msg_type, payload
            FROM messages
            WHERE created_at > datetime('now', '-5 minutes')
            ORDER BY id DESC
            LIMIT 20
        """).fetchall()

        return status
```

### 7.7 Efficient Polling Pattern

```python
import time
import threading

class AgentPoller:
    """Efficient polling loop for an agent to receive messages and monitor state."""

    def __init__(self, coordinator, channels, poll_interval=2.0):
        self.coord = coordinator
        self.channels = {ch: 0 for ch in channels}  # channel -> last_seen_id
        self.poll_interval = poll_interval
        self._running = False
        self._callbacks = {}

    def on_message(self, channel, callback):
        """Register a callback for messages on a channel."""
        self._callbacks[channel] = callback

    def poll_once(self):
        """Single poll iteration. Returns list of new messages."""
        all_new = []
        for channel in self.channels:
            messages = self.coord.poll_messages(channel, self.channels[channel])
            for msg in messages:
                self.channels[channel] = msg["id"]
                if channel in self._callbacks:
                    self._callbacks[channel](msg)
                all_new.append(msg)
        return all_new

    def run(self):
        """Run polling loop (blocking). Call from a thread."""
        self._running = True
        while self._running:
            self.poll_once()
            # Also send heartbeat
            self.coord.heartbeat()
            time.sleep(self.poll_interval)

    def stop(self):
        self._running = False
```

## 8. Gotchas & Limitations

- **Single writer at a time.** WAL mode does not enable concurrent writes. All writes are serialized. If write throughput is a bottleneck, serialize through a coordinator process.
- **Always use `BEGIN IMMEDIATE` for write transactions.** DEFERRED transactions that attempt to write can fail immediately without respecting `busy_timeout`, and cannot be retried meaningfully.
- **Never use SQLite on NFS, CIFS, SMB, or any network filesystem.** Locking is unreliable and will silently corrupt your database.
- **All processes must access the database via the same filesystem path.** Using different paths (e.g., hard links, symlinks to different mount points) causes processes to use separate lock namespaces, leading to corruption.
- **The WAL file can grow unbounded** if a long-running read transaction prevents checkpointing. Ensure read transactions are short-lived. If an agent crashes with an open read transaction, the WAL will be cleaned up when that connection's file descriptors are closed by the OS.
- **`synchronous=NORMAL` can lose recent commits on power failure** (not application crash). Acceptable for ephemeral coordination data; use `synchronous=FULL` if you need durability guarantees.
- **No push notifications.** SQLite has no built-in mechanism to notify other processes of changes. Polling is required. For sub-second responsiveness, use a Unix socket sidecar for notifications alongside SQLite for state.
- **WAL mode requires SQLite 3.7.0+** (2010). All modern Python distributions include a much newer version.
- **Very large transactions (>100 MB) perform poorly in WAL mode.** Not a concern for coordination data, but worth noting.
- **Auto-checkpoint runs in the connection that triggers the threshold.** This can add unexpected latency to a write operation. If this is a problem, disable auto-checkpoint and run checkpoints from the coordinator on a schedule.
- **The `-shm` and `-wal` files must not be deleted while the database is in use.** They are cleaned up automatically when the last connection closes cleanly.
- **`PRAGMA journal_mode=WAL` is a no-op inside a transaction.** Set it before any transaction begins.
- **Python `sqlite3.Row` objects become invalid after the cursor is closed.** Convert to dicts if you need to store results: `dict(row)`.
- **Busy timeout has no fairness guarantee.** Under high contention, some processes may starve. Add application-level jitter to retry delays.
