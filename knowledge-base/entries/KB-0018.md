# Effectiveness & Fit Analysis: JSONL Bus + SQLite WAL State

## Executive Summary

The proposed JSONL Message Bus + SQLite WAL Shared State system (KB-0015 + KB-0016) addresses **7 of 10 documented gaps** from prior operations, with 4 FULLY SOLVED, 3 PARTIALLY SOLVED, and 3 NOT SOLVED. The system is strongest on communication and coordination gaps (blocker propagation, inter-agent messaging, rate limiting, phase signaling) and weakest on tooling-level gaps (thread safety, orphan detection) that require code changes rather than infrastructure. However, the two-component design introduces redundancy: SQLite's `messages` table duplicates the JSONL bus's core function. A SQLite-only approach would deliver approximately 90% of the value at roughly 60% of the complexity. The recommendation is **CONDITIONAL YES** -- implement SQLite WAL shared state as the primary system, and drop the JSONL bus unless a specific high-frequency streaming use case emerges that SQLite cannot handle.

The 4 FULLY SOLVED gaps are arguably the **most operationally critical** ones: rate limiting was causing redundant API calls and inconsistent throttling across agents; blocker propagation caused wasted effort (TEAM-0005's Wikidata 403 was not known to other teams); phase signaling was entirely manual; and live communication was the single most frequently cited gap across all session logs.

The 3 NOT SOLVED gaps are lower severity and solvable through simple code changes independent of the proposed system.

## Critical Assessment

### Is the Juice Worth the Squeeze?

**For SQLite WAL: Yes.** It provides structured, queryable shared state with ACID guarantees, zero infrastructure, and well-understood concurrency semantics. The `rate_limits`, `phase_signals`, `blockers`, and `agents` tables each solve a real problem that cannot be easily addressed with flat files. The AgentCoordinator class in KB-0016 is a clean abstraction that agents can adopt incrementally. SQLite is already a dependency of Python's standard library, so there are no new dependencies.

**For the JSONL bus: Questionable.** KB-0016's `messages` table already provides pub/sub messaging with channel-based polling, message expiry, and ordered delivery. The JSONL bus (KB-0015) offers:
- Slightly lower latency (file append vs. SQLite write transaction)
- No write contention (append-only, no locks needed for writes under 4096 bytes)
- Simpler mental model for streaming/fire-and-forget

But these advantages are marginal for our use case (5-20 agents, a few messages per second). SQLite handles this load trivially. The JSONL bus adds a second data format, a second polling mechanism, a second set of failure modes, and a second system to maintain. The complexity cost outweighs the marginal performance benefit.

### Complexity-to-Value Ratio

| Component | Implementation Effort | Ongoing Maintenance | Value Delivered |
|-----------|----------------------|--------------------|----|
| SQLite WAL state | Medium (schema + AgentCoordinator class) | Low (self-maintaining, auto-checkpoint) | High (4 gaps solved, 3 partially) |
| JSONL bus | Medium (BusWriter + BusReader + file rotation) | Medium (file rotation, corruption handling, epoch management) | Low incremental (redundant with SQLite messages) |
| Both together | High | Medium-High (two systems to monitor) | Marginally higher than SQLite alone |

### Would Simpler Alternatives Achieve 80% of the Benefit?

**A single shared JSON state file** (not SQLite) could handle heartbeats, blockers, and phase signals with atomic writes (temp file + rename). However, it would fail at:
- Rate limit tracking (requires atomic read-modify-write across processes)
- Message history (overwritten on each write)
- Concurrent reads during writes (read may see partial state during rename window)
- Query flexibility (no SQL, must load entire file)

A shared JSON file would achieve roughly 40% of the benefit -- enough for heartbeats and blockers, but not for rate limiting or messaging.

**SQLite alone** (without the JSONL bus) achieves approximately 90% of the benefit. The only loss is the JSONL bus's lower write latency and simpler append model, which are not meaningful advantages at our scale.

## Alternative Approaches Considered

### 1. Improve Existing File-Based Handoff System

The current system uses files + git for all coordination. Improvements could include:
- A `status.json` file updated atomically by each agent
- A `blockers.json` file for broadcasting blockers
- Convention-based phase files (`phase-research.done`, `phase-implementation.done`)

**Assessment:** This gets you heartbeats and blocker propagation (2 of the 4 fully solved gaps) but fails at rate limiting (needs atomic counters) and messaging (no history, no channels). Approximately 30% of the value for minimal effort. Viable as a stopgap but not a long-term solution.

### 2. Single Shared JSON State File (No SQLite)

A single JSON file with atomic write (temp + rename) containing all coordination state.

**Assessment:** Fails at concurrent access patterns. Two agents trying to update simultaneously will clobber each other's writes. No query capability. No message history. Approximately 40% of the value. Not recommended.

### 3. SQLite Only (Drop JSONL Bus)

Use SQLite WAL for everything: structured state tables (agents, rate_limits, phase_signals, blockers) plus the `messages` table for pub/sub.

**Assessment:** Achieves approximately 90% of the combined system's value. The `messages` table with `poll_messages()` provides equivalent functionality to the JSONL bus for our message volumes. Write contention is not a concern at 5-20 agents with short transactions. **This is the recommended approach.**

### 4. JSONL Bus Only (Drop SQLite)

Use JSONL files for everything, encoding rate limits and state as message streams.

**Assessment:** Loses queryability (cannot efficiently ask "how many API calls in the last 60 seconds?" without scanning the entire file). Loses ACID guarantees for rate limit checks. Approximately 60% of the value. Not recommended for structured state.

### 5. Unix Domain Sockets / Named Pipes

True real-time push-based IPC.

**Assessment:** Sub-millisecond latency, true push notifications. However, requires a running broker process, is harder to debug (no persistent log), and loses state on restart. Overkill for our latency requirements (100ms polling is fine). Not recommended unless sub-10ms latency becomes a requirement.

## Recommendation

**CONDITIONAL YES -- Implement SQLite WAL shared state (KB-0016) as the sole coordination system. Do NOT implement the JSONL bus (KB-0015) unless a concrete high-throughput streaming need emerges.**

### Rationale

1. SQLite alone solves 4 gaps fully and 3 partially -- the same coverage as the combined system.
2. The JSONL bus is redundant with SQLite's `messages` table for our message volumes.
3. One system is easier to adopt, debug, and maintain than two.
4. The JSONL bus's advantages (no write contention, lower latency) are irrelevant at our scale.
5. If a streaming need emerges later, the JSONL bus can be added as an optimization without changing the SQLite layer.

### Implementation Priority

1. **Phase 1 (immediate):** Deploy SQLite coordination database with `agents`, `rate_limits`, `rate_limit_config`, and `blockers` tables. Integrate rate limiting into `ddg_utils.py` and other API tools.
2. **Phase 2 (next operation):** Add `phase_signals` and `messages` tables. Update coordinator pattern to use reactive phase triggering.
3. **Phase 3 (when needed):** Add ID allocation table to prevent parallel team ID collisions. Add auto-remediation logic for stale agents.
4. **Deferred:** JSONL bus. Only implement if SQLite write contention becomes measurable (unlikely below 50 agents).

### Remaining Gaps to Address Outside This System

- **Thread safety in ddg_utils.py:** Add `threading.Lock` to the rate limiter class. One-line fix.
- **Orphan detection:** Add `index_rebuilder.py --fix` as a post-commit hook or coordinator task. Already built, just needs automation.
- **ID collisions:** Add an `id_sequences` table to the SQLite coordination database.
