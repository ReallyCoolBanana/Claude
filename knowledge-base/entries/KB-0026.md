# Multi-Agent Coordination System Benchmark Results

## Context
The Proto A multi-agent coordination system (JSONL + SQLite WAL) needed empirical validation across 6 dimensions: communication overhead, team sizing efficiency, failure recovery, capability matching, pipeline correctness, and scaling limits. Previous work built the infrastructure but lacked comprehensive benchmarks measuring real collaboration quality.

## Method
Designed and ran a 20-test benchmark suite (`storage/coordination/overhaul/benchmark_coordination.py`) testing:

1. **Communication Overhead**: Measured bus message volume, ack round-trips, and coordination-to-productive-work ratio with 9 agents across 3 teams
2. **Team Sizing Efficiency**: Ran identical work-stealing tasks with 2, 3, 4, 5 agent teams to validate the E = 4.0 × N^(-0.75) efficiency formula
3. **Failure Recovery**: Injected agent crashes, SQLite contention storms (10 concurrent writers), and help-request race conditions
4. **Capability Matching**: Compared auto-assignment accuracy against random baseline with 5 specialized teams
5. **Pipeline Correctness**: Ran 10 concurrent diamond-DAG pipelines, 1000 concurrent bus messages, and 200-item work-stealing with 10 concurrent stealers
6. **Scaling Limits**: Measured throughput and latency at 5, 10, 20, and 50 concurrent agents

## Result
**20/20 tests passed.** Key findings:

### Communication Overhead
- **Overhead ratio: 6.33 coordination ops per deliverable** (86.4% of total ops are coordination)
- Bus throughput: **~9,500 msg/s** with 9 concurrent agents
- Bus write latency: avg 0.84ms, p95 2.78ms, p99 4.75ms
- Direct channel latency: avg 0.52ms send, batch read at 50,000 msg/s

### Team Sizing Efficiency
- Per-agent throughput drops with team size: 290/agent (2), 170/agent (3), 134/agent (4), 118/agent (5)
- Steal-to-work ratio crosses 1.0 at 4 agents (coordination exceeds productive work)
- **Measured scaling: E = 1.88 × N^(-0.99)** vs expected E = 4.0 × N^(-0.75)
- Exponent delta: 0.24 — degradation is **steeper than the formula predicts**
- Work distribution becomes uneven at 4+ agents (CV: 0.03 at 2 agents → 0.64 at 4 agents)

### Failure Recovery
- Crashed agent detection: 3.0ms (all items accounted for)
- SQLite contention: **100% success rate** with 10 concurrent writers (built-in retry works)
- Max write latency under contention: 230ms (50× average, indicating retry kicks in)
- Help request race: exactly 1 winner out of 5 concurrent offers (BEGIN IMMEDIATE works)

### Capability Matching
- Auto-assignment: **100% accuracy** (10/10 correct matches)
- Random baseline: 0% (expected ~20%)
- Improvement: +100 percentage points over random

### Pipeline Correctness
- 10 concurrent diamond-DAG pipelines: **0 ordering violations**, all completed
- Bus messages: **0 loss** across 1,000 messages from 5 concurrent senders
- Per-sender ordering: **preserved** (POSIX atomic writes work as designed)
- Work stealing: **exactly-once delivery** — 200 items, 10 concurrent stealers, 0 duplicates

### Scaling Limits
- Total throughput plateaus around **640-660 items/s** regardless of agent count (5→50)
- Per-agent throughput: 115.5 (5 agents) → 12.9 (50 agents)
- Steal latency increases: 49ms (5) → 215ms (50 agents)
- **Zero contention events at all scales** (retry logic absorbs it completely)
- Linear scaling efficiency: **11.2%** (significant diminishing returns)
- Biggest efficiency drop at 10 agents (per-agent throughput halves from 5→10)

## Lessons Learned

1. **Coordination overhead is high but acceptable**: 86% of operations are coordination, but the absolute throughput (~9,500 msg/s) means this doesn't bottleneck real agent work which is orders of magnitude slower (LLM inference).

2. **Team sizing formula needs revision**: The actual degradation exponent (-0.99) is steeper than SOP-032's -0.75. For work-stealing with SQLite contention, a better model is **E ≈ 2.0 × N^(-1.0)** — effectively, per-agent throughput is inversely proportional to team size.

3. **Work distribution is the real bottleneck, not contention**: At 4+ agents, work distribution CV exceeds 0.5 (some agents do 3-4× more work than others). The steal-based approach creates "fast stealer" bias where one thread wins the contention lottery repeatedly.

4. **The retry mechanism is the unsung hero**: Zero explicit contention events at any scale. The exponential backoff (0.1-3.2s, 5 retries) in `BEGIN IMMEDIATE` transactions absorbs all SQLite contention silently. Max retry-induced latency is ~230ms.

5. **Total throughput ceiling exists around 650 items/s**: Adding agents beyond 5 doesn't increase total throughput — the shared SQLite database is the serialization point. This is fine for real multi-agent use where each "work item" is an expensive LLM call.

6. **Pipeline DAG execution is rock-solid**: The dependency tracking, fan-in/fan-out, and concurrent completion all work correctly with zero violations across 80 concurrent stages.

## Recommendations

1. **For teams of 2-3 agents**: Best efficiency zone. Steal-to-work ratio stays below 1.0, distribution is even (CV < 0.35). Use this for latency-sensitive work.

2. **For teams of 4+**: Accept uneven distribution. Consider explicit work pre-assignment (round-robin) instead of work-stealing to avoid "fast stealer" bias.

3. **Don't worry about SQLite contention**: The retry mechanism handles it completely up to at least 50 concurrent agents. No need for database partitioning at these scales.

4. **Update the efficiency formula**: Replace E = 4.0 × N^(-0.75) with E ≈ 2.0 × N^(-1.0) based on empirical data. This better predicts the actual coordination overhead.

5. **Bus throughput is not a bottleneck**: At ~9,500 msg/s, the JSONL bus can handle thousands of agents before becoming a concern. The bottleneck is SQLite write serialization in work-stealing.

6. **Run these benchmarks regularly**: Use `python -m storage.coordination.overhaul.benchmark_coordination` as a regression test after any coordination layer changes.
