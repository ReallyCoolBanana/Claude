# Unified Multi-Agent System Benchmark Suite v2.0

## Context
The coordination system had multiple scattered benchmark scripts (benchmark_overhaul.py, benchmark_wave3.py, coord_stress_bench.py) that each tested subsets of the infrastructure. There was no single unified runner that benchmarked all 11 subsystems with consistent methodology, regression detection, and SOP-035 compliance.

## Method
Created `storage/coordination/benchmark_multi_agent.py` -- a comprehensive benchmark suite covering all coordination subsystems:

1. **Coordinator Hub** - Registration, status updates, dashboard reads, instruction delivery
2. **Help Protocol** - Work items, help requests, auto-assignment, idle detection
3. **Work Stealing** - Enqueue, steal (sequential + thundering herd), complete, pipelines
4. **Direct Channels** - send_direct, read_direct, presence, progress updates
5. **Bus Core** - Read/write throughput at 1/4/8/16 agent concurrency levels
6. **Circuit Breaker** - call_allowed (hot path), record outcomes, state transitions
7. **Capability Matching** - register_agent, find_best_match with 20 teams
8. **Load Balancer** - update_load, get_least_loaded across 16 teams
9. **Quality Gates** - define_gate, validate_output throughput
10. **SQLite Contention** - Raw write ops/sec at 1/4/8/16/32 concurrent writers
11. **End-to-End Scenario** - Full multi-team lifecycle (register, distribute, steal, help, communicate, teardown)

## Result
All 11 suites pass. Key findings from 5-iteration, 8-agent benchmark:

| Subsystem | Operation | p95 Latency |
|-----------|-----------|------------|
| Coordinator Hub | Registration | 11.4 ms |
| Coordinator Hub | Status Update | 1.1 ms |
| Coordinator Hub | Dashboard Read | 0.19 ms |
| Help Protocol | Auto-assign (8 teams) | 4.5 ms |
| Work Stealing | Steal (sequential) | 1.6 ms |
| Work Stealing | Steal (thundering herd, 8t) | 80.5 ms |
| Direct Channels | send_direct | 1.9 ms |
| Bus Core | Write (1 agent) | 0.05 ms |
| Bus Core | Write (16 agents) | 4.8 ms |
| Circuit Breaker | call_allowed | 0.46 ms |
| Capability Matching | find_best_match | 0.10 ms |
| Load Balancer | get_least_loaded | 0.07 ms |
| Quality Gates | validate_output | 0.59 ms |
| SQLite Contention | 1 writer | 2,451 ops/sec |
| SQLite Contention | 4 writers | 588 ops/sec (6% efficiency) |
| SQLite Contention | 16 writers | 125 ops/sec (0.3% efficiency) |
| End-to-End | Full scenario (24 agents) | 145 ms total |

**Critical finding confirmed**: SQLite contention cliff at 4+ writers remains the primary scaling bottleneck (6% efficiency at 4 writers, 0.3% at 16).

## Lessons Learned
- Always use the actual API signatures when writing benchmarks (payload must be JSON string, not dict; presence must use valid status enum values)
- Thundering herd work stealing shows 50-80x latency amplification vs sequential (p95: 80ms vs 1.6ms)
- Circuit breaker hot path (call_allowed) is extremely fast at ~0.01ms median, confirming negligible overhead
- Capability matching at 0.05ms median confirms the Wave 3 optimization from 5ms

## Recommendations
- Use `benchmark_multi_agent.py` as the single entry point for all coordination benchmarks
- Run with `--baseline` flag to detect regressions per SOP-035 thresholds
- Keep SQLite writer count under 4 per database partition (SOP-034 guidance confirmed)
- Save benchmark_results.json as baseline before making coordination changes
