# Local GPU Network Assist: RTX 4070 Super Tasks for the Pointer Network

## Context
The pointer network currently has 310 nodes (114 Wikipedia, 57 scripts, 48 sources, 46 KB entries, 22 SOPs, 22 teams, 1 tool) connected by 4,809 edges. The user has expanded the Wikipedia corpus to cover **all of Wikipedia** on their home PC with an RTX 4070 Super (12GB VRAM, 7168 CUDA cores, ~28 TFLOPS FP16).

Run-006 revealed critical structural issues:
- **92 of 114 wiki nodes have ZERO inbound edges** (source-only dead ends)
- **92% of edges are synthetic** (tag/category-based), only 8% are "real" explicit references
- SCR→wiki transitions fail 100% of the time
- Wiki nodes lack categories entirely (all show `none`)
- Edge weights are mostly tangential (weight 1) — the weakest links are paradoxically the most structurally important

The full-Wikipedia expansion means we're going from 114 AI-focused articles to **millions** of articles. A local GPU can process this corpus in ways that cloud-based Claude sessions cannot.

## Method: GPU-Accelerated Tasks

### TIER 1 — Embedding & Semantic Search (Highest Impact)

#### Task 1: Generate Dense Embeddings for All Wikipedia Articles
- **Model**: Run `nomic-embed-text` (137M params, fits easily in 12GB) or `bge-large-en-v1.5` via `sentence-transformers`
- **What it does**: Produce a 768-dim vector for every Wikipedia article (title + first 512 tokens)
- **Output**: An HNSW index (via `faiss-gpu` or `hnswlib`) that allows instant nearest-neighbor lookup
- **Why it matters**: Currently pointer edges are built from string-matching tags. Embeddings find **semantic** relationships that tags miss entirely. An article about "reinforcement learning" would connect to "Markov decision process" even if they share zero tags.
- **Estimated time**: ~6M articles × ~200 articles/sec on 4070S = ~8 hours for full Wikipedia
- **Deliverable**: `wikipedia_embeddings.index` + `id_map.json` mapping vector IDs → article titles

#### Task 2: Semantic Edge Generator
- **What it does**: For each of the 310 pointer network nodes, query the embedding index to find the top-K (K=20) most semantically similar Wikipedia articles. Generate new `semantic_similarity` edges with cosine-similarity weights.
- **Why it matters**: Fixes the "92 wiki nodes with zero inbound edges" problem instantly. Every node in the network gets semantically-grounded connections to relevant Wikipedia content.
- **Output**: `semantic_edges.jsonl` — new edges ready to merge into `pointer-network.json`

#### Task 3: Full-Wikipedia Topic Classifier
- **Model**: Fine-tune or run zero-shot classification (`facebook/bart-large-mnli`, fits in 12GB) to assign categories to all wiki nodes
- **Why it matters**: All 114 wiki nodes currently have `category: none`. This populates them, enabling `category_affinity` edges (currently 708 edges, could grow significantly)
- **Output**: `wiki_categories.json` mapping article → category from the pointer network's taxonomy

### TIER 2 — Graph Intelligence (Medium Impact)

#### Task 4: GPU-Accelerated Pathfinding on Expanded Network
- **What it does**: Use `cugraph` (RAPIDS GPU graph library) to run all 8 pathfinding strategies (PF-01 through PF-08) on the expanded network at GPU speed
- **Why it matters**: Run-006 tested pathfinding on 310 nodes. With millions of Wikipedia nodes, CPU pathfinding becomes intractable. GPU can compute all-pairs-shortest-paths, betweenness centrality, and community detection on the full graph in seconds.
- **Specific computations**:
  - PageRank across the full expanded network (find the most important nodes)
  - Louvain community detection (discover natural topic clusters beyond tag-based clusters)
  - Bridge edge identification (which edges, if removed, increase diameter?)
  - k-core decomposition (find the densely connected core vs. periphery)
- **Output**: `network_analytics.json` with centrality scores, communities, bridge edges

#### Task 5: Link Prediction Model
- **Model**: Train a simple GNN (Graph Neural Network) like GraphSAGE on the existing 4,809 edges to predict missing edges
- **Why it matters**: The network is known to have missing connections (Run-006 found 134 previously unreachable nodes). A GNN trained on the existing edge patterns can predict which node pairs *should* be connected but aren't.
- **Training**: ~4K positive edges + negative sampling, train for 50 epochs on 4070S in minutes
- **Output**: `predicted_edges.jsonl` with confidence scores for proposed new connections

### TIER 3 — Content Processing (Supporting)

#### Task 6: Wikipedia Article Summarization Pipeline
- **Model**: Run `Mistral-7B-Instruct` or `Phi-3-medium` (14B, fits in 12GB at 4-bit) locally
- **What it does**: Generate structured summaries of Wikipedia articles in a format the pointer network can index: key concepts, related topics, domain classification
- **Why it matters**: Claude sessions have limited context windows. Pre-summarized articles mean agents can quickly ingest article content without fetching full text.
- **Output**: `wiki_summaries/` directory with one JSON per article containing structured metadata

#### Task 7: Named Entity Extraction & Cross-Reference Index
- **Model**: Run `spaCy` with `en_core_web_trf` (transformer-backed NER) on GPU
- **What it does**: Extract all named entities (people, organizations, technologies, concepts) from every Wikipedia article. Build a cross-reference index: entity → list of articles mentioning it.
- **Why it matters**: Creates a new edge type `shared_entity` — if two articles both mention "Geoffrey Hinton" or "backpropagation", they get connected even without shared tags.
- **Output**: `entity_index.json` + `entity_edges.jsonl`

#### Task 8: Wikidata Property Extraction
- **What it does**: For each Wikipedia article, fetch its corresponding Wikidata item and extract structured properties (instance_of, subclass_of, part_of, field_of_work, etc.)
- **Why it matters**: Wikidata provides a formal ontology. `instance_of: "machine learning algorithm"` is far more precise than tag-based clustering. Enables ontology-aware pathfinding.
- **Output**: `wikidata_properties.json` mapping article → structured properties

### TIER 4 — Real-Time Assist (Ongoing)

#### Task 9: Local Embedding Search Server
- **What it does**: Run a persistent FastAPI server on the GPU that accepts text queries and returns the top-K most relevant Wikipedia articles from the embedding index
- **API**: `POST /search {"query": "how do transformer attention heads work", "k": 10}`
- **Why it matters**: Any Claude session can query local Wikipedia semantically in real-time. Acts as a personal search engine grounded in the pointer network.
- **Stack**: FastAPI + faiss-gpu + uvicorn, runs continuously in background

#### Task 10: Incremental Network Rebuilder
- **What it does**: Watch for changes to `pointer-network.json` and automatically recompute affected embeddings, edges, and analytics
- **Why it matters**: Currently network rebuilds are manual (SOP-028 OP-07). A GPU daemon can keep the expanded network current as agents add/modify nodes.

## Result
These tasks are ordered by impact-to-effort ratio. The recommended execution order:

1. **Start with Task 1** (embeddings) — everything else depends on this
2. **Then Task 2** (semantic edges) — immediately fixes the dead-end wiki problem
3. **Then Task 9** (search server) — makes the embeddings useful to Claude sessions
4. **Then Task 4** (graph analytics) — reveals network structure at scale
5. **Remaining tasks** in any order based on interest

## Lessons Learned
- The pointer network's biggest weakness is its reliance on string-matching tags for edge creation (92% of edges). Embeddings provide a fundamentally better signal.
- 12GB VRAM is sufficient for all recommended models at INT4/INT8 quantization.
- The 4070 Super's 7168 CUDA cores make it well-suited for batch embedding workloads.
- GPU graph libraries (cugraph/RAPIDS) can handle million-node graphs that would be impractical on CPU.

## Recommendations
- Install `conda` with RAPIDS 24.x for cugraph support on the 4070S
- Use `sentence-transformers` + `faiss-gpu` as the embedding stack (well-tested, good 4070 support)
- Store embeddings in `storage/embeddings/` with the same ID scheme as the pointer network
- New edge types should be added to SOP-028 before merging into the live network
- The FastAPI search server should log queries to `storage/pointer-routes/search_log.jsonl` for route optimization
